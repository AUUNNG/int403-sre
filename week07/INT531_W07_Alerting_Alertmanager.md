## 1. บทนำ: ทำไมระบบแจ้งเตือนส่วนใหญ่จึงล้มเหลว (Why Most Alerts Fail)

ในโลกการปฏิบัติการจริง หลายองค์กรมักมีความเข้าใจผิดว่า **"การมีระบบ Monitoring ใหญ่โตที่จับเมตริกทุกอย่าง แล้วตั้ง Alert ไว้เยอะๆ คือระบบที่ดี"** แต่ความเป็นจริงกลับพบว่าเมื่อเกิดเหตุการณ์ระบบล่ม (Outage) ขึ้นจริง ระบบแจ้งเตือนเหล่านั้นกลับไม่สามารถช่วยเหลืออะไรวิศวกรได้เลย

### ปัญหาสำคัญ 4 ประการของระบบมอนิเตอร์แบบดั้งเดิม:
1. **ภาวะล้าจากการแจ้งเตือน (Alert Fatigue & Notification Blindness)**:
   * เมื่อระบบส่งข้อความแจ้งเตือนที่ไม่ได้สำคัญจริงออกมาอย่างต่อเนื่อง (เช่น วันละหลายร้อยข้อความ) จิตวิทยาของมนุษย์จะเริ่มเพิกเฉย ไม่เปิดอ่าน เปรียบเสมือนการแจ้งเตือนอีเมลในสมาร์ตโฟนที่มีตัวเลขสีแดงค้างไว้เป็นพันๆ ข้อความจนไม่มีใครสนใจ
   * นำไปสู่อาการ **เด็กเลี้ยงแกะ (Crying Wolf Syndrome)** เมื่อเกิดปัญหาคอขาดบาดตายขึ้นจริง วิศวกรก็จะไม่ตอบสนอง
2. **การเฝ้าระวังแบบแยกส่วน (Siloed Monitoring)**:
   * ทีมเซิร์ฟเวอร์มอนิเตอร์เฉพาะ CPU/RAM ของตนเอง ทีมเน็ตเวิร์กมอนิเตอร์เฉพาะพอร์ตสวิตช์ ทีมซอฟต์แวร์ดูเฉพาะ Exception ในโค้ด
   * ปัญหาคือไม่มีวิศวกร SRE ยืนอยู่ตรงกลางเพื่อเชื่อมโยงความสัมพันธ์ (Correlation) เช่น เมื่อ CPU พุ่ง 90% ทีมเซิร์ฟเวอร์เห็นแค่ CPU สูง แต่ไม่รู้ว่าต้นตอมาจากเน็ตเวิร์กที่มีลูปทราฟฟิกมหาศาล หรือแอปรัน Query วนลูป
3. **วัฒนธรรมการรีบูตแก้ปัญหา (Reboot Culture)**:
   * เมื่อไม่มีข้อมูล Observability ที่แท้จริง และระบบส่งเสียงเตือนจนน่ารำคาญ แอดมินมักแก้ปัญหาด้วยการ **"สั่งรีสตาร์ตระบบหรือปิด VM ชั่วคราว"**
   * *ผลกระทบทางวิศวกรรม*: การรีสตาร์ตเป็นการทำลายหลักฐานในหน่วยความจำและร่องรอยการสืบสวน (Forensic Evidence) ทิ้งทั้งหมด เมื่อระบบเปิดกลับขึ้นมาใหม่ ปัญหาเดิมก็จะวนกลับมาเกิดซ้ำอีก
4. **ความรู้ผูกติดอยู่กับบุคคลคนเดียว (Single Point of Knowledge)**:
   * ระบบใหญ่โตแต่มีคนรู้เรื่องอยู่คนเดียว หากคนนั้นลาป่วยหรือไปเที่ยวพักผ่อน ระบบทั้งหมดย่อมตกอยู่ในความเสี่ยงที่ไม่สามารถรับประกันความน่าเชื่อถือได้

## 2. การจำแนกประเภทความผิดพลาดของการแจ้งเตือน (False Positive vs False Negative)

ในการประเมินประสิทธิภาพของระบบ Alerting ต้องเข้าใจความผิดพลาดทั้งสองมิติ:

```
                          สภาพความเป็นจริงในระบบ
                   [มีปัญหาจริง]           [ไม่มีปัญหาจริง]
                +-----------------------+-----------------------+
   [Alert ดัง]  |    True Positive      |    False Positive     |
การ             |  (ยิงถูก ปัญหาจริง)   |  (ยิงมั่ว หลอกแอดมิน)  |
ตัดสินใจ        +-----------------------+-----------------------+
ของระบบ         |    False Negative     |    True Negative      |
   [ไม่ดัง]     |  (พังเงียบ ผู้ใช้ด่า)  |   (ระบบปกติ นิ่งสงบ)   |
                +-----------------------+-----------------------+
```

### 2.1 สัญญาณเตือนหลอกเชิงบวก (False Positive)
* **ลักษณะ**: ปัญหายังไม่ได้เกิดขึ้นจริง หรือเกิดขึ้นเล็กน้อยมากจนผู้ใช้ปลายทางไม่ได้รับผลกระทบใดๆ แต่ระบบกลับยิงสัญญาณเตือนออกมา
* **ผลกระทบ**: วิศวกรต้องเสียเวลาตื่นขึ้นมาดูหน้าจอตอนกลางดึกโดยไม่เกิดประโยชน์ ทำให้เกิดความเหนื่อยล้า และนำไปสู่การละเลยการแจ้งเตือนในระยะยาว

### 2.2 สัญญาณหลุดรอดเชิงลบ (False Negative)
* **ลักษณะ**: ระบบเกิดความล้มเหลว บริการใช้งานไม่ได้จริง แต่ระบบ Alert กลับเงียบสนิท ไม่มีการส่งสัญญาณเตือนใดๆ
* **ผลกระทบ**: วิศวกรและผู้ดูแลระบบจะทราบว่าเกิดปัญหา ก็ต่อเมื่อ **"ผู้ใช้งานโทรศัพท์เข้ามาต่อว่า หรือแจ้งฟ้องเข้ามาเอง"** ซึ่งถือเป็นความล้มเหลวร้ายแรงที่สุดของทีม SRE เพราะคะแนนความน่าเชื่อถือ (Reliability) และงบประมาณความผิดพลาด (Error Budget) ได้ถูกเผาผลาญจนหมดสิ้นไปแล้ว

## 3. การเตือนตามอาการเทียบกับการเตือนตามสาเหตุ (Symptom-based vs Cause-based Alerting)

### 3.1 อุปมาอุปไมยทางการแพทย์ (Doctor Diagnosis Analogy)
* **อาการ (Symptom)**: ผู้ป่วยมาพบแพทย์ด้วยอาการ **"ปวดหัว"** (สิ่งที่ผู้ป่วยรู้สึกและได้รับความทุกข์ทรมานโดยตรง)
* **สาเหตุ (Cause)**: สิ่งที่ซ่อนอยู่ภายในร่างกาย เช่น ความดันโลหิตสูง, อดนอน, สายตาสั้น, หรือเนื้องอกในสมอง

### 3.2 เปรียบเทียบในการบริหารจัดการระบบ SRE

| มิติการเปรียบเทียบ | การแจ้งเตือนตามอาการ (Symptom-based) | การแจ้งเตือนตามสาเหตุ (Cause-based) |
| :--- | :--- | :--- |
| **นิยาม** | เตือนเมื่อ **"ผู้ใช้งานปลายทางได้รับผลกระทบ"** หรือระบบไม่สามารถให้บริการได้ตาม SLO | เตือนเมื่อ **"ทรัพยากรภายในหรือโครงสร้างพื้นฐาน"** มีค่าเปลี่ยนไปตามเงื่อนไข |
| **ตัวอย่าง** | อัตราคำขอ HTTP 5xx พุ่งสูงเกิน 1%, ค่าความหน่วง p95 สูงเกิน 2 วินาที, การล็อกอินล้มเหลว | CPU พุ่งสูง 85%, หน่วยความจำถูกใช้ไป 90%, อินเทอร์เฟซเน็ตเวิร์กมีทราฟฟิกแน่น |
| **ความเหมาะสม** | **เหมาะสำหรับการปลุกคน (Page / On-call Wakeup)** | **เหมาะสำหรับการเปิดใบงาน (Ticket) หรือการวิเคราะห์สืบค้น (Debugging)** |
| **ความเสี่ยง** | ไม่มี เพราะถ้าระบบเตือน แปลว่าผู้ใช้เดือดร้อนจริง | เสี่ยงต่อ False Positive สูงมาก เพราะ CPU 85% ระบบอาจยังตอบสนองผู้ใช้ได้ตามปกติ |

> [!IMPORTANT]
> **กฎเหล็กของ SRE (Golden Rule of Alerting)**:
> **"หากคุณไม่สามารถตอบได้อย่างชัดเจนว่าผู้ใช้คนไหนกำลังเดือดร้อน ห้ามตั้งกฎปลุกวิศวกรให้ตื่นขึ้นมาด้วย Alert ตัวนั้นเด็ดขาด"**  
> การที่ CPU พุ่ง 80-90% แต่ระบบยังคงตอบสนองผู้ใช้ได้ตามมาตรฐาน SLO เมตริกดังกล่าวมีไว้สำหรับให้ระบบ Monitoring สะสมข้อมูล ไม่จำเป็นต้องรีบยิง Alert ออกมาปลุกคน

## 4. 4 คำถามสำคัญก่อนสร้าง Alert ทุกตัว (The 4 Critical Alert Questions)

ก่อนที่วิศวกรจะอนุมัติให้เพิ่มกฎการแจ้งเตือน (Alerting Rule) ใดๆ เข้าสู่ระบบผลิต ต้องตอบคำถาม 4 ข้อนี้ให้ผ่านทั้งหมด:

```
[จะสร้าง Alert ใหม่]
        │
        ▼
1. ผู้ใช้เดือดร้อนจริงหรือไม่? ────(ไม่ใช่)────► ไม่ต้องสร้าง Alert / ให้เก็บเป็น Dashboard
        │ (ใช่)
        ▼
2. มีงานที่ต้องทำทันทีหรือไม่? ────(ไม่ใช่)────► ส่งเข้า Ticket รอเวลาทำการ
        │ (ใช่)
        ▼
3. เร่งด่วนระดับใด? (SLO Burn) ────(ไม่ด่วน)───► ส่งเข้า Ticket / Chat Notification
        │ (ด่วนมาก)
        ▼
4. ใครควรรับ และมี Runbook ไหม? ───(ไม่มี)────► เขียน Runbook ให้เสร็จก่อนสร้าง Alert
        │ (พร้อม)
        ▼
[อนุมัติให้ตั้งกฎ Page On-call]
```

1. **ผู้ใช้กำลังเดือดร้อนจริงหรือไม่ (User Impact)**: มีผลกระทบต่อสัญญา SLO หรือทำให้ผู้ใช้ใช้งานบริการหลักไม่ได้หรือไม่
2. **มีสิ่งที่สามารถลงมือกระทำได้ทันทีหรือไม่ (Actionability)**: หากวิศวกรตื่นขึ้นมาแล้วทำได้แค่นั่งมองหน้าจอ รอให้ระบบหมุนกลับมาเอง หรือไม่สามารถทำอะไรได้เลย ก็ไม่ควรปลุก
3. **มีความเร่งด่วนระดับใด (Urgency)**: ปัญหานี้สามารถรอถึงเวลาทำการ 9:00 น. ในเช้าวันพรุ่งนี้ได้หรือไม่ ถ้ารอได้ ห้ามส่งเสียงเตือนตอนตีสอง
4. **ใครควรเป็นผู้รับ และมีคู่มือปฏิบัติการ (Runbook) แนบไปด้วยหรือไม่**: ระบุทีมเจ้าของระบบให้ถูกต้อง และต้องมีลิงก์ไปยังคู่มือขั้นตอนการแก้ปัญหาที่ตรงจุด

## 5. ลำดับชั้นความรุนแรงและช่องทางการแจ้งเตือน (Alert Severity & Routing Channels)

การแจ้งเตือนตามมาตรฐาน SRE แบ่งออกเป็น 3 ระดับขั้น เพื่อลดภาระและป้องกันอาการเหนื่อยล้าของทีมงาน:

| ระดับความรุนแรง | ช่องทางการส่ง (Channel) | พฤติกรรมที่ระบบต้องการ (Action Required) | ตัวอย่างเหตุการณ์จริง |
| :--- | :--- | :--- | :--- |
| **Page (On-call)** | โทรศัพท์เข้าเบอร์มือถือ, PagerDuty, SMS ฉุกเฉิน | **ต้องตอบสนองทันที (Immediate Response)** ทั้งในและนอกเวลาทำการ วิศวกรเวรต้องล็อกอินเข้าแก้ไขภายใน 5-15 นาที | งบประมาณความผิดพลาดกำลังถูกเผาผลาญหมดใน 1 ชั่วโมง, สวิตช์หลักหรือไฟเบอร์ขาด, ดาต้าเบสไม่ตอบสนอง |
| **Ticket (Work Order)** | Jira Service Desk, ระบบ Ticket กลาง | **ดำเนินการแก้ไขในเวลาทำการ (Business Hours)** มีเวลาจัดการตามข้อตกลง SLA (เช่น ภายใน 24-72 ชม.) | ดิสก์เหลือพื้นที่ว่างต่ำกว่า 20%, แบตเตอรี่ RAID เริ่มเสื่อม, ใบรับรอง TLS จะหมดอายุในอีก 30 วัน |
| **Info / Notification** | ช่อง Slack / Discord รวม, แดชบอร์ดมอนิเตอร์ | **รับทราบเพื่อเป็นข้อมูลบริบท (Passive Context)** ไม่ต้องตอบสนองทันที ไม่มีการส่งเสียงปลุก | การ Deploy เวอร์ชันใหม่สำเร็จ, การสำรองข้อมูลรอบดึกเสร็จสิ้น, สเกล VM อัตโนมัติ |

## 6. การออกแบบ Alert ตามงบประมาณความผิดพลาด (Multi-Window Multi-Burn-Rate Alerting)

การแจ้งเตือนที่ดีที่สุดตามมาตรฐาน Google SRE คือการผูกเงื่อนไขการเตือนเข้ากับ **อัตราการเผาผลาญงบประมาณความผิดพลาด (Burn Rate)** ของเป้าหมาย SLO โดยตรง

### 6.1 สูตรการคำนวณ Burn Rate:
$$\text{Burn Rate (BR)} = \frac{\text{อัตราความผิดพลาดจริง ณ ช่วงเวลานั้น (Observed Error Rate)}}{\text{อัตราความผิดพลาดสูงสุดที่ยอมรับได้ตาม SLO (Budgeted Error Rate)}}$$

* $\text{Burn Rate} = 1$: เผางบประมาณความผิดพลาดหมดพอดีภายในรอบเวลาที่กำหนด (เช่น 30 วัน)
* $\text{Burn Rate} = 14.4$: เผางบประมาณความผิดพลาด 30 วัน หมดลงภายในเวลาเพียง 2 วัน (หรือหมด 2% ใน 1 ชั่วโมง)
* $\text{Burn Rate} = 36$: เผางบประมาณ 30 วัน หมดเกลี้ยงภายใน 20 ชั่วโมง

### 6.2 ตารางมาตรฐานการออกแบบ Multi-Window Multi-Burn-Rate Alerting (สำหรับรอบ 30 วัน):

| อัตราการเผา (Burn Rate) | สัดส่วนงบประมาณที่ถูกเผา | หน้าต่างเวลายาว (Long Window) | หน้าต่างเวลาสั้น (Short Window) | ระดับการเตือน (Severity) | เวลาที่งบประมาณจะหมดเกลี้ยง |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **$14.4 \times$** | $2\%$ ของงบทั้งหมด | $1 \text{ ชั่วโมง}$ | $5 \text{ นาที}$ | **Page (ฉุกเฉิน)** | $2 \text{ วัน}$ |
| **$6 \times$** | $5\%$ ของงบทั้งหมด | $6 \text{ ชั่วโมง}$ | $30 \text{ นาที}$ | **Page (ฉุกเฉิน)** | $5 \text{ วัน}$ |
| **$3 \times$** | $10\%$ ของงบทั้งหมด | $1 \text{ วัน (24 ชม.)}$ | $2 \text{ ชั่วโมง}$ | **Ticket (ใบงาน)** | $10 \text{ วัน}$ |
| **$1 \times$** | $10\%$ ของงบทั้งหมด | $3 \text{ วัน (72 ชม.)}$ | $6 \text{ ชั่วโมง}$ | **Ticket (ใบงาน)** | $30 \text{ วัน}$ |

> [!TIP]
> **ทำไมต้องใช้ทั้ง Long Window และ Short Window ควบคู่กัน?**:
> * **ถ้าใช้เฉพาะ Long Window**: เมื่อระบบหยุดพังแล้ว สัญญาณ Alert จะยังคงค้างอยู่ (Alert Lag) ต่อเนื่องไปอีกหลายชั่วโมง ทำให้วิศวกรสับสน
> * **ถ้าใช้เฉพาะ Short Window**: ปัญหาความผิดพลาดที่เกิดขึ้นเป็นระยะสั้นๆ แล้วหายไป จะทำให้เกิดเสียงเตือนกวนใจ (Alert Flapping)
> * **การใช้คู่กัน (Multi-Window)**: สัญญาณ Alert จะส่งเสียงเฉพาะเมื่อ "มีปัญหาต่อเนื่องในหน้าต่างยาว และ ณ ขณะนี้ (หน้าต่างสั้น) ปัญหาก็ยังคงเกิดขึ้นอยู่จริง"

## 7. ตัวชี้วัดคุณภาพของระบบแจ้งเตือน (Alert Quality Metrics)

ระบบการแจ้งเตือนต้องได้รับการประเมินคุณภาพเชิงวิศวกรรมอย่างต่อเนื่อง โดยมี 4 ดัชนีชี้วัดหลัก:

### 7.1 ความแม่นยำของการแจ้งเตือน (Precision):
$$\text{Precision} = \frac{\text{จำนวน Alert ที่เป็นปัญหาจริง (True Positives)}}{\text{จำนวน Alert ทั้งหมดที่ถูกยิงออกมา (Total Alerts Fired)}} \times 100\%$$
* **เกณฑ์เป้าหมาย**: **ต้องมากกว่าหรือเท่ากับ $90\%$**
* หากยิง Alert ออกมา 20 ครั้ง ต้องเป็นปัญหาจริงอย่างน้อย 18-19 ครั้ง หากเป็นปัญหาจริงเพียง 15 ครั้ง (ได้ 75%) ถือว่าระบบแจ้งเตือนล้มเหลวและต้องได้รับการปรับปรุงทันที

### 7.2 การครอบคลุมปัญหา (Recall):
$$\text{Recall} = \frac{\text{จำนวนปัญหาจริงที่ระบบตรวจจับได้ (Caught Incidents)}}{\text{จำนวนปัญหาจริงทั้งหมดที่เกิดขึ้นในระบบ (Total Real Incidents)}} \times 100\%$$
* **เกณฑ์เป้าหมาย**: **ต้องมากกว่าหรือเท่ากับ $80\%$**
* หากเกิดเหตุการณ์ระบบขัดข้องขึ้นจริง 10 ครั้ง ระบบ Alert ต้องสามารถส่งสัญญาณตรวจจับได้ไม่น้อยกว่า 8 ครั้ง

### 7.3 ความสามารถในการลงมือปฏิบัติจริง (Actionability):
$$\text{Actionability} = \frac{\text{จำนวนครั้งที่ถูกปลุกแล้วมีงานให้แก้ไขจริง (Actionable Pages)}}{\text{จำนวนครั้งที่ถูกส่งสัญญาณ Page ทั้งหมด (Total Pages)}} \times 100\%$$
* **เกณฑ์เป้าหมาย**: **ต้องเท่ากับ $100\%$**
* การปลุกวิศวกรเวร On-call ออกมานั่งดูเฉยๆ โดยไม่มีขั้นตอนให้แก้ไข ถือว่าล้มเหลวโดยสิ้นเชิง

### 7.4 เวลาในการตรวจจับ (Time to Detect: TTD):
* ระยะเวลาตั้งแต่เริ่มเกิดความผิดพลาดในระบบ จนกระทั่งสัญญาณ Alert ถูกยิงออกไป
* **เกณฑ์เป้าหมาย**: ต้องส่งสัญญาณเตือนและเริ่มการแก้ไข **ก่อนที่ผู้ใช้งานปลายทางจะรับรู้หรือติดต่อแจ้งปัญหาเข้ามา**

## 8. สุขอนามัยของทีม On-call และจรรยาบรรณวิศวกรรม (On-call Health & Engineering Hygiene)

### 8.1 การปรับเปลี่ยนทัศนคติต่องาน On-call (De-stigmatizing On-call)
* ในวัฒนธรรมองค์กรทั่วไป วิศวกรมักมองว่าการเข้าเวร On-call คือ **"การถูกลงโทษ (Punishment)"** ที่ทำให้สูญเสียอิสรภาพในการใช้ชีวิต ไม่สามารถไปท่องเที่ยวช่วงวันหยุดยาวได้ เพราะต้องแบกคอมพิวเตอร์และพะวงกับสัญญาณเตือนตลอดเวลา
* แนวทางของ SRE ต้องเปลี่ยนมุมมองว่าการ On-call คืองานวิศวกรรมที่มีระบบระเบียบชัดเจน และระบบต้องมีความเสถียรพอจนไม่ต้องมีการปลุกพร่ำเพรื่อ

### 8.2 กฎเพดานการถูกปลุก (Maximum Paging Threshold)
* **เพดานสูงสุด**: **ไม่เกิน 2 ครั้งต่อหนึ่งกะเวร (Shift)**
* หากวิศวกรถูกปลุกเกินกว่า 2 ครั้งต่อเวรอย่างต่อเนื่อง แสดงว่า **"ระบบมีความน่าเชื่อถือต่ำมาก และระบบการแจ้งเตือนไม่ได้มาตรฐาน"** ผู้บริหารต้องสั่งระงับการปล่อยฟีเจอร์ใหม่ และดึงทีมงานมาแก้ไขเรื่องความเสถียรของระบบทันที

### 8.3 ขนาดทีมและภาระงานที่ยั่งยืน
* ระบบที่มีความสำคัญสูง (Mission-Critical) ไม่สามารถพึ่งพาวิศวกรเพียงคนเดียวหรือสองคนได้ เพราะไม่สามารถลาป่วยหรือลาพักผ่อนได้จริง
* ขนาดทีม On-call ขั้นต่ำควรมีอย่างน้อย 3-4 คน เพื่อให้สามารถหมุนเวียนสลับกะได้อย่างมีสุขอนามัย

### 8.4 บทบาทของปัญญาประดิษฐ์เชิงรุก (Proactive AI Agents) ในงาน SRE ยุค 2026
* **การกรองปัญหาขั้นต้น (L1 Alert Filter)**: นำ AI Agent มาคอยตรวจจับและกลั่นกรอง Alert ก่อนที่จะตัดสินใจยิงสัญญาณ Page ไปปลุกมนุษย์
* **การแก้ไขปัญหาอัตโนมัติ (Automated Remediation)**: สำหรับปัญหาจุกจิกที่มีขั้นตอนแก้ไขตายตัว (เช่น สั่งเคลียร์แคช, รีสตาร์ตพอดที่ค้าง, จัดสรรพื้นที่ดิสก์สำรอง) AI สามารถดำเนินการแก้ไขล่วงหน้า และส่งรายงาน (Resolution Report) สรุปให้วิศวกรทราบในตอนเช้า โดยที่ผู้ใช้งานปลายทางไม่สะดุดและวิศวกรไม่ต้องตื่นกลางดึก

## 9. มาตรฐานคู่มือปฏิบัติการแก้ไขปัญหา (Runbook Engineering Standards)

Alert ทุกตัวที่ส่งสัญญาณ Page **ต้องแนบลิงก์ไปยัง Runbook เสมอ** โดยคู่มือ Runbook ต้องมีคุณลักษณะดังนี้:

1. **สั้น กระชับ ตรงประเด็น**: ไม่มีเนื้อหาอารัมภบทหรือทฤษฎียืดยาว เพราะวิศวกรที่ตื่นขึ้นมาตอนตีสองต้องการขั้นตอนปฏิบัติที่ทำได้ทันที
2. **เรียงลำดับขั้นตอนชัดเจน (Step-by-Step)**:
   * ขั้นตอนที่ 1: คำสั่งตรวจสอบสถานะ (Diagnosis Command)
   * ขั้นตอนที่ 2: ขั้นตอนการบรรเทาปัญหาเฉพาะหน้า (Mitigation Step เช่น Failover, Rate-limit)
   * ขั้นตอนที่ 3: ขั้นตอนการแก้ไขที่สาเหตุ (Root-cause Remediation)
   * ขั้นตอนที่ 4: การตรวจสอบยืนยันว่าระบบกลับสู่สภาวะปกติ (Verification)
   * ขั้นตอนที่ 5: ลำดับการส่งต่อปัญหา (Escalation Path) หากทำตามขั้นตอนแล้วยังไม่สำเร็จ
3. **การทดสอบความถูกต้องของ Runbook (The Outsider Test)**:
   * **บททดสอบที่ดีที่สุด**: นำ Runbook ไปให้วิศวกรที่ไม่ได้อยู่ในทีมหรือไม่เคยดูแลระบบนั้นมาก่อน ทดลองปฏิบัติตาม
   * หากบุคคลภายนอกสามารถทำตามขั้นตอนในคู่มือและแก้ไขปัญหาได้สำเร็จโดยไม่ต้องเอ่ยปากถาม แสดงว่าเป็น Runbook ที่มีคุณภาพสมบูรณ์

## 10. สถาปัตยกรรมการทำงานของ Prometheus Alertmanager

ในสถาปัตยกรรม Prometheus โมดูล **Alertmanager** ทำหน้าที่เป็นศูนย์กลางในการบริหารจัดการสัญญาณเตือนทั้งหมด โดยมี 4 กลไกหลัก:

```
[Prometheus TSDB]
  │ (ประเมิน Alerting Rules ทุก 15 วินาที)
  ▼
[Alertmanager]
  ├── 1. Inhibition (ระงับสัญญาณย่อยเมื่อเหตุใหญ่ล่ม)
  ├── 2. Silencing  (ปิดเสียงชั่วคราวระหว่างซ่อมบำรุง)
  ├── 3. Grouping   (มัดรวม Alert หลายร้อยตัวในเหตุเดียวกัน)
  └── 4. Routing    (ส่งสัญญาณตามระดับความรุนแรง)
        │
        ├──► Page Channel   ──► PagerDuty / On-call Phone
        ├──► Ticket Channel ──► Jira Service Desk
        └──► Info Channel   ──► Slack / Discord Channel
```

### 4 กลไกการทำงานสำคัญของ Alertmanager:
1. **การระงับสัญญาณที่เกี่ยวเนื่อง (Inhibition)**:
   * หากมี Alert ระดับโหนดล่ม (`NodeDown`) ดังขึ้น Alertmanager จะสั่งระงับการแจ้งเตือนระดับย่อยอื่นๆ ทั้งหมดบนโหนดนั้นโดยอัตโนมัติ (เช่น `InstanceDown`, `HighCPU`, `ServiceUnreachable`) เพื่อไม่ให้ข้อความแจ้งเตือนระดมยิงใส่ทีมงาน
2. **การรวมกลุ่มสัญญาณเตือน (Grouping)**:
   * เมื่อเกิดความเสียหายในระบบกระจายตัวที่ทำให้เซอร์วิส 50 ตัวพังพร้อมกัน Alertmanager จะมัดรวมเหตุการณ์ทั้งหมดส่งออกมาเป็นข้อความสรุปเพียง 1 ฉบับ แทนที่จะยิง 50 ครั้งแยกกัน
3. **การกำหนดเส้นทางตามป้ายกำกับ (Routing by Labels)**:
   * คัดแยกเส้นทางการส่งสัญญาณตาม Label เช่น `severity: page` ส่งเข้า PagerDuty, `severity: ticket` ส่งเข้า Jira, และ `team: network` ส่งไปยังวิศวกรเน็ตเวิร์ก
4. **การระงับเสียงเตือนตามกำหนดเวลา (Silencing)**:
   * อนุญาตให้วิศวกรสั่งปิดเสียงเตือนของอุปกรณ์เป้าหมายเป็นการชั่วคราว เมื่อมีแผนเข้าซ่อมบำรุงตามกำหนดเวลา (Scheduled Maintenance) โดยต้องระบุเวลาหมดอายุ (Expiration Time) เสมอ เพื่อป้องกันการลืมเปิดเสียงทิ้งไว้ถาวร

## 11. วงรอบการทบทวนระบบแจ้งเตือนประจำเดือน (Monthly Alert Review Hygiene)

การบริหารจัดการ Alert ไม่ใช่สิ่งที่ตั้งค่าเพียงครั้งเดียวแล้วจบ แต่ต้องมีกระบวนการทบทวนอย่างเป็นระบบ **ทุกๆ 1 เดือน**:

### ขั้นตอนการทบทวน 5 ขั้นตอน:
1. **ดึงข้อมูลสถิติ Alert ทั้งหมดในรอบ 30 วันที่ผ่านมา**: รวบรวมจำนวนครั้งที่ Alert แต่ละตัวส่งสัญญาณเตือนออกมา
2. **จัดอันดับตัวที่ส่งเสียงบ่อยที่สุด (Top Offender Alerts)**: นำ Alert ที่ยิงบ่อยที่สุด 5 อันดับแรกมาพิจารณาอย่างเข้มงวด
3. **ประเมินด้วย 4 คำถามหลัก**: หากพบว่าเป็น Alert ที่ยิงออกมาแล้วไม่มีใครทำอะไร หรือไม่กระทบผู้ใช้ ให้ดำเนินการปรับเพิ่ม Threshold หรือลบทิ้งทันที
4. **ตรวจสอบสถิติเวลาที่วิศวกรต้องตื่นนอน**: คำนวณจำนวนครั้งที่ทีมงานถูกปลุก เพื่อดูว่าเกินเกณฑ์มาตรฐานหรือไม่
5. **สืบค้นเหตุการณ์ที่เกิดขึ้นจริงแต่ไม่มี Alert (Silent Incidents)**: นำปัญหาที่ผู้ใช้แจ้งเข้ามาแต่ระบบมอนิเตอร์ตรวจไม่พบ มาเขียนเป็นกฎ Alerting Rules เพิ่มเติมเพื่อปิดช่องโหว่
