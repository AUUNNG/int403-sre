### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- การเชื่อมโยงเนื้อหากับสัปดาห์ที่ผ่านมา: ในสัปดาห์ที่ 2 เราโฟกัสที่มุมมองของผู้ใช้ (User Perspective) ผ่านตัวชี้วัดระดับการให้บริการ (Service Level: SLA, SLO, SLI) เพื่อประเมินว่า "ผู้ใช้งานกำลังประสบปัญหาหรือเจ็บปวดหรือไม่" แต่ในสัปดาห์ที่ 3 นี้ เราจะทำการเจาะลึก (Drill-down) เข้าไปในระดับระบบภายในและระบบกระจาย (Distributed Systems) เพื่อค้นหาว่า "อะไรคือต้นตอที่ทำให้ระบบล้มเหลวและทำให้ผู้ใช้เจ็บปวด" โดยมุ่งเน้นการชี้เป้าว่าตัวเลขประสิทธิภาพที่เสื่อมถอยลงนั้นมีจุดกำเนิดมาจากทรัพยากรส่วนใด
- ความเข้าใจเรื่องความหลากหลายของฮาร์ดแวร์ในห้องปฏิบัติการ: เครื่องเซิร์ฟเวอร์ที่ใช้งานจริงในศูนย์ข้อมูลหรือในห้องแล็บ แต่ละกลุ่มจะไม่ได้รับเครื่องที่มีคุณสมบัติทางเทคนิคเหมือนกันทั้งหมด บางเครื่องมีหน่วยความจำ (RAM) ปริมาณมาก บางเครื่องมีพื้นที่จัดเก็บข้อมูล (Storage) แตกต่างกัน หรือใช้หน่วยประมวลผล (CPU) คนละรุ่น หัวใจสำคัญของวิศวกร SRE ไม่ใช่การเรียกร้องหาเครื่องที่มีสเปกสูงที่สุดหรือทำงานได้เร็วที่สุด แต่คือการทำความเข้าใจขอบเขตขีดความสามารถ (Boundaries) ของทรัพยากรที่มีอยู่จริง แล้วสามารถวัดผล ตรวจสอบ วิเคราะห์ และบริหารจัดการให้ระบบทำงานได้อย่างมีเสถียรภาพและน่าเชื่อถือภายใต้ข้อจำกัดนั้น

## แผนการเรียนวันนี้ (Agenda)

ช่วงเช้า: ทฤษฎีการวิเคราะห์ระบบและการวินิจฉัยปัญหา  
ช่วงบ่าย: การลงพื้นที่จริงเพื่อขนย้ายอุปกรณ์และทำรายการครุภัณฑ์

1. ทรัพยากรวิกฤต 4 ชนิด (Critical Resources) - สัญญาณบ่งชี้ความอิ่มตัวของทรัพยากรแต่ละชนิด
2. USE / RED / Golden Signals - เช็กลิสต์การตรวจวัดสามชุด และการเลือกใช้ให้ตรงกับเป้าหมายที่กำลังตรวจสอบ
3. ทฤษฎีแถวคอยเบื้องต้น (Queueing Theory) - กฎของลิตเติล (Little's Law) และเหตุผลที่ระดับ 80% คือเส้นแบ่งวิกฤต
4. โหมดความล้มเหลวของระบบกระจาย (Distributed Systems Failure Modes) - ความล้มเหลวแบบลูกโซ่ (Cascading Failure), พายุการส่งซ้ำ (Retry Storm) และงบประมาณเวลา (Timeout Budget)
5. ตู้แร็กในฐานะระบบกระจาย (Rack as a Distributed System) - การเชื่อมโยงทฤษฎีระบบเข้ากับงานภาคสนาม
6. ภาคบ่าย: ปฏิบัติการลงพื้นที่จริง (Field Operations) - การลงทะเบียนเข้าพื้นที่ การรื้อถอนอุปกรณ์ และการทำทะเบียนครุภัณฑ์

## ผลลัพธ์การเรียนรู้ประจำคาบ (Specific Learning Outcomes: SLO)

เมื่อสิ้นสุดการเรียนรู้ในคาบนี้ นักศึกษาจะสามารถ:

- SLO 3.1: ประยุกต์ใช้เมธอด USE และ RED ในการวิเคราะห์ทรัพยากรและบริการได้อย่างเป็นระบบ (CLO5)
- SLO 3.2: ใช้เครื่องมือบรรทัดคำสั่งบนระบบปฏิบัติการ Linux ในการระบุคอขวดของระบบจากสัญญาณความอิ่มตัวได้ถูกต้อง (CLO5)
- SLO 3.3: อธิบายความสัมพันธ์ระหว่างอัตราการใช้งาน (Utilization), แถวคอย (Queue) และความหน่วงเวลา (Latency) ตามกฎของลิตเติล (Little's Law) ได้ (CLO5)
- SLO 3.4: อธิบายโหมดความล้มเหลวของระบบกระจายและระบุจุดตัดวงจรความล้มเหลวได้อย่างถูกต้อง (CLO1, CLO5)
- SLO 3.5: ปฏิบัติตามขั้นตอนการเข้าพื้นที่ศูนย์ข้อมูล การรื้อถอนขนย้าย และการบันทึกทะเบียนครุภัณฑ์ตามมาตรฐานความปลอดภัยได้ถูกต้อง (CLO3, CLO7)

### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- กรอบการประเมินและแนวข้อสอบ: สไลด์ผลลัพธ์การเรียนรู้ประจำคาบ (SLO) คือพิมพ์เขียวหลักในการออกแบบข้อสอบวัดผลของรายวิชานี้ ข้อสอบจะไม่เน้นการท่องจำความหมายแบบตื้นเขิน แต่จะให้นักศึกษาอธิบายความสัมพันธ์เชิงระบบ เช่น การวิเคราะห์ตัวเลขความสัมพันธ์ระหว่าง Utilization และ Latency ตาม Little's Law, การคำนวณส่วนเผื่อความจุ (Headroom) เมื่อระบบสูญเสียโหนดประมวลผล (N-1 Redundancy), ลำดับการเกิด Cascading Failure และกลไกการสกัดกั้น, ตลอดจนขั้นตอนการปฏิบัติงานหน้างานตามมาตรฐานความปลอดภัยทางวิศวกรรม

## ส่วนที่ 1: พื้นฐานระบบและระบบกระจาย — หาว่าตัวเลขที่แย่ลงมาจากตรงไหน

ในสัปดาห์ก่อนหน้า เราได้ศึกษาการตรวจวัดมุมมองจากฝั่งผู้ใช้งานผ่านตัวชี้วัดระดับการให้บริการ (Service Level Indicators: SLI) และเป้าหมายระดับการให้บริการ (Service Level Objectives: SLO) ทำให้ทราบว่า "ผู้ใช้งานกำลังประสบปัญหา (ผู้ใช้เจ็บ)" หรือไม่ แต่ในสัปดาห์นี้ เป้าหมายสำคัญคือการเจาะลึกเข้าไปในระบบเพื่อตอบคำถามว่า "อะไรคือสิ่งที่ทำให้เกิดปัญหา (อะไรทำให้เจ็บ)" และระบุให้ได้ว่าตัวเลขประสิทธิภาพที่เสื่อมถอยลงนั้นมีต้นตอมาจากจุดใด

### 1.1 ทรัพยากรวิกฤต 4 ชนิด และสัญญาณบ่งชี้ความอิ่มตัว

ในการวิเคราะห์ระบบคอมพิวเตอร์ระดับโครงสร้างพื้นฐาน ทรัพยากรหลักที่ต้องตรวจสอบประกอบด้วย หน่วยประมวลผลกลาง (CPU), หน่วยความจำหลัก (Memory), ระบบอินพุต/เอาต์พุตของดิสก์ (Disk I/O) และระบบเครือข่าย (Network)

หลักการสำคัญ: อัตราการใช้งาน (Utilization) บอกเพียงว่าเราใช้ทรัพยากรไปแล้วเท่าไร แต่ความอิ่มตัว (Saturation) คือตัวชี้วัดที่แท้จริงที่บ่งบอกว่าระบบกำลังจะล่มสลาย

| ทรัพยากร (Resource) | ตัวชี้วัดอัตราการใช้งาน (Utilization) | สัญญาณความอิ่มตัวที่ต้องตรวจวัด (Saturation) | อาการที่ผู้ใช้งานรับรู้ (User Experience Impact) |
|---|---|---|---|
| หน่วยประมวลผล (CPU) | เปอร์เซ็นต์การใช้งานต่อคอร์ (% CPU utilization per core) | คิวงานรอรันยาว (Run queue length), ค่าการแย่งเวลาประมวลผลสูง (CPU steal), การสลับบริบทพุ่งสูง (Context switch spike) | ระบบและทุกบริการทำงานช้าลงพร้อมกันอย่างสม่ำเสมอ |
| หน่วยความจำ (Memory) | สัดส่วนหน่วยความจำที่ถูกใช้งานจริง (Resident memory used) | หน่วยความจำเสมือนเริ่มทำงาน (Swap active), อัตราความผิดพร่องของหน้าหน่วยความจำสูง (Page fault high), กลไกสังหารโพรเซสทำงาน (OOM Killer triggered) | ระบบค้างและสะดุดเป็นช่วงๆ ก่อนที่บริการจะหยุดทำงานหรือดับหายไปโดยไม่แจ้งเตือน |
| ดิสก์ I/O (Disk I/O) | เปอร์เซ็นต์เวลาที่อุปกรณ์ดิสก์ทำงาน (% disk utilization) | คิว I/O รอประมวลผลยาว (I/O queue length), เวลารอคอยเฉลี่ยสูงกว่าเวลาให้บริการจริงมาก (await >> svctm) | คำสั่งหรือฟังก์ชันที่ต้องอ่านหรือเขียนข้อมูลช้าลงอย่างมาก แต่หน้าเว็บส่วนอื่นที่อ่านจากแคชยังทำงานได้ปกติ |
| เครือข่าย (Network) | ปริมาณแบนด์วิดท์ที่ใช้งานเทียบกับพิกัดสูงสุด (Bandwidth utilization vs capacity) | อัตราแพ็กเก็ตตกหล่น (Dropped packets), อัตราการส่งซ้ำระดับ TCP (TCP retransmits), คิวส่งข้อมูลเต็ม (TX/RX buffer queue full) | ความเร็วไม่สม่ำเสมอ การเชื่อมต่อสะดุด บางคำขอผ่านได้ตามปกติแต่บางคำขอค้างหรือหลุดการเชื่อมต่อ |

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- การเปรียบเทียบ Saturation กับการปรับแต่งภาพและวิดีโอ:
  - คนทั่วไปเวลาตรวจสอบระบบมักดูเพียงค่า Utilization ผ่านเครื่องมือพื้นฐาน เช่น Windows Task Manager แล้วมองดูว่า CPU ใช้งานกี่เปอร์เซ็นต์ หรือ RAM มี 16 GB ถูกใช้ไปแล้ว 14 GB แล้วด่วนสรุปว่าระบบยังปกติหรือช้าเพราะแรมใกล้เต็ม
  - แต่ในมุมมองของ SRE คำว่า "Saturation" แปลว่า "ความอิ่มตัว" ซึ่งเปรียบได้กับการปรับค่า Saturation ของสีในโปรแกรมแต่งภาพถ่ายหรือตัดต่อวิดีโอ หากปรับแต่งในระดับที่พอเหมาะ เม็ดสีจะอิ่ม ชัดเจน และสวยงาม (สีแดงสด สีเขียวสด) แต่หากปรับเพิ่มค่า Saturation เกินขีดจำกัดที่ภาพจะรับได้ (Over-saturated) ภาพทั้งใบจะเละ เม็ดสีจะแตก ช้ำ และบิดเบือนจากความเป็นจริงอย่างสิ้นเชิง
  - ในระบบคอมพิวเตอร์ก็เช่นเดียวกัน เมื่อทรัพยากรเกิดความอิ่มตัวเกินขีดจำกัดที่โครงสร้างระบบจะรองรับได้ คิวงานจะล้นทะลัก และระบบจะไม่ใช่แค่ช้าลง แต่จะเกิดอาการค้าง ชะงัก (Hang) หรือหยุดการทำงานลงทันที
- การทำงานของหน่วยความจำ (Memory), กลไก Swap, Page Fault และ OOM Killer:
  - การทำความเข้าใจพฤติกรรมของหน่วยความจำเชื่อมโยงโดยตรงกับวิชาโครงสร้างสถาปัตยกรรมและแพลตฟอร์มระบบคอมพิวเตอร์ (Computer Platform & Operating Systems) ในหัวข้อ CPU Architecture และ Memory Allocation
  - กลไก Swap: โดยปกติระบบปฏิบัติการจะจัดสรรพื้นที่ Swap เอาไว้บนดิสก์หรือ SSD ข้อมูลใน RAM มีความเร็วในการเข้าถึงสูงกว่าดิสก์หลายร้อยเท่า เมื่อระบบตรวจพบว่าหน่วยความจำกายภาพ (Physical RAM) เริ่มไม่เพียงพอ ระบบปฏิบัติการจะเริ่มย้ายหน้าหน่วยความจำ (Memory Pages) ที่ไม่ได้ถูกเรียกใช้งานบ่อยออกไปพักไว้ในพื้นที่ Swap บนดิสก์ ดังนั้น เมื่อใดก็ตามที่ระบบเริ่มมีกิจกรรม Swap เกิดขึ้น นั่นคือสัญญาณเตือนขั้นแรกว่าระบบเริ่มอิ่มตัวและประสิทธิภาพจะลดลงอย่างมีนัยสำคัญ
  - อัตรา Page Fault สูง: เกิดขึ้นเมื่อโพรเซสต้องการเข้าถึงข้อมูลในหน้าหน่วยความจำ แต่หน้านั้นไม่ได้อยู่ใน RAM กายภาพ (อาจถูกย้ายไปอยู่ใน Swap หรือยังไม่ได้ถูกโหลดขึ้นมา) ทำให้ซีพียูต้องระงับการทำงานของโพรเซสชั่วคราวเพื่อรอให้ระบบปฏิบัติการอ่านข้อมูลจากดิสก์กลับเข้ามาใน RAM
  - กลไก Out-of-Memory Killer (OOM Killer): หากหน่วยความจำกายภาพและพื้นที่ Swap เต็มอย่างสมบูรณ์จนระบบปฏิบัติการไม่สามารถจัดสรรหน่วยความจำให้แก่ระบบต่อไปได้ เคอร์เนลของ Linux จะเปิดใช้งานกลไก OOM Killer ทันที โดยเคอร์เนลจะคำนวณคะแนน (OOM Score) แล้วเลือกสั่งปิดหรือกำจัด (Kill/Drop) โพรเซสที่กินหน่วยความจำมากที่สุดทิ้งทันที อาการที่ปรากฏต่อผู้ใช้งานคือ เมื่อเปิดแอปพลิเคชันขึ้นมา หน้าจอแรกอาจเด้งขึ้นมาสักครู่แล้วหน้าต่างแอปพลิเคชันก็ปิดตัวดับหายไปในทันทีโดยไม่มีข้อความแจ้งเตือนความผิดพลาดใดๆ
- สัญญาณความอิ่มตัวของทรัพยากรอื่น:
  - CPU Saturation: ต้องดูที่ความยาวของคิวงานรอรับบริการ (Run Queue Length), การสลับบริบทการทำงาน (Context Switching พุ่งสูง) และค่า CPU Steal (กรณีใช้งานบนสภาพแวดล้อมเสมือนหรือคลาวด์ ซึ่งบ่งบอกว่าเครื่องโฮสต์จริงกำลังแย่งเวลาซีพียูไปให้ Virtual Machine เครื่องอื่น) ทำให้อาการที่ผู้ใช้รู้สึกคือทุกบริการบนเครื่องทำงานช้าลงพร้อมๆ กันอย่างเท่าเทียม
  - Disk I/O Saturation: สังเกตจากค่าความแตกต่างระหว่างเวลารวมของคำขอ (`await`) กับเวลาที่ฮาร์ดแวร์ให้บริการจริง (`svctm`) หากค่ารอคอยสูง แสดงว่ามีคิวสะสมหน่วงอยู่หน้าดิสก์ ส่งผลให้คำสั่งค้นหาหรือเขียนฐานข้อมูลช้าลงอย่างมาก แต่หน้าเว็บที่โหลดเนื้อหาคงที่ (Static Assets) ยังทำงานได้ตามปกติ
  - Network Saturation: สังเกตจากอัตราแพ็กเก็ตตกหล่น (Dropped Packets), การส่งแพ็กเก็ตซ้ำในระดับโพรโทคอล TCP (TCP Retransmissions) และคิวบัฟเฟอร์รับส่งข้อมูลที่เต็ม ทำให้ผู้ใช้สัมผัสได้ถึงความหน่วงที่ไม่สม่ำเสมอ บางคำขอผ่านได้รวดเร็วแต่บางคำขอเกิดอาการค้างตัดการเชื่อมต่อ

### 1.2 กรอบการตรวจวัดสามชุด: USE, RED และ Google Golden Signals

การเลือกใช้กรอบการตรวจสอบต้องสอดคล้องกับชั้นของระบบที่กำลังพิจารณา การใช้เครื่องมือผิดชุดจะทำให้ไม่สามารถตรวจพบต้นเหตุของปัญหาได้

#### 1. เมธอด USE (USE Method)
- พัฒนาโดย: เบรนแดน เกรกก์ (Brendan Gregg)
- มุ่งเน้น: มุ่งเน้นทรัพยากรเป็นศูนย์กลาง (Resource-centric)
- ขอบเขต: ใช้สำหรับวิเคราะห์ชิ้นส่วนโครงสร้างพื้นฐานระดับล่าง เช่น CPU, หน่วยความจำ, ดิสก์, และอินเทอร์เฟซเครือข่าย
- คำถามหลัก: ทรัพยากรชิ้นใดกำลังมีปัญหาหรือเป็นคอขวด?
- องค์ประกอบ:
  - อัตราการใช้งาน (Utilization): สัดส่วนเวลาหรือความจุที่ทรัพยากรถูกใช้งาน (คิดเป็นเปอร์เซ็นต์)
  - ความอิ่มตัว (Saturation): ปริมาณงานที่ค้างรอคิวเนื่องจากทรัพยากรให้บริการไม่ทัน (ความยาวคิว)
  - ข้อผิดพลาด (Errors): จำนวนครั้งที่เกิดเหตุการณ์ผิดพลาดในระดับฮาร์ดแวร์หรืออุปกรณ์

#### 2. เมธอด RED (RED Method)
- พัฒนาโดย: ทอม วิลกี (Tom Wilkie)
- มุ่งเน้น: มุ่งเน้นบริการและคำขอเป็นศูนย์กลาง (Service-centric / Request-driven)
- ขอบเขต: เหมาะสำหรับสถาปัตยกรรมไมโครเซอร์วิส (Microservices), เว็บแอปพลิเคชัน และ Application Programming Interfaces (API)
- คำถามหลัก: ผู้ใช้งานกำลังสัมผัสกับประสิทธิภาพในระดับใด?
- องค์ประกอบ:
  - อัตราคำขอ (Rate): ปริมาณคำขอที่ส่งเข้ามายังบริการต่อหนึ่งหน่วยเวลา (Requests per second)
  - ข้อผิดพลาด (Errors): ปริมาณหรืออัตราของคำขอที่ไม่สำเร็จต่อหนึ่งหน่วยเวลา (Failed requests per second)
  - ระยะเวลาตอบสนอง (Duration): การกระจายตัวของเวลาที่ใช้ในการประมวลผลแต่ละคำขอ (Latency distribution / Percentiles)

#### 3. สัญญาณทองคำ 4 ประการ (Google 4 Golden Signals)
- พัฒนาโดย: ทีมวิศวกรรมความน่าเชื่อถือของกูเกิล (Google Site Reliability Engineering)
- มุ่งเน้น: ครอบคลุมทั้งมุมมองบริการที่ผู้ใช้สัมผัส และมุมมองความจุของระบบ (อิงตามหนังสือ Google SRE Book บทที่ 6: Monitoring Distributed Systems)
- องค์ประกอบ:
  - ความหน่วงเวลา (Latency): เวลาที่ใช้ในการประมวลผลคำขอ โดยต้องแยกแยะระหว่างคำขอที่สำเร็จและคำขอที่ล้มเหลวอย่างชัดเจน
  - ปริมาณการใช้งาน (Traffic): การวัดปริมาณความต้องการที่มีต่อระบบ เช่น HTTP Requests per second หรือ Network I/O
  - ข้อผิดพลาด (Errors): อัตราการล้มเหลวของคำขอ ทั้งที่ระบุชัดเจนด้วยรหัสสถานะ (Explicit failure เช่น HTTP 500) และที่ส่งเนื้อหาผิดพลาดกลับไป (Implicit failure เช่น HTTP 200 แต่มีข้อความแจ้งเตือนข้อผิดพลาด)
  - ความอิ่มตัว (Saturation): สัดส่วนความจุของระบบและทรัพยากรที่ถูกใช้ไป ซึ่งทำหน้าที่เป็นตัวชี้วัดล่วงหน้าก่อนที่ระบบจะเริ่มล้มเหลว

#### ตารางเปรียบเทียบกรอบการตรวจวัดทั้งสามรูปแบบ

| เกณฑ์การเปรียบเทียบ | USE Method | RED Method | Google Golden Signals |
|---|---|---|---|
| จุดโฟกัสหลัก | ทรัพยากรระบบ (Hardware / OS Resources) | บริการและคำขอ (Software Services / APIs) | ภาพรวมบริการและความจุ (User Experience + Capacity) |
| ผู้พัฒนา | Brendan Gregg | Tom Wilkie | Google SRE Team |
| มิติที่ตรวจวัด | Utilization, Saturation, Errors | Rate, Errors, Duration | Latency, Traffic, Errors, Saturation |
| ประโยชน์หลัก | ใช้ชี้เป้าว่า "ทรัพยากรตัวไหนเป็นสาเหตุ" (Cause) | ใช้วัดว่า "ผู้ใช้กำลังได้รับผลกระทบอย่างไร" (Symptom) | ใช้เป็นแดชบอร์ดภาพรวมและระบบแจ้งเตือนเชิงรุก (Holistic SRE Monitoring) |
| ระดับชั้นที่ใช้งาน | ชั้นระบบปฏิบัติการ, ฮาร์ดแวร์, คอนเทนเนอร์โฮสต์ | ชั้นแอปพลิเคชัน, เอนด์พอยต์ API, ไมโครเซอร์วิส | ครอบคลุมทั้งชั้นผู้ใช้งาน, แอปพลิเคชัน และระบบหลังบ้าน |

กฎการใช้งานร่วมกัน: 
- RED บอกว่าผู้ใช้กำลังเจ็บปวด (User Symptom)
- USE บอกว่าทรัพยากรตัวใดเป็นตัวการทำให้เจ็บปวด (Underlying Cause)
- ในงานวิศวกรรมความน่าเชื่อถือ วิศวกรจำเป็นต้องใช้ทั้งสองชุดควบคู่กันเสมอ

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- ปัญหาการทำงานแบบแยกส่วน (Dev vs. Infra Silo) และกรณีศึกษาระบบลงทะเบียน:
  - ในโลกการทำงานจริง ปัญหาคลาสสิกที่พบบ่อยมากคือทีมดูแลโครงสร้างพื้นฐาน (Infrastructure Team) และทีมนักพัฒนาซอฟต์แวร์ (Developer Team) ทำงานแยกขาดจากกันอย่างสิ้นเชิง เมื่อเกิดปัญหาระบบช้า ทีม Infra มักตรวจสอบดูเพียงแค่ค่า Utilization พื้นฐาน เช่น เห็นว่า CPU หรือ Network มีการใช้งานสูง แต่ไม่ทราบว่าสูงมาจากอะไร เมื่อไม่ทราบสาเหตุก็มักแก้ปัญหาที่ปลายเหตุ เช่น การสั่งปิดเครื่อง (Shutdown) หรือแจ้งว่าเซิร์ฟเวอร์ยังปกติเพราะแรมเหลือ
  - ตัวอย่างจริงที่เคยเกิดขึ้นในระบบลงทะเบียนเรียน: เมื่อมีนักศึกษาเข้าใช้งานพร้อมกันจำนวนมาก ระบบเกิดอาการค้างและช้าอย่างหนัก ในอดีตทีมผู้ดูแลมักสรุปปัญหาแบบผิวเผินว่า "แรมไม่พอ" แล้วแก้ปัญหาด้วยการของบประมาณจัดซื้อแรมเพิ่ม จากเดิม 16 GB ขยายเป็น 32 GB และขยายเป็น 64 GB หรือเปลี่ยนฮาร์ดดิสก์ไปเป็น SSD/NVMe ราคาแพง ซึ่งเป็นการแก้ปัญหาที่ปลายเหตุ เพราะแท้จริงแล้วต้นเหตุเกิดจากโค้ดของแอปพลิเคชันที่เขียนคำสั่งค้นหาฐานข้อมูล (Database Query) แบบวนลูปซ้ำๆ โดยไม่มีการทำ Caching ข้อมูล ดึงข้อมูลก้อนใหญ่ซ้ำไปซ้ำมา ส่งผลให้เกิด I/O Saturation ที่ฐานข้อมูล
  - หน้าที่สำคัญของวิศวกร SRE คือการทำหน้าที่เป็นสะพานเชื่อมระหว่างโค้ดและโครงสร้างพื้นฐาน โดยใช้กรอบ RED และ USE เข้ามาจำแนกอาการ (Symptom) ออกจากสาเหตุรากเหง้า (Cause) อย่างเป็นวิทยาศาสตร์
- คำแนะนำสำหรับการจัดทำโครงงานจบและพอร์ตโฟลิโอวิศวกร SRE:
  - ในการทำโครงงานระดับ Capstone การติดตั้งเครื่องมือ Monitoring อย่าง Prometheus หรือ Grafana เป็นเรื่องทางเทคนิคพื้นฐานที่ทุกคนสามารถทำตามคู่มือได้ แต่สิ่งที่มีมูลค่าสูงและสร้างความแตกต่างอย่างแท้จริงคือ "การรู้ว่าจะวัดค่าอะไร และตั้งเกณฑ์การแจ้งเตือน (Alerting Rules) อย่างไรให้มีความหมาย"
  - การออกแบบแดชบอร์ดที่สะท้อน Golden Signals และ USE Method อย่างเป็นระบบ พร้อมทั้งการกำหนดค่า SLI/SLO และการทดสอบระบบด้วยการยิงโหลดจำลอง (Load/Stress Testing เช่น ยิงโหลด 200 หรือ 500 requests/sec) ถือเป็นผลงานเชิงประจักษ์ชั้นยอดที่สามารถนำไปใช้อธิบายในกระบวนการสัมภาษณ์งานตำแหน่ง SRE, DevOps Engineer หรือ Systems Engineer ได้อย่างน่าเชื่อถือ

### 1.3 เครื่องมือคำสั่งจริงสำหรับการวินิจฉัยบนระบบปฏิบัติการ Linux

การวิเคราะห์ระบบบนลินุกซ์ไม่จำเป็นต้องใช้คำสั่งจำนวนมาก แต่ต้องเข้าใจว่าคำสั่งแต่ละตัวตอบคำถามอะไร และควรมุ่งเน้นดูค่าใดเป็นลำดับแรก

| คำสั่ง (Command) | ตอบคำถามว่า | จุดตรวจวัดที่ต้องดูเป็นอันดับแรก (Primary Inspection Metric) |
|---|---|---|
| `uptime` / `top` | ระบบมีงานคั่งค้างสะสมมากน้อยเพียงใด | ค่าเฉลี่ยภาระงาน (Load average 1, 5, 15 นาที) เทียบกับจำนวนคอร์ประมวลผล (Logical CPU Cores) หาก Load Average เกินจำนวนคอร์ แสดงว่ามีคิวงานรอรับบริการ |
| `vmstat 1` | หน่วยความจำและซีพียูกำลังเกิดภาวะอึดอัดหรือไม่ | คอลัมน์ `r` (จำนวนโพรเซสในคิวรอประมวลผล CPU) และคอลัมน์ `si`/`so` (อัตราการอ่านเข้า/เขียนออกพื้นที่ Swap) |
| `iostat -xz 1` | ระบบจัดเก็บข้อมูลดิสก์กลายเป็นคอขวดหรือไม่ | คอลัมน์ `%util` (เปอร์เซ็นต์เวลาทำงานของดิสก์) และค่า `await` (เวลารวมที่คำขอใช้รอและประมวลผล) หาก `await` สูงกว่า `svctm` มาก แสดงว่ามีคิวรอ I/O หน่วงสะสม |
| `ss -s` / `ss -tin` | ระบบเครือข่ายและการเชื่อมต่อมีปัญหาติดขัดอะไร | จำนวนการเชื่อมต่อที่คั่งค้าง (Sockets in ESTAB/TIME-WAIT), อัตราการส่งซ้ำ (Retransmit count), และขนาดคิวรับส่ง (Send-Q / Recv-Q) |
| `dmesg -T \| tail` | เคอร์เนลตรวจพบและบันทึกความผิดปกติอะไรไว้บ้าง | ข้อความแจ้งเตือนจากหน่วยความจำเต็ม (Out of Memory: OOM Killer), ข้อผิดพลาดของคอนโทรลเลอร์หรือบล็อกข้อมูลดิสก์ (Disk I/O error), และการรีเซ็ตบัสของฮาร์ดแวร์ |
| `pidstat 1` | โพรเซสหรือกระบวนการใดที่บริโภคทรัพยากรผิดปกติ | จัดเรียงดูตามการบริโภค CPU (`%CPU`) และการอ่านเขียนดิสก์ (`kB_rd/s`, `kB_wr/s`) เพื่อระบุตัวการที่แท้จริง |

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- การนำคำสั่ง Linux ไปใช้งานจริงอย่างมีเป้าหมาย:
  - ในการทำงานจริงไม่ต้องจำคำสั่งทุกตัวในระบบ แต่ต้องรู้ว่าคำสั่งหลัก 6 คำสั่งนี้ใช้ตอบคำถามอะไรในแต่ละสถานการณ์
  - การตีความค่า `uptime` และ `top`: ค่า Load Average 3 ตัวแทนช่วงเวลา 1 นาที, 5 นาที และ 15 นาที หากเซิร์ฟเวอร์ของเรามี 2 คอร์ประมวลผล แต่ค่า Load Average พุ่งขึ้นไปที่ 4.0 หมายความว่า ณ ขณะนั้น มีโพรเซสที่กำลังรอคิวเข้าใช้ CPU เฉลี่ยถึง 2 โพรเซสตลอดเวลา ซึ่งบ่งชี้สภาวะ CPU Saturation อย่างชัดเจน
  - การตีความ `vmstat 1`: คอลัมน์ `r` (Runnable) แสดงจำนวนโพรเซสที่รอเข้าซีพียู หากสูงกว่าจำนวนคอร์คือเกิดคิว และให้สังเกตคอลัมน์ `si` (Swap-in) กับ `so` (Swap-out) หากมีตัวเลขวิ่งต่อเนื่อง แสดงว่าระบบปฏิบัติการกำลังดิ้นรนสลับหน้าหน่วยความจำกับดิสก์ตลอดเวลา
  - ความสำคัญของ `dmesg -T`: ข้อความใน Kernel Ring Buffer คือหลักฐานชี้ขาดในการวินิจฉัยปัญหาของฮาร์ดแวร์ระดับล่าง หากเกิดความผิดปกติของดิสก์ แบตเตอรี่เสื่อม หรือ OOM Killer สั่งฆ่าโพรเซส ข้อมูลเหล่านี้จะถูกบันทึกไว้ในเคอร์เนลเสมอ

### 1.4 ตัวอย่างการวินิจฉัยปัญหาตามลำดับขั้นด้วย USE Method (Worked Diagnosis)

กรณีศึกษาจำลอง: ศูนย์คอมพิวเตอร์ได้รับแจ้งจากผู้ใช้งานว่าระบบลงทะเบียนเรียนทำงานช้าลงอย่างมากนับตั้งแต่เวลา 09:00 น.

ลำดับขั้นตอนการสืบค้นอย่างเป็นระบบ:

1. เริ่มต้นวิเคราะห์จากฝั่งผู้ใช้งานก่อนเสมอ (User-facing Inspection):
   - ตรวจสอบตัวชี้วัด RED ของบริการลงทะเบียน พบว่าเวลาตอบสนองที่เปอร์เซ็นไทล์ 99 (p99 Latency) เพิ่มสูงขึ้นจาก 400 มิลลิวินาทีเป็น 3.2 วินาที
   - อัตราข้อผิดพลาด (Error Rate) ยังคงอยู่ที่ระดับปกติ (ไม่มีข้อผิดพลาดรหัส HTTP 500)
   - ข้อสรุปเบื้องต้น: ระบบไม่ได้หยุดทำงานหรือพังทลาย แต่กำลังเผชิญภาวะความหน่วงรุนแรง (Degraded Performance)

2. ไล่เรียงตรวจสอบลงไปตามลำดับชั้นสถาปัตยกรรม (Downstream Isolation):
   - ชั้นเว็บเซิร์ฟเวอร์ (Web Tier): เวลาตอบสนองภายในชั้นนี้ยังคงปกติ
   - ชั้นแอปพลิเคชัน (API Tier): ค่า p99 Latency ปรับตัวสูงขึ้นสอดคล้องกับฝั่งผู้ใช้งาน
   - ชั้นฐานข้อมูล (Database Tier): ค่า p99 Query Latency ปรับตัวพุ่งสูงขึ้นตามเช่นกัน
   - ข้อสรุป: ต้นตอของปัญหาคอขวดอยู่ที่ชั้นฐานข้อมูล หรือระบบโครงสร้างพื้นฐานที่อยู่ต่ำกว่าฐานข้อมูล

3. ใช้เมธอด USE กับเซิร์ฟเวอร์ฐานข้อมูล (Applying USE on Database Host):
   - ตรวจสอบ CPU Utilization พบว่าอยู่ที่ 45% ซึ่งอยู่ในเกณฑ์ปกติ
   - ตรวจสอบระบบดิสก์ด้วยคำสั่ง `iostat -xz 1` พบว่าค่า `%util` อยู่ที่ 98% และค่าเวลารอคอยเฉลี่ย `await` พุ่งสูงถึง 180 มิลลิวินาที
   - ข้อสรุป: ฮาร์ดดิสก์ I/O เกิดภาวะอิ่มตัว (Saturation) และกลายเป็นคอขวดหลักของระบบ

4. ค้นหาสาเหตุของการเปลี่ยนแปลง (Root Cause Identification):
   - ตรวจสอบบันทึกระบบปฏิบัติการผ่าน `dmesg -T` พบข้อความแจ้งเตือนว่าการ์ดควบคุมฮาร์ดแวร์เรด (Hardware RAID Controller) ได้ทำการปรับลดโหมดการทำงานจากการบันทึกผ่านหน่วยความจำแคช (Write-Back Caching) ไปเป็นโหมดเขียนลงแผ่นดิสก์โดยตรงทันที (Write-Through Mode)
   - สาเหตุเกิดจากหน่วยแบตเตอรี่สำรองของแคช (Battery Backup Unit: BBU) เสื่อมสภาพ เพื่อป้องกันข้อมูลสูญหายเมื่อไฟดับ คอนโทรลเลอร์จึงปิดแคช ส่งผลให้ความเร็วในการเขียนข้อมูลของระบบตกลงอย่างกะทันหันถึง 10 เท่า

5. บรรเทาผลกระทบก่อน แล้วจึงวางแผนแก้ไขที่ต้นเหตุ (Mitigate before Root-Cause Fix):
   - ในภาวะวิกฤตที่มีผู้ใช้งานหนาแน่น ห้ามทำการดับเครื่องเซิร์ฟเวอร์เพื่อเปลี่ยนอุปกรณ์ทันที
   - การบรรเทาปัญหา (Mitigation): ปรับแต่งระบบกระจายโหลดให้ส่งทราฟฟิกประเภทการอ่าน (Read Queries) ทั้งหมดไปยังเครื่องสำรอง (Read Replica) เพื่อลดภาระการเขียนอ่านที่ทับซ้อนบนเครื่องฐานข้อมูลหลัก
   - การแก้ไขถาวร (Remediation): วางแผนนัดหมายช่วงเวลาปิดปรับปรุงระบบนอกเวลาทำการ (Maintenance Window) เพื่อทำการเปลี่ยนโมดูลแบตเตอรี่สำรองของการ์ด RAID

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- เหตุผลทางวิศวกรรมของเคสแบตเตอรี่แคช RAID เสื่อมสภาพ:
  - ในเซิร์ฟเวอร์ระดับ Enterprise การ์ด RAID Controller จะมีหน่วยความจำแคชความเร็วสูงติดตั้งอยู่ ในสภาวะปกติ ระบบจะใช้โหมดการทำงานแบบ Write-Back ซึ่งหมายถึงเมื่อมีคำสั่งเขียนข้อมูลเข้ามา คอนโทรลเลอร์จะเขียนข้อมูลลงใน RAM แคชความเร็วสูงแล้วตอบกลับไปยังระบบปฏิบัติการทันทีว่า "เขียนเสร็จแล้ว" ทำให้ประสิทธิภาพการเขียนข้อมูลรวดเร็วมาก
  - กลไกป้องกันความเสี่ยง: การเก็บข้อมูลไว้ใน RAM แคชมีความเสี่ยง หากไฟฟ้าดับกะทันหัน ข้อมูลที่ค้างอยู่ในแคชจะสูญหายทันที ผู้ผลิตจึงออกแบบหน่วยแบตเตอรี่สำรอง (Battery Backup Unit: BBU) ไว้คอยจ่ายไฟเลี้ยงข้อมูลในแคชได้นาน 48–72 ชั่วโมงเมื่อไฟดับ
  - พฤติกรรมเมื่อแบตเตอรี่เสื่อม: เมื่อโมดูล BBU มีอายุการใช้งานนานจนแบตเตอรี่เสื่อมสภาพ คอนโทรลเลอร์จะตัดการทำงานเข้าสู่โหมดป้องกันความปลอดภัย (Failsafe) โดยปรับเปลี่ยนไปใช้โหมด Write-Through โดยอัตโนมัติ ในโหมดนี้ ทุกคำสั่งเขียนจะต้องรอให้ข้อมูลถูกบันทึกลงสู่จานแม่เหล็กของฮาร์ดดิสก์จริงเสียก่อนจึงจะตอบกลับว่าเขียนเสร็จ ความเร็วในการเขียนจึงตกลงถึง 10 เท่าในชั่วพริบตา
- หลักคิดในการกู้คืนระบบ: "บรรเทาก่อน แล้วค่อยแก้ราก"
  - วิศวกรที่ขาดประสบการณ์เมื่อพบว่าแบตเตอรี่เสื่อม มักต้องการดับเครื่องเซิร์ฟเวอร์เพื่อแกะเปลี่ยนแบตเตอรี่ทันที แต่ในสถานการณ์จริงที่ผู้ใช้กำลังแห่กันเข้ามาลงทะเบียน การดับระบบจะทำให้บริการล่ม 100% ทันที
  - หน้าที่ของ SRE คือต้องคิดหาวิธี "บรรเทาอาการ (Mitigation)" ณ เวลานั้นก่อน โดยวิเคราะห์ว่าคำสั่งค้นหาที่เป็นการอ่านข้อมูล (Read Traffic) คิดเป็นสัดส่วนกว่า 80% ของระบบ จึงควรย้ายทราฟฟิกส่วนนี้ไปประมวลผลบนเครื่อง Read Replica เพื่อปลดเปลื้องภาระของดิสก์บนเครื่องหลักให้เหลือเฉพาะงานเขียนที่จำเป็นเท่านั้น ทำให้ระบบสามารถประคองตัวเปิดให้บริการต่อไปได้ จากนั้นจึงค่อยวางแผนเปิดหน้าต่างซ่อมบำรุง (Maintenance Window) เพื่อเปลี่ยนแบตเตอรี่นอกเวลาทำการ

## ส่วนที่ 2: ทฤษฎีแถวคอยเบื้องต้น — ทำไมระบบถึงพังตอนที่ยังดู "ไม่เต็ม"

หนึ่งในความเข้าใจผิดที่พบบ่อยที่สุดในการบริหารจัดการระบบคอมพิวเตอร์คือ ความเชื่อที่ว่าตราบใดที่อัตราการใช้งาน (Utilization) ยังไม่ถึง 100% ระบบจะยังคงสามารถให้บริการได้ตามปกติ แต่ในความเป็นจริง ระบบมักจะล่มสลายหรือมีความหน่วงพุ่งสูงตั้งแต่ทรัพยากรแตะระดับ 80%

### 2.1 กฎของลิตเติลและความสัมพันธ์แบบไม่เป็นเส้นตรง (The Knee Curve)

ความสัมพันธ์ระหว่างอัตราการใช้งานระบบ (Utilization) กับเวลาตอบสนอง (Latency) ไม่ได้ดำเนินไปแบบเส้นตรง (Non-linear Relationship) แต่มีลักษณะเป็นเส้นโค้งที่หักเลี้ยวและพุ่งทะยานขึ้นอย่างรวดเร็ว (The Knee Curve)

#### กฎของลิตเติล (Little's Law)
ในทฤษฎีแถวคอยพื้นฐาน กฎของลิตเติลระบุความสัมพันธ์ของระบบในสภาวะเสถียรไว้ดังสมการ:

$$L = \lambda \times W$$

โดยที่:
- $L$ คือ จำนวนงานหรือคำขอเฉลี่ยที่ค้างสะสมอยู่ในระบบ (Queue Length / Concurrency)
- $\lambda$ (แลมบ์ดา) คือ อัตราการมาถึงของคำขอเฉลี่ยต่อหนึ่งหน่วยเวลา (Arrival Rate / Throughput)
- $W$ คือ เวลาเฉลี่ยที่คำขอแต่ละชิ้นใช้เวลาอยู่ในระบบตั้งแต่เข้าจนออก (Wait Time / Residence Time / Latency)

ตัวอย่างการประยุกต์ใช้:
หากมีคำขอส่งเข้ามายังระบบด้วยอัตรา $\lambda = 200$ ครั้งต่อวินาที และคำขอแต่ละรายการใช้เวลาประมวลผลเฉลี่ย $W = 0.25$ วินาที  
จำนวนคำขอที่ค้างสะสมและประมวลผลพร้อมกันอยู่ในระบบจะมีค่าเท่ากับ:

$$L = 200 \times 0.25 = 50 \text{ คำขอ}$$

#### พฤติกรรมจุดหักเลี้ยวที่ระดับการใช้งาน 80% (The Knee at ~80%)
เมื่อพิจารณาแบบจำลองแถวคอยแบบแถวเดี่ยวและผู้ให้บริการเดี่ยว (M/M/1 Queue) ความสัมพันธ์ระหว่างเวลาตอบสนองสัมพัทธ์ ($W$) กับอัตราการใช้งาน ($\rho$) มีความสัมพันธ์ผกผันดังนี้:

$$W \propto \frac{1}{1 - \rho}$$

- เมื่ออัตราการใช้งานอยู่ที่ 50% ($\rho = 0.50$): เวลาตอบสนองจะช้าเป็น $1 / (1 - 0.5) = 2$ เท่าของเวลาพื้นฐาน
- เมื่ออัตราการใช้งานอยู่ที่ 80% ($\rho = 0.80$): เวลาตอบสนองจะช้าเป็น $1 / (1 - 0.8) = 5$ เท่าของเวลาพื้นฐาน
- เมื่ออัตราการใช้งานขยับไปที่ 90% ($\rho = 0.90$): เวลาตอบสนองจะพุ่งทะยานเป็น $1 / (1 - 0.9) = 10$ เท่าของเวลาพื้นฐาน

ผลกระทบเชิงวิศวกรรม:
- หากระบบทำงานอยู่ที่ Utilization 50% แล้วมีปริมาณงานเพิ่มขึ้นอีก 10% (กลายเป็น 60%) ผู้ใช้งานแทบจะไม่รู้สึกถึงความแตกต่างของความเร็ว
- แต่หากระบบทำงานอยู่ที่ Utilization 80% แล้วมีปริมาณงานเพิ่มขึ้นอีกเพียง 10% (กลายเป็น 90%) เวลาตอบสนองจะกระโดดเพิ่มขึ้นเป็นเท่าตัวในทันที ส่งผลให้เกิดคิวงานคั่งค้างอย่างรวดเร็วและนำไปสู่การล่มสลายของระบบ

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- กราฟรูปทรงไม้ฮอกกี้ (Hockey-stick Curve) และสาเหตุที่ระบบพังโดยไม่มีสัญญาณเตือนล่วงหน้า:
  - ในช่วงโหลดการทำงาน 0% ถึง 60% กราฟความหน่วงของระบบจะมีความลาดเอียงต่ำมาก ระบบจะตอบสนองได้อย่างรวดเร็ว ทำให้ผู้ดูแลระบบเกิดความชะล่าใจ
  - เมื่อระบบเริ่มไต่ขึ้นมาที่ระดับ 70% ถึง 80% ผู้ดูแลระบบส่วนใหญ่มักรู้สึกว่า "ยังเหลือทรัพยากรว่างอยู่อีกตั้ง 20–30% คงไม่มีอะไรต้องกังวล" แต่ในความเป็นจริง จุด 80% คือจุดที่เรียกว่า "The Knee" (จุดหัวเข่าหักงอ)
  - หลังจากจุด 80% ขึ้นไป กราฟจะเปลี่ยนความชันเป็นเส้นแนวตั้งแบบเอ็กซ์โพเนนเชียล (Exponential) การเพิ่มโหลดเพียงเล็กน้อยจะทำให้คิวงานระเบิดตัวเพิ่มขึ้นในเวลาเพียงเสี้ยววินาที จนกระทั่งระบบเกิดอาการแฮงก์และค้างอย่างสมบูรณ์ก่อนที่ทีมวิศวกรจะมีเวลาเข้าแทรกแซง
  - ด้วยเหตุนี้ ในทางวิศวกรรม SRE จึงต้องกำหนดค่าขีดจำกัดแจ้งเตือน (Alert Threshold) ไว้ที่ 80% เสมอ เพื่อเป็นเส้นแบ่งความปลอดภัยที่ไม่ยอมให้ระบบก้าวข้ามไป

### 2.2 การคำนวณส่วนเผื่อความจุที่ใช้งานได้จริง (Headroom Calculation)

ในการออกแบบระบบให้มีความน่าเชื่อถือ วิศวกรต้องกำหนดขนาดความจุสำรอง (Headroom) อย่างเป็นวิทยาศาสตร์ โดยมีขั้นตอนการคำนวณที่เป็นมาตรฐาน 4 ขั้นตอน:

1. ตรวจวัดโหลดสูงสุดจริงที่เคยเกิดขึ้น (Measure Historical Peak Load):
   - เก็บข้อมูลโหลดสูงสุดรายวันย้อนหลัง 90 วัน โดยห้ามใช้ค่าเฉลี่ย (Do not use average) เพราะค่าเฉลี่ยจะกลบช่วงที่ทราฟฟิกพุ่งสูง (Spikes)  
   - สมมุติค่าพีคสูงสุดที่บันทึกได้คือ $1,200$ คำขอต่อวินาที

2. บวกอัตราการเติบโตของระบบตามที่คาดการณ์ (Add Expected Growth):
   - ประเมินการเติบโตของปริมาณผู้ใช้งาน เช่น เติบโต 15% ต่อภาคการศึกษา  
   - โหลดสูงสุดที่ต้องรองรับในอนาคต $= 1,200 \times (1 + 0.15) = 1,380$ คำขอต่อวินาที

3. เผื่อการสูญเสียโหนดประมวลผลหนึ่งโหนด (Design for N-1 Redundancy):
   - หากระบบประกอบด้วยเซิร์ฟเวอร์คลัสเตอร์จำนวน 3 เครื่อง ระบบจะต้องสามารถทำงานได้อย่างสมบูรณ์แม้จะมีเครื่องใดเครื่องหนึ่งพังเสียหายไป (โหนดเหลือ 2 เครื่อง)  
   - ดังนั้น ภาระงานทั้งหมด $1,380$ คำขอต่อวินาที ต้องถูกหารเฉลี่ยด้วยเซิร์ฟเวอร์ที่เหลือ 2 เครื่อง (ไม่ใช่หาร 3)  
   - พิกัดโหลดที่แต่ละเครื่องต้องรองรับได้ $= 1,380 \div 2 = 690$ คำขอต่อวินาทีต่อเครื่อง

4. ควบคุมอัตราการใช้งานไม่ให้เกินเพดาน 80% (Cap Utilization at 80% Ceiling):
   - เพื่อป้องกันไม่ให้โหนดที่เหลือทำงานเกินจุด Knee เมื่อเกิดเหตุขัดข้อง โหลด $690$ คำขอต่อวินาทีจะต้องคิดเป็นไม่เกิน 80% ของความจุสูงสุดของเครื่อง  
   - ความจุที่ต้องจัดเตรียมต่อเครื่อง $= 690 \div 0.80 = 863$ คำขอต่อวินาทีต่อเครื่อง

บทสรุปเชิงปฏิบัติการ:
หากทำการทดสอบสมรรถนะ (Benchmark) แล้วพบว่าเครื่องเซิร์ฟเวอร์หนึ่งเครื่องสามารถรองรับโหลดจริงได้สูงสุดเพียง 700 คำขอต่อวินาที แต่ผลการคำนวณตามหลักวิศวกรรมต้องการ 863 คำขอต่อวินาทีต่อเครื่อง ทีมวิศวกรต้องจัดหาเครื่องเซิร์ฟเวอร์มาเสริมในระบบทันที โดยไม่ต้องรอให้เกิดปัญหาคอขวดหรือให้ผู้ใช้ร้องเรียน

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- ความหมายและการเปรียบเทียบคำว่า Headroom:
  - คำว่า "Headroom" มีที่มาจากการออกแบบห้องโดยสารของรถยนต์และพื้นที่ในห้องเรียน ในห้องเรียนที่เพดานสูง 4 เมตร หากคนสูง 2 เมตรยืนอยู่ จะเหลือ Headroom ถึง 2 เมตร ทำให้รู้สึกโปร่ง โล่ง และหายใจสะดวก เปรียบได้กับรถตู้ที่มี Headroom กว้างขวาง ในขณะที่รถสปอร์ตถูกออกแบบให้หลังคาเตี้ยและเบาะนั่งแนบพื้นเพื่อเน้นความเร็ว ทำให้ Headroom เหลือน้อยมาก นั่งไม่ค่อยสบาย
  - ในระบบไอที การเผื่อ Headroom มากจนเกินไป (เช่น โครงสร้างพื้นฐานของคณะที่มีทรัพยากรเผื่อไว้มหาศาลเพื่อรองรับโปรเจกต์ของทุกวิชา) ก่อให้เกิดต้นทุนงบประมาณที่สูงเกินความจำเป็น แต่หากเผื่อ Headroom ไว้น้อยเกินไป ระบบจะเปราะบางและพร้อมจะล่มสลายเมื่อมีทราฟฟิกกระชาก
- กฎเหล็ก: ห้ามใช้ค่าเฉลี่ย (Average) ในการประเมินความจุระบบ:
  - การใช้ค่าเฉลี่ยเป็นข้อผิดพลาดที่ร้ายแรงที่สุดของวิศวกร เพราะค่าเฉลี่ยจะเกลี่ยทับกลืนช่วงเวลาที่เกิดทราฟฟิกพุ่งสูงสุด (Traffic Spikes) ทิ้งไป หากเราจัดสรรทรัพยากรตามค่าเฉลี่ย เมื่อถึงเวลาที่ผู้ใช้แห่กันเข้ามาใช้งานพร้อมกัน ระบบจะไม่มีความจุเพียงพอและล่มสลายทันที
- การนำไปปรับใช้ในการขอทรัพยากรสำหรับโครงงาน (Project Resource Sizing):
  - สำหรับนักศึกษาที่ต้องทำโครงงานจบ (Capstone Project) เวลาทำเรื่องขอโควตาทรัพยากรเครื่องเซิร์ฟเวอร์หรือสร้าง Virtual Machine จากทีม Infra ของคณะ ให้เขียนคำนวณตัวเลข Headroom อิงตามสมการ 4 ขั้นตอนนี้แนบไปด้วยเสมอ เพื่อแสดงให้เห็นอย่างมีหลักการทางวิศวกรรมว่าเหตุใดโครงงานของเราจึงต้องการซีพียูและหน่วยความจำตามตัวเลขดังกล่าว แทนที่จะเป็นการขอทรัพยากรแบบกะประมาณตามใจชอบ

## ส่วนที่ 3: โหมดความล้มเหลวของระบบกระจาย (Distributed Systems Failure Modes)

ในสถาปัตยกรรมระบบกระจาย ความล้มเหลวมักไม่ได้เกิดขึ้นพร้อมกันทั้งระบบตั้งแต่ต้น แต่จะเริ่มต้นจากจุดบริการจุดใดจุดหนึ่งที่ทำงานช้าลง แล้วลุกลามต่อเนื่องเป็นลูกโซ่จากชั้นล่างขึ้นสู่ชั้นบน

### 3.1 ความล้มเหลวแบบลูกโซ่ (Cascading Failure)

ปรากฏการณ์ที่ไม่มีองค์ประกอบใดพังทลายด้วยตัวเองตั้งแต่แรก แต่เส้นทางการให้บริการทั้งหมดกลับล่มสลายลง เกิดขึ้นตามลำดับดังนี้:

1. ชั้นล่างสุดเริ่มช้าลง (Downstream Slowdown):
   - ฐานข้อมูลทำงานช้าลงจากคำสั่งค้นหาที่ซับซ้อน ตัวระบบยังไม่ได้หยุดทำงานหรือส่งข้อผิดพลาด เพียงแต่เวลาตอบสนองเพิ่มขึ้นจาก 0.2 วินาทีเป็น 3 วินาที
2. ทรัพยากรในชั้นกลางเริ่มสะสมค้าง (Thread/Connection Exhaustion):
   - แต่ละคำขอที่ค้างรอการตอบสนองจากฐานข้อมูล จะยังคงยึดครองเธรด (Thread) และการเชื่อมต่อในพูลของ API เซิร์ฟเวอร์ไว้ ส่งผลให้เธรดพูลเต็ม คำขอใหม่ที่เข้ามาไม่สามารถจัดสรรทรัพยากรได้และต้องเข้าคิวรอ
3. ไคลเอนต์หมดเวลาและส่งคำขอซ้ำ (Client Timeout and Retry Storm):
   - ฝั่งผู้ใช้งานหรือระบบไคลเอนต์รอคอยคำตอบจนหมดเวลาตัดการเชื่อมต่อ (Timeout) จึงเริ่มส่งคำขอเดิมซ้ำเข้ามาใหม่ ในขณะที่คำขอเดิมยังคงประมวลผลค้างอยู่ในเซิร์ฟเวอร์ ส่งผลให้ภาระงานรวมทวีคูณขึ้นเป็น 2 เท่า และ 3 เท่า
4. ระบบล่มสลายทั้งเส้นทางและการวนลูปมรณะ (System Collapse and Death Spiral):
   - ชั้นเว็บเซิร์ฟเวอร์เกิดความอิ่มตัวอย่างสมบูรณ์ ระบบตรวจสอบสถานะสุขภาพ (Health Check) ไม่ผ่าน ทำให้ระบบจัดการคอนเทนเนอร์ (Orchestrator) สั่งรีสตาร์ตเครื่องหรือคอนเทนเนอร์อย่างต่อเนื่อง เมื่อโหนดใหม่บูตเสร็จจะถูกทราฟฟิกมหาศาลที่สะสมอยู่ถล่มซ้ำจนดับไปอีกครั้ง กลายเป็นการวนลูปตายซ้ำไม่รู้จบ

#### จุดและกลไกตัดวงจรความล้มเหลว (Circuit Breaking Points)
- การกำหนดค่า Timeout ให้สั้นกว่าขีดความอดทนของผู้เรียก
- การหน่วงเวลาส่งซ้ำแบบเพิ่มค่าทวีคูณร่วมกับการสุ่มเวลา (Exponential Backoff with Jitter)
- การจำกัดเพดานงบประมาณการส่งซ้ำ (Retry Budget)
- การติดตั้งกลไกตัดวงจรไฟฟ้าเสมือน (Circuit Breaker) เพื่อปฏิเสธคำขอทันทีเมื่อระบบปลายทางไม่พร้อม
- การสลัดทิ้งภาระงานที่ไม่จำเป็นที่ขอบนอกของระบบ (Load Shedding at system boundaries)

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- ภาพลวงตาของความหน่วงเวลาและกลไก Death Spiral:
  - เวลาตอบสนองที่เพิ่มขึ้นจาก 0.2 วินาที เป็น 3.0 วินาที หากมองในมุมมองมนุษย์คนเดียว เราอาจรู้สึกว่ารอคอยเพียง 3 วินาทีไม่นานเท่าใดนัก แต่เมื่อมีผู้ใช้งานพร้อมกันหลายพันหรือหลายหมื่นคำขอ การที่แต่ละคำขอยึดครองเธรดและหน่วยความจำนานขึ้น 15 เท่า จะทำให้ทรัพยากรการประมวลผลของเซิร์ฟเวอร์หมดลงในทันที
  - เมื่อคอนเทนเนอร์ไม่สามารถตอบคำขอตรวจสอบสุขภาพ (Health Check) ระบบ Kubernetes หรือ Docker Swarm จะสรุปว่าคอนเทนเนอร์พังแล้วสั่งรีสตาร์ตใหม่ แต่เมื่อคอนเทนเนอร์บูตกลับขึ้นมา ก็จะถูกคำขอจำนวนมหาศาลที่สะสมค้างอยู่ถล่มเข้าใส่ในเสี้ยววินาที ทำให้แครชและดับซ้ำอีก กลายเป็นวงจรความตายไม่รู้จบ (Death Spiral)
  - กลไก Circuit Breaker: เปรียบเหมือนการติดตั้งเบรกเกอร์ตัดไฟในบ้าน เมื่อตรวจพบว่าเซอร์วิสด้านหลังเริ่มล้มเหลว Circuit Breaker จะ "ตัดการเชื่อมต่อโดยเด็ดขาดแบบไม่ประนีประนอม" โดยปฏิเสธคำขอใหม่ทันที เพื่อให้เซอร์วิสด้านหลังมีเวลาเคลียร์คิวและฟื้นคืนชีพกลับมา

### 3.2 งบประมาณเวลา (Timeout Budget) และการส่งซ้ำอย่างปลอดภัย

การตั้งค่าเวลาและการส่งซ้ำคำขอจำเป็นต้องมีการคำนวณและวางแผนล่วงหน้า เพื่อไม่ให้กลายเป็นตัวการเร่งให้ระบบพังทลายเร็วยิ่งขึ้น

#### 1. งบประมาณเวลาต้องจัดสรรจากบนลงล่าง (Top-Down Timeout Budgeting)
- หลักการ: เวลารอคอยของบริการชั้นล่างสุดจะต้องสั้นกว่าเวลารอคอยของบริการชั้นบนเสมอ
- ตัวอย่างการกำหนด:
  - ผู้ใช้งานยอมรอคอยสูงสุด: 3.0 วินาที
  - ชั้นเว็บเซิร์ฟเวอร์ (Web Tier) ตั้ง Timeout: 2.5 วินาที
  - ชั้นแอปพลิเคชัน API (API Tier) ตั้ง Timeout: 2.0 วินาที
  - ชั้นฐานข้อมูล (Database Tier) ตั้ง Timeout: 1.5 วินาที
- กฎเหล็ก: ห้ามมิให้ชั้นล่างตั้ง Timeout นานกว่าชั้นบนเป็นอันขาด เพราะหากชั้นบนตัดการเชื่อมต่อไปแล้ว แต่ชั้นล่างยังคงประมวลผลต่อ จะทำให้ระบบสูญเสียทรัพยากรซีพียูและหน่วยความจำไปกับการทำงานที่ไม่มีผู้รอรับผลลัพธ์แล้ว (Wasted Work)

#### 2. การส่งซ้ำต้องมีงบประมาณจำกัด (Retry Budget)
- ในสถาปัตยกรรมระบบกระจาย ควรกำหนดเพดานงบประมาณให้การส่งซ้ำ (Retry) เกิดขึ้นได้ไม่เกิน 10% ของปริมาณคำขอทั้งหมด
- หากอัตราคำขอผิดพลาดเกินกว่า 10% นั่นเป็นสัญญาณบ่งชี้ว่าระบบปลายทางกำลังประสบปัญหาล่มสลายจริง การดึงดันส่งซ้ำคำขอต่อไปจะก่อให้เกิดสภาวะ "พายุการส่งซ้ำ (Retry Storm)" ที่ทำลายระบบให้พังถาวร

#### 3. การหน่วงเวลาส่งซ้ำต้องผสมค่าสุ่ม (Exponential Backoff with Jitter)
- หากไคลเอนต์ทั้งหมดที่พบข้อผิดพลาดพร้อมกันตั้งเวลารอ 1 วินาทีเท่ากันอย่างคงที่ เมื่อครบเวลา คำขอทั้งหมดจะยิงกลับเข้ามายังเซิร์ฟเวอร์พร้อมกันในจังหวะเดียวกัน ก่อให้เกิดคลื่นโหลดกระแทกซ้ำ หรือปรากฏการณ์ฝูงชนวิ่งกรู (Thundering Herd Problem)
- วิธีแก้ไข: ต้องนำฟังก์ชันคณิตศาสตร์ Exponential Backoff มาคำนวณระยะเวลารอที่เพิ่มขึ้นเป็นเท่าตัวในแต่ละรอบ และบวกค่าสุ่มเวลา (Jitter) เพื่อกระจายจังหวะเวลาของคำขอให้กระจายตัว ไม่รวมกลุ่มเป็นยอดคลื่น

#### 4. ข้อห้ามการส่งซ้ำสำหรับคำขอที่ไม่ใช่ไอเดมโพเทนต์ (Non-Idempotent Operations)
- คำขอที่มีผลกระทบเปลี่ยนแปลงสถานะของระบบ เช่น คำสั่งตัดยอดเงินในบัญชี หรือการกดยืนยันลงทะเบียนวิชา ห้ามทำการ Retry โดยตรงเด็ดขาด
- หากจำเป็นต้องส่งซ้ำเพื่อความน่าเชื่อถือ จำเป็นต้องส่งรหัสเอกลักษณ์ประจำคำขอ (Idempotency Key) แนบไปด้วยเสมอ เพื่อให้เซิร์ฟเวอร์ปลายทางตรวจสอบได้ว่าคำขอนี้เคยได้รับการประมวลผลไปแล้วหรือไม่ เพื่อป้องกันการตัดเงินหรือลงทะเบียนซ้ำซ้อน

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- มายาคติเรื่องความน่าเชื่อถือ 100% (100% Reliability Myth):
  - ในโลกความเป็นจริงของงานวิศวกรรม SRE ความพร้อมใช้งาน 100% โดยไม่มีข้อผิดพลาดเลยเป็นสิ่งที่เป็นไปไม่ได้ หากระบบใดไม่เคยมี Error เกิดขึ้นเลย ย่อมแสดงว่าไม่มีผู้ใช้งานอยู่ในระบบนั้น หากระบบไม่มี Error และทำงานได้สมบูรณ์แบบตลอดเวลา อาชีพวิศวกร SRE ก็คงไม่มีความจำเป็น
  - ดังนั้น เป้าหมายของการออกแบบ Timeout Budget, Retry Budget และ Jitter จึงไม่ใช่การกำจัดความล้มเหลวให้เป็นศูนย์ แต่เป็นการควบคุมความเสี่ยงไม่ให้ข้อผิดพลาดเล็กน้อยลุกลามกลายเป็นหายนะของทั้งระบบ
- ประสบการณ์ของผู้ใช้กับคำสั่งที่ไม่เป็น Idempotent:
  - ลองจินตนาการถึงความรู้สึกของผู้ใช้เวลาสั่งซื้อสินค้าออนไลน์หรือกดตัดบัตรเครดิต แล้วหน้าจอขึ้นสัญลักษณ์หมุนค้างโดยไม่ยอมเปลี่ยนหน้า ผู้ใช้จะเกิดความกังวลใจเป็นอย่างมากว่าเงินถูกตัดไปแล้วหรือไม่ และไม่กล้าที่จะกดยืนยันซ้ำเพราะกลัวว่าจะถูกหักเงินเป็นสองเท่า
  - หากระบบไม่ได้ออกแบบให้รองรับ Idempotency Key แล้วอนุญาตให้เบราว์เซอร์หรือแอปพลิเคชันทำการ Retry คำขอนั้นซ้ำ ผลลัพธ์คือเงินของผู้ใช้จะถูกตัดซ้ำซ้อน ซึ่งถือเป็นความผิดพลาดร้ายแรงของระบบธุรกรรม ดังนั้น สำหรับคำขอที่มีความสำคัญสูง ต้องมีการจัดการด้วย Idempotency Key เสมอ

## ส่วนที่ 4: การมองตู้แร็กในฐานะระบบกระจายทางกายภาพ (Rack as a Distributed System)

แนวคิดทางวิศวกรรมระบบกระจายไม่ได้จำกัดอยู่เพียงซอฟต์แวร์ แต่สามารถนำมาใช้อธิบายและวิเคราะห์โครงสร้างทางกายภาพของตู้แร็ก (Server Rack) ในศูนย์ข้อมูลได้อย่างสมบูรณ์

| มิติเชิงระบบกระจาย | การสะท้อนในโลกกายภาพของตู้แร็กเซิร์ฟเวอร์ |
|---|---|
| จุดล้มเหลวเดี่ยว (Single Point of Failure: SPOF) | เซิร์ฟเวอร์ระดับองค์กรมีพาวเวอร์ซัพพลายคู่ (Dual PSU) เพื่อความซ้ำซ้อน แต่ช่างกลับเสียบสายไฟทั้งสองเส้นเข้าสู่รางปลั๊กไฟ (PDU) รางเดียวกัน ซึ่งเป็น "ความซ้ำซ้อนปลอม (Fake Redundancy)" หากเบรกเกอร์ของ PDU รางนั้นตัด เซิร์ฟเวอร์จะดับทันที เช่นเดียวกับบริการคู่ที่รันอยู่บนเครื่องโฮสต์เดียวกัน |
| ความล้มเหลวแบบลูกโซ่ (Cascading Failure) | การถอดหรือปิดสวิตช์เครือข่ายหลัก (Top-of-Rack Switch) เพียงตัวเดียวผิดจังหวะ จะส่งผลให้อุปกรณ์และเซิร์ฟเวอร์ทั้งหมดที่เชื่อมต่อผ่านสวิตช์ตัวนั้นขาดการติดต่อและล่มสลายไปพร้อมกันทั้งหมด เหมือนฐานข้อมูลช้าแล้วฉุดให้ทุกเซอร์วิสด้านบนพังตาม |
| ความอิ่มตัวของระบบ (Saturation) | รางปลั๊กไฟ PDU ที่มีโหลดการใช้กระแสไฟฟ้าอยู่ที่ 85% แม้จะยังจ่ายไฟได้ตามปกติ แต่จะไม่เหลือพื้นที่รองรับ "กระแสไฟกระชากขณะเริ่มต้นทำงาน (Inrush Current)" หากเซิร์ฟเวอร์หลายเครื่องเริ่มทำงานพร้อมกัน จะทำให้เบรกเกอร์ทริปตัดไฟทั้งตู้แร็กทันที |
| ขอบเขตความเสียหาย (Blast Radius) | ก่อนที่จะทำการถอดหรือปลดสายอุปกรณ์ใดๆ วิศวกรต้องตอบให้ได้ว่ามีระบบหรือบริการใดดับตาม และผู้ใช้งานกลุ่มใดจะได้รับผลกระทบ ซึ่งต้องอาศัยแผนผังความขึ้นต่อกัน (Dependency Map) ที่จัดทำไว้ |
| แผนการย้อนกลับคืนสภาพเดิม (Rollback Plan) | การถ่ายภาพบันทึกสภาพเดิมก่อนเริ่มงาน และการติดป้ายระบุสายสัญญาณทั้งสองฝั่งอย่างชัดเจน คือแผนการ Rollback ในโลกกายภาพ หากปราศจากสิ่งเหล่านี้ จะไม่สามารถประกอบอุปกรณ์กลับคืนสู่สภาพเดิมที่ทำงานได้ |

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- กายภาพและซอฟต์แวร์คือทฤษฎีเดียวกัน:
  - ความซ้ำซ้อนปลอม (Fake Redundancy): เซิร์ฟเวอร์ระดับ Enterprise ถูกสร้างให้มี Power Supply Unit (PSU) 2 ตัว เพื่อรองรับกรณีที่แหล่งจ่ายไฟด้านหนึ่งขาดหาย แต่บ่อยครั้งที่เจ้าหน้าที่หน้างานเลือกเสียบสายไฟทั้งสองเส้นเข้ากับรางไฟ (Power Distribution Unit: PDU) รางเดียวกันเพราะความสะดวกหรือสายไฟยาวไม่พอ หากเบรกเกอร์ของ PDU รางนั้นตัดไฟ เซิร์ฟเวอร์จะดับสนิททันที การกระทำเช่นนี้ทำให้ความซ้ำซ้อนที่มีกลายเป็นภาพลวงตา
  - ปัญหากระแสไฟกระชาก (Inrush Current) และข้อจำกัดด้านความร้อน: ภายในศูนย์ข้อมูล การติดตั้งอุปกรณ์ไม่ได้พิจารณาแค่ว่ามีช่องว่างในตู้แร็ก (Rack Units: U) เหลือหรือไม่ แต่ต้องคำนวณการใช้ไฟฟ้าและความร้อนด้วย หากตู้แร็กมีการติดตั้งเซิร์ฟเวอร์ที่ใส่การ์ดจอประมวลผล (GPU) หลายใบ แม้ตู้จะเหลือพื้นที่ว่าง แต่หากคำนวณแล้วว่าค่าไฟเกินพิกัดที่ PDU จ่ายได้ หรือปล่อยความร้อนเกินกว่าที่ระบบปรับอากาศของห้องจะระบายทัน ผู้ดูแลศูนย์ข้อมูลมีอำนาจสั่งปิดตู้หรือไม่อนุญาตให้นำเข้าตามมาตรฐาน ISO ทันที
  - แผนการย้อนกลับ (Rollback) ในโลกจริง: ก่อนที่จะแตะต้อง ถอด หรือขยับอุปกรณ์ใดๆ การถ่ายภาพมุมกว้างและภาพระยะใกล้ของเส้นทางการเดินสาย และการทำป้ายกำกับ (Labels) หัวท้ายสายทุกเส้น คือสิ่งเดียวที่รับประกันว่าเมื่อเกิดเหตุฉุกเฉิน เราจะสามารถประกอบอุปกรณ์กลับคืนสภาพเดิมได้อย่างถูกต้อง

### 5.2 การตรวจความพร้อมก่อนเข้าพื้นที่ (เวลา 11:45 น.)

กฎเหล็ก: หากขาดคุณสมบัติหรือเอกสารข้อใดข้อหนึ่ง จะถูกตัดสิทธิ์ไม่ให้เข้าพื้นที่โดยเด็ดขาด

#### 1. เอกสารที่ต้องจัดเตรียมครบถ้วน
- ใบขออนุมัติเข้าพื้นที่ (AR-01) ที่ผ่านการลงนามอนุมัติแล้ว พร้อมรายชื่อสมาชิกครบทุกคนในกลุ่ม
- แบบฟอร์มทะเบียนครุภัณฑ์ (INV-01) ฉบับพิมพ์ลงกระดาษ อย่างน้อย 3 ชุดต่อกลุ่ม
- แบบฟอร์มควบคุมสื่อบันทึกข้อมูล (MED-01) สำหรับอุปกรณ์ที่มีชิ้นส่วนดิสก์บันทึกข้อมูล
- แผนผังความขึ้นต่อกันของระบบ (Dependency Map) ฉบับปรับปรุงล่าสุด
- บัตรประจำตัวนักศึกษาของสมาชิกทุกคน เพื่อใช้แสดงตนขณะลงทะเบียนเข้าพื้นที่

#### 2. เครื่องมือและอุปกรณ์ประจำกลุ่ม
- ป้ายสติกเกอร์สำหรับระบุสาย และปากกาเคมีหมึกกันน้ำ
- ตลับเมตรวัดระยะ และไฟฉายส่องสว่าง
- กล้องถ่ายภาพหรือโทรศัพท์มือถือที่ผ่านการขออนุญาตบันทึกภาพตามแบบฟอร์ม PH-01
- ถุงมือผ้าสำหรับป้องกันอันตรายจากขอบโลหะคม (มีถุงมือสำรอง ณ จุดลงชื่อ)
- กระดานรองเขียนแบบมีคลิปหนีบ สำหรับใช้กรอกแบบฟอร์มขณะยืนปฏิบัติงาน

#### 3. องค์ความรู้และบทบาทหน้าที่ที่ต้องกำหนดก่อนเข้าพื้นที่
- การระบุบทบาทหน้าที่ชัดเจนในกลุ่ม:
  - หัวหน้าผู้ควบคุมการเปลี่ยนแปลง (Change Owner)
  - หัวหน้ารับผิดชอบงานทะเบียนพัสดุ (Inventory Lead)
  - เจ้าหน้าที่ควบคุมความปลอดภัย (Safety Officer)
  - ผู้บันทึกและถ่ายภาพหลักฐาน (Scribe)
- ลำดับขั้นตอนการถอดอุปกรณ์ตามแผนผัง Dependency Map
- การจดจำตำแหน่งของปุ่มหยุดทำงานฉุกเฉิน (Emergency Power Off: EPO) และเส้นทางหนีไฟ
- กฎความปลอดภัย: ห้ามถอดหรือปลดสายสัญญาณใดๆ ก่อนได้รับสัญญาณสั่งการ
- กฎการยศาสตร์: อุปกรณ์ที่มีน้ำหนักเกิน 20 กิโลกรัม ต้องใช้คนยกอย่างน้อยสองคนเสมอ

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- มาตรฐานความปลอดภัยตาม ISO/IEC 27001 (A.7.4) และหลักการยศาสตร์ (Ergonomics):
  - กฎการยกของหนัก: อุปกรณ์เซิร์ฟเวอร์ที่มีน้ำหนักเกิน 20 กิโลกรัม ต้องใช้คนยกอย่างน้อย 2 คนเสมอ แม้นักศึกษาจะมั่นใจในสมรรถภาพทางกายของตนเอง แต่มาตรฐานความปลอดภัยถูกกำหนดขึ้นเพื่อป้องกันการบาดเจ็บของกล้ามเนื้อกระดูกสันหลังในระยะยาว
  - กฎการเคลื่อนย้ายระยะทางเกิน 5 เมตร: ห้ามใช้คนเดินยกอุปกรณ์ระยะไกล เช่น ยกจากชั้น 8 ขึ้นลิฟต์มายังชั้น 10 การยกด้วยคนอนุญาตเฉพาะการยกจากตู้ขึ้นวางบนรถเข็นเท่านั้น หากเคลื่อนย้ายเกินกว่า 5 เมตร ต้องใช้รถเข็นในการลำเลียงเสมอ
  - อันตรายจากขอบคม: รางเลื่อนและขอบตู้แร็กที่เป็นโลหะมีความคมมาก สมาชิกทุกคนที่สัมผัสอุปกรณ์ต้องสวมถุงมือผ้าป้องกันการบาดเจ็บทุกครั้ง
- อำนาจหน้าที่ของ Safety Officer:
  - สมาชิกที่ได้รับมอบหมายให้ทำหน้าที่ Safety Officer มี "อำนาจสั่งหยุดงานทันที (Stop-Work Authority)" หากตรวจพบสภาพแวดล้อมที่ไม่ปลอดภัย เช่น มีสายไฟหรือสิ่งของขวางเส้นทางหนีไฟ หรือพบคราบน้ำรั่วซึมบนพื้น
- ข้อกำหนดการบันทึกภาพตามแบบฟอร์ม PH-01:
  - โทรศัพท์หรือกล้องที่ใช้ถ่ายภาพต้องระบุรายชื่อและได้รับอนุญาตล่วงหน้า ห้ามถ่ายภาพเซลฟี่ส่วนตัว ห้ามถ่ายหน้าจอที่อาจแสดงรหัสผ่านหรือข้อมูลการเข้าถึง (Credentials) และห้ามถ่ายภาพอุปกรณ์หรือตู้แร็กของหน่วยงานอื่นที่ติดตั้งอยู่ในห้องเด็ดขาด

### 5.3 ลำดับขั้นตอนการทำงานภาคสนาม (Work Breakdown Structure)

เงื่อนไขบังคับ: แต่ละขั้นตอนต้องได้รับการตรวจรับและลงนามรับรองให้เสร็จสิ้นสมบูรณ์ จึงจะสามารถเริ่มขั้นตอนถัดไปได้

```
[13:00] ตรวจสอบสิทธิ์เข้าพื้นที่ (AR-01, LOG-01, นับเครื่องมือเข้า)
   ↓
[13:20] บรีฟความปลอดภัยหน้างาน (กฎการยกของ, ทางออกฉุกเฉิน, อำนาจสั่งหยุดงาน)
   ↓
[13:40] ถ่ายภาพบันทึกสภาพเดิม (ด้านหน้า, ด้านหลัง, เส้นทางสายสัญญาณทุกเส้น)
   ↓
[14:00] ติดป้ายระบุสายสัญญาณ (ระบุสองปลายสาย) และหมายเลขประจำอุปกรณ์ทุกชิ้น
   ↓
[14:30] ถอดอุปกรณ์ออกจากตู้แร็ก (ชิ้นที่หนักเกิน 20 กก. ต้องใช้คนยกสองคน)
   ↓
[15:00] นำอุปกรณ์เข้าสถานีทำรายการครุภัณฑ์ (บันทึก Serial, ตำแหน่ง U, สภาพ ลง INV-01 ทันที)
   ↓
[15:40] จัดกลุ่มปลายทาง (ติดป้ายสี), ตรวจนับเครื่องมือออกครบถ้วน และปิดบันทึก LOG-01
```

กฎด่านตรวจคนเข้าเมือง (Border Control Rule):
อุปกรณ์ใดที่ยังไม่มีบรรทัดข้อมูลระบุในแบบฟอร์ม INV-01 อย่างครบถ้วน ห้ามเคลื่อนย้ายออกจากห้องศูนย์ข้อมูลโดยเด็ดขาด

### 5.4 สายพานสถานีทำรายการครุภัณฑ์ (Inventory Assembly Line)

การดำเนินงานต้องจัดเป็นระบบสายพานแบ่งหน้าที่เฉพาะด้าน ไม่ใช่ต่างคนต่างจด เพื่อป้องกันความผิดพลาดและการสูญหาย

- สถานีที่ 1 — การรับมอบอุปกรณ์ (Intake):
  - รับชิ้นส่วนอุปกรณ์จากทีมรื้อถอน ตรวจสอบว่ามีป้ายหมายเลขระบุติดมาแล้วหรือไม่ หากไม่มีป้าย ให้ส่งกลับไปให้ทีมรื้อถอนแก้ไขทันที
- สถานีที่ 2 — การอ่านและจดบันทึกข้อมูล (Identification & Logging):
  - ผู้ตรวจอ่านจะทำการอ่านหมายเลขเครื่อง (Serial Number) และหมายเลขรหัสครุภัณฑ์ออกเสียงอย่างชัดเจน
  - ผู้บันทึกจะทวนเสียงซ้ำและกรอกข้อมูลลงในแบบฟอร์ม INV-01 จากนั้นอ่านทวนข้อมูลกลับเพื่อยืนยันความถูกต้องแบบสองทาง (Readback Verification)
- สถานีที่ 3 — การบันทึกภาพถ่ายหลักฐาน (Photographic Evidence):
  - ถ่ายภาพสภาพความสมบูรณ์ของตัวเครื่อง ป้ายหมายเลข และป้ายรหัสครุภัณฑ์ อย่างน้อย 1 ภาพต่อชิ้นงาน
  - ตั้งชื่อไฟล์ภาพให้ตรงกับหมายเลขป้ายกำกับของอุปกรณ์นั้นๆ
- สถานีที่ 4 — การคัดแยกกลุ่มปลายทาง (Disposition & Sorting):
  - ติดป้ายสติกเกอร์สีเพื่อกำหนดสถานะปลายทางของอุปกรณ์:
    - ป้ายสีเขียว: สำหรับอุปกรณ์ที่คัดเลือกไว้เพื่อนำไปใช้งานต่อในห้องปฏิบัติการ
    - ป้ายสีน้ำเงิน: สำหรับอุปกรณ์ที่ต้องส่งคืนกองพัสดุและคลังกลาง
    - ป้ายสีแดง: สำหรับอุปกรณ์ชำรุดเสียหายที่ต้องทำลายหรือปลดระวาง
  - เคลื่อนย้ายอุปกรณ์ไปวางแยกตามพื้นที่โซนสีที่กำหนดไว้

กฎพิเศษสำหรับอุปกรณ์ที่มีดิสก์บรรจุอยู่:
อุปกรณ์ที่มีฮาร์ดดิสก์จะต้องผ่านการบันทึกข้อมูลที่สถานีที่ 2 จำนวนสองรอบ:
- รอบที่ 1: บันทึกข้อมูลตัวเครื่องเซิร์ฟเวอร์ลงในแบบฟอร์ม INV-01
- รอบที่ 2: ถอดถาดดิสก์ออกมาบันทึกรายละเอียดของดิสก์แต่ละก้อน (Serial, ยี่ห้อ, ขนาดความจุ) ลงในแบบฟอร์ม MED-01 อย่างละเอียด

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- ประสิทธิภาพของระบบสายพาน (Assembly Line Concept):
  - การแบ่งทีมงานออกเป็นสถานีย่อยทำให้การทำงานรวดเร็วและลดความสับสน หากปล่อยให้ต่างคนต่างทำจะเกิดความโกลาหลและอุปกรณ์สูญหาย การมีผู้ตรวจอ่านออกเสียงและผู้จดบันทึกทวนข้อมูลซ้ำ (Readback Verification) เป็นมาตรฐานสากลที่ใช้ในศูนย์ข้อมูลและห้องผ่าตัดเพื่อป้องกันข้อผิดพลาดจากการสื่อสาร
  - การจัดการอุปกรณ์จัดเก็บข้อมูล (Storage): ตัว SAN Switch หรือ SAN Storage เดิมที่ค่อนข้างเก่าและซับซ้อน จะถูกส่งคืนพัสดุของคณะ ส่วนฮาร์ดดิสก์ทั้งหมดจะต้องถูกถอดแยกเก็บลงในกล่องนิรภัยที่ปิดล็อก เพื่อเตรียมเข้าสู่กระบวนการล้างทำลายข้อมูล (Media Sanitization ตามมาตรฐาน NIST SP 800-88) ในสัปดาห์ถัดไป

### 5.5 กฎระเบียบการบันทึกข้อมูลเอกสารหน้างาน

ข้อผิดพลาดที่พบบ่อยและข้อปฏิบัติตามมาตรฐานการควบคุม ISO/IEC 27001 Annex A.5.9:

#### ข้อปฏิบัติที่ต้องกระทำ (Mandatory Practices)
- ต้องจดบันทึกข้อมูลทันทีที่มีการถอดชิ้นส่วนอุปกรณ์ ห้ามจดจำไว้ในใจแล้วมาจดบันทึกย้อนหลัง
- ยึดหลักการ: หนึ่งชิ้นงานต่อหนึ่งบรรทัดข้อมูล แม้จะเป็นเครื่องเซิร์ฟเวอร์รุ่นเดียวกันสิบเครื่อง ก็ต้องบันทึกแยกเป็นสิบบรรทัด
- กรณีอ่านหมายเลข Serial Number ไม่ชัดเจน ให้ถ่ายภาพระยะใกล้ (Macro) แนบไว้ แล้วระบุในช่องว่า "อ่านไม่ออก" ห้ามเดาตัวเลขเป็นอันขาด
- หากช่องข้อมูลใดไม่มีค่าให้กรอก ให้ขีดเครื่องหมายขีด (-) ปิดช่อง ห้ามเว้นว่างไว้เด็ดขาด
- ผู้บันทึกข้อมูล (Recorder) และผู้ตรวจทานความถูกต้อง (Reviewer) จะต้องเป็นคนละคนกันเสมอ

#### ข้อห้ามเด็ดขาด (Strict Prohibitions)
- ห้ามใช้ดินสอในการกรอกเอกสาร ต้องใช้ปากกาหมึกแห้งหรือปากกาลูกลื่นเท่านั้น
- ห้ามลบข้อความด้วยน้ำยาลบคำผิดหรือเทปลบคำผิด หากเขียนผิด ให้ใช้ปากกาขีดฆ่าด้วยเส้นตรงหนึ่งเส้น แล้วลงลายมือชื่อกำกับข้างรอยขีดฆ่า
- ห้ามเคลื่อนย้ายอุปกรณ์ออกจากห้องก่อนที่จะกรอกข้อมูลในบรรทัดนั้นเสร็จสิ้นอย่างสมบูรณ์
- ห้ามถ่ายภาพหน้าจอแสดงผลที่มีข้อมูลรับรองตัวตน (Credentials / Passwords) ปรากฏอยู่
- ห้ามถอดดิสก์ออกจากเครื่องโดยไม่มีการจดบันทึกรายละเอียดลงในแบบฟอร์ม MED-01

เหตุผลของความเข้มงวด:
เอกสารชุดนี้เป็นเอกสารหลักฐานที่มีผลผูกพันทางกฎหมายในการตรวจสอบและส่งมอบทรัพย์สินของทางราชการตามข้อควบคุม A.5.9 หากตัวเลขในเอกสารไม่ตรงกับสภาพจริง ผู้ที่ลงลายมือชื่อรับรองจะต้องเป็นผู้รับผิดชอบทางกฎหมายและวินัย การขีดฆ่าแล้วเซ็นชื่อกำกับจึงเป็นหลักปฏิบัติสากลของเอกสารเชิงพยานหลักฐาน (Audit Trail)

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- ความสำคัญของร่องรอยการตรวจสอบ (Audit Trail) และมาตรฐานเอกสารทางราชการ:
  - ในมุมมองของนักศึกษา อาจรู้สึกว่าการห้ามใช้ดินสอหรือการห้ามใช้น้ำยาลบคำผิดเป็นเรื่องจุกจิก แต่ในความเป็นจริงของระบบราชการและมาตรฐาน ISO/IEC 27001 เอกสารทะเบียนทรัพย์สินถือเป็นเอกสารเชิงพยานหลักฐานทางกฎหมาย (Legal Audit Trail)
  - หากเอกสารมีการใช้ดินสอหรือน้ำยาลบคำผิด เอกสารนั้นจะถูกตัดสิทธิ์ความน่าเชื่อถือทันที เพราะเปิดช่องให้เกิดการทุจริตหรือแก้ไขตัวเลขย้อนหลังได้
  - การขีดฆ่าด้วยเส้นตรงเส้นเดียวแล้วลงลายมือชื่อกำกับ เป็นวิธีปฏิบัติสากลที่ยืนยันว่าข้อมูลเดิมถูกแก้ไขโดยใคร และแสดงให้ผู้ตรวจประเมินเห็นถึงความโปร่งใสของกระบวนการทำงาน ผู้ใดเป็นผู้ลงลายมือชื่อในเอกสาร ผู้นั้นต้องรับผิดชอบต่อความถูกต้องของทรัพย์สินจริงทุกชิ้น

### 5.6 เกณฑ์การตรวจรับความสำเร็จของงาน (Definition of Done: DoD)

การตรวจรับความสำเร็จต้องดำเนินการให้เสร็จสิ้นหน้าห้องศูนย์ข้อมูลก่อนออกจากพื้นที่ โดยมีรายการตรวจสอบดังนี้:

| รายการตรวจสอบความสำเร็จ (Checklist Item) | ผู้รับผิดชอบในการตรวจรับ |
|---|---|
| ทุกอุปกรณ์ที่ถูกถอดออกมามีบรรทัดข้อมูลใน INV-01 ที่กรอกครบถ้วนทุกช่อง | หัวหน้ารับผิดชอบงานทะเบียน (Inventory Lead) |
| ดิสก์ทุกชิ้นที่ถอดแยกมีบรรทัดข้อมูลใน MED-01 และถูกจัดเก็บในกล่องนิรภัยที่ปิดล็อก | เจ้าหน้าที่ควบคุมความปลอดภัย (Safety Officer) |
| อุปกรณ์ทั้งหมดได้รับการติดป้ายสีคัดแยกประเภทครบทั้งสามสี และวางแยกโซนถูกต้อง | หัวหน้ารับผิดชอบงานทะเบียน (Inventory Lead) |
| ภาพถ่ายหลักฐานมีความครบถ้วนทุกชิ้น และตั้งชื่อไฟล์ภาพตรงกับหมายเลขป้ายกำกับ | ผู้บันทึกและถ่ายภาพหลักฐาน (Scribe) |
| เครื่องมือและอุปกรณ์ที่นำเข้าไป ได้รับการตรวจสอบนับยอดนำออกครบตามใบ AR-01 | เจ้าหน้าที่ควบคุมความปลอดภัย (Safety Officer) |
| แบบฟอร์มบันทึกการเข้าออก LOG-01 มีการลงลายมือชื่อออกครบทุกคน และส่งมอบให้ผู้ควบคุมพื้นที่ | หัวหน้าผู้ควบคุมการเปลี่ยนแปลง (Change Owner) |

#### คำอธิบายเสริมและบริบทจากผู้สอน (Instructor Insights)
- การตรวจรับก่อนออกจากพื้นที่:

## สรุปสามประโยคสำคัญประจำบทเรียน (Key Takeaways)

1. Utilization บอกเพียงว่าเราใช้ทรัพยากรไปเท่าไร แต่ Saturation คือสัญญาณเตือนล่วงหน้าว่าระบบกำลังจะพังทลาย — ในงานวิศวกรรมความน่าเชื่อถือต้องตรวจวัดควบคู่กันเสมอ
2. ความล้มเหลวในระบบกระจายไม่ได้เกิดขึ้นพร้อมกันทั้งระบบ แต่จะเริ่มต้นจากจุดเล็กๆ แล้วลุกลามย้อนขึ้นสู่ชั้นบน และการตั้ง Retry ที่ไร้การควบคุมจะกลายเป็นพายุที่เร่งให้ระบบล่มสลายเร็วขึ้น
3. ตู้แร็กในศูนย์ข้อมูลก็คือระบบกระจายทางกายภาพที่มีทั้งจุดล้มเหลวเดี่ยว (SPOF), ขอบเขตความเสียหาย (Blast Radius) และความจำเป็นในการมีแผนย้อนกลับคืนสภาพเดิม (Rollback) เช่นเดียวกับระบบซอฟต์แวร์ทุกประการ
