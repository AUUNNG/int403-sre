# INT531 วิศวกรรมความน่าเชื่อถือของระบบ (Site Reliability Engineering)
## สัปดาห์ที่ 3: พื้นฐานระบบและระบบกระจาย · หาว่าตัวเลขที่แย่ลงมาจากตรงไหน

คณะเทคโนโลยีสารสนเทศ มหาวิทยาลัยเทคโนโลยีพระจอมเกล้าธนบุรี  
บรรยาย 1.5 ชม. + ปฏิบัติการภาคสนาม 1.5 ชม. | ปรับปรุงเนื้อหา พ.ศ. 2569 (2026)

### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- การเชื่อมโยงเนื้อหากับสัปดาห์ที่ผ่านมา: ในสัปดาห์ที่ 2 เราโฟกัสที่มุมมองของผู้ใช้ (User Perspective) ผ่านตัวชี้วัดระดับการให้บริการ (Service Level: SLA, SLO, SLI) เพื่อวัดว่า "ผู้ใช้กำลังเจ็บปวดหรือไม่" แต่ในสัปดาห์ที่ 3 นี้ เราจะเจาะลึก (Drill-down) เข้าไปในระดับระบบและระบบกระจาย (Distributed Systems) เพื่อหาว่า "อะไรคือสาเหตุที่ทำให้ผู้ใช้เจ็บปวด" และตัวเลขประสิทธิภาพที่แย่ลงนั้นมาจากจุดใด
- ความเข้าใจเรื่องความหลากหลายของฮาร์ดแวร์: เซิร์ฟเวอร์ที่ใช้งานจริงในระบบหรือในห้องปฏิบัติการ แต่ละกลุ่มจะไม่ได้รับเครื่องที่มีสเปกเหมือนกันทั้งหมด บางเครื่องมี RAM มาก บางเครื่องมี Storage หรือ CPU ต่างกัน ในทาง SRE หัวใจสำคัญไม่ใช่การมีเครื่องที่แรงที่สุดหรือเร็วที่สุด แต่คือการเข้าใจขอบเขตขีดความสามารถ (Boundaries) ของทรัพยากรที่มีอยู่ และสามารถวัด ประเมิน และบริหารจัดการให้อยู่ในเกณฑ์ความน่าเชื่อถือได้

## สารบัญและแผนการเรียนวันนี้

เช้า: ทฤษฎีและการวินิจฉัย · บ่าย: ลงพื้นที่ขนของและทำรายการครุภัณฑ์

1. ทรัพยากรวิกฤต 4 ชนิด - สัญญาณที่บอกว่าทรัพยากรแต่ละชนิดกำลังอิ่มตัว
2. USE / RED / Golden Signals - เช็กลิสต์สามชุด และการเลือกใช้ให้ตรงกับสิ่งที่กำลังดู
3. ทฤษฎีแถวคอยเบื้องต้น - Little's Law และเหตุผลที่ 80% คือเส้นแบ่ง
4. โหมดความล้มเหลวของระบบกระจาย - Cascading Failure, Retry Storm และ Timeout Budget
5. ตู้ Rack ก็เป็นระบบกระจาย - เชื่อมทฤษฎีเช้ากับงานที่จะทำตอนบ่าย
6. ภาคบ่าย — ลงพื้นที่ - ลงชื่อเข้าพื้นที่ ขนของออก และทำรายการครุภัณฑ์

## ผลลัพธ์การเรียนรู้ประจำคาบ (SLO)

เมื่อจบคาบนี้ นักศึกษาจะสามารถ:

- SLO 3.1: ใช้เมธอด USE และ RED วิเคราะห์ทรัพยากรและบริการได้อย่างเป็นระบบ (CLO5)
- SLO 3.2: ใช้เครื่องมือ Linux ระบุคอขวดของระบบจากสัญญาณความอิ่มตัว (CLO5)
- SLO 3.3: อธิบายความสัมพันธ์ระหว่าง Utilization, คิว และ Latency ตาม Little's Law (CLO5)
- SLO 3.4: อธิบายโหมดความล้มเหลวของระบบกระจายและวิธีตัดวงจรความล้มเหลว (CLO1, CLO5)
- SLO 3.5: ปฏิบัติตามขั้นตอนเข้าพื้นที่ ขนย้าย และบันทึกทะเบียนครุภัณฑ์ได้ถูกต้อง (CLO3, CLO7)

### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- ข้อสอบและการประเมินผล: สไลด์ผลลัพธ์การเรียนรู้ (SLO) เป็นกรอบหลักในการออกข้อสอบวัดผลของรายวิชา นักศึกษาต้องสามารถอธิบายความสัมพันธ์เชิงตัวเลขและทฤษฎี เช่น ความสัมพันธ์ระหว่าง Utilization กับ Latency, การคำนวณ Headroom, พฤติกรรมของ Cascading Failure, และขั้นตอนการจัดการหน้างานตามมาตรฐานความปลอดภัยได้

## ส่วนที่ 1: หาว่าตัวเลขที่แย่ลงมาจากตรงไหน

สัปดาห์ที่แล้วเราวัดได้ว่าผู้ใช้เจ็บ วันนี้เราหาว่าอะไรทำให้เจ็บ

### ทรัพยากรวิกฤต 4 ชนิด และสัญญาณที่บอกว่ากำลังอิ่มตัว

Utilization บอกว่าใช้ไปเท่าไร แต่ Saturation คือตัวที่บอกว่ากำลังจะพัง

| ทรัพยากร | ตัวชี้วัด Utilization | สัญญาณ Saturation ที่ต้องดู | อาการที่ผู้ใช้รู้สึก |
|---|---|---|---|
| CPU | เปอร์เซ็นต์การใช้งานต่อคอร์ | Run queue ยาว, CPU steal สูง, context switch พุ่ง | ทุกอย่างช้าลงพร้อมกันแบบเท่า ๆ กัน |
| หน่วยความจำ | หน่วยความจำที่ถูกใช้จริง | Swap เริ่มทำงาน, page fault สูง, OOM killer ทำงาน | ระบบค้างเป็นช่วง แล้วบริการหายไปเฉย ๆ |
| ดิสก์ I/O | เปอร์เซ็นต์เวลาที่ดิสก์ทำงาน | คิว I/O ยาว, await สูงกว่า service time มาก | คำสั่งที่ต้องอ่านเขียนช้ามาก แต่หน้าอื่นปกติ |
| เครือข่าย | แบนด์วิดท์ที่ใช้เทียบพิกัด | แพ็กเก็ตตกหล่น, retransmit, คิวส่งเต็ม | ช้าไม่สม่ำเสมอ บางคำขอผ่าน บางคำขอค้าง |

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- Utilization vs. Saturation:
  - คนส่วนใหญ่เวลาดูระบบมักดูแค่ Utilization ผ่าน Task Manager หรือหน้าจอมอนิเตอร์ทั่วไป เช่น ดูว่า CPU กี่เปอร์เซ็นต์ หรือ RAM ใช้ไปกี่ GB (เช่น มี 16 GB ใช้ไป 14 GB)
  - แต่ในมุมมอง SRE ตัวเลข Utilization บอกแค่ว่าทรัพยากรถูกใช้งานไปเท่าไร ตัวที่บอกว่าระบบกำลังจะพังจริง ๆ คือ "Saturation" (ความอิ่มตัว / การล้นคิว)
  - เปรียบเทียบ Saturation เหมือนการปรับความอิ่มตัวของสีในภาพถ่ายหรือวิดีโอ หากปรับพอดีภาพจะสดใส แต่ถ้าปรับเกินระดับที่รับได้ (Over-saturated) ภาพจะเละและเพี้ยน ในทางระบบคอมพิวเตอร์ เมื่อเกิดความอิ่มตัวเกินขีดจำกัด ระบบจะค้าง แฮงก์ หรือหยุดทำงานทันที
- เจาะลึกสัญญาณของแต่ละทรัพยากร:
  - CPU Saturation: ดูที่ความยาวของคิวรอรัน (Run Queue), ค่า CPU Steal (กรณีรันบน Virtual Machine / Cloud ที่ถูกเครื่องอื่นแย่ง CPU), และการสลับโพรเซสไปมาอย่างรวดเร็ว (Context Switching พุ่ง) ทำให้อาการที่ผู้ใช้พบคือทุกบริการช้าลงพร้อม ๆ กันอย่างสม่ำเสมอ
  - Memory Saturation: อย่าดูแค่ขนาด RAM ที่ใช้ ให้ดูว่าระบบเริ่มเกิด Swap หรือไม่ เมื่อหน่วยความจำจริงไม่เพียงพอ ระบบปฏิบัติการจะโยกย้ายข้อมูลที่ไม่ได้ใช้งานบ่อยไปไว้บนดิสก์/SSD ซึ่งความเร็วช้ากว่า RAM หลายร้อยเท่า ส่งผลให้เกิด Page Fault สูง และหากพื้นที่หมดอย่างสิ้นเชิง Linux OOM Killer (Out-of-Memory Killer) จะทำงานโดยการปิดหรือกำจัด Process ทิ้ง ส่งผลให้อาการคือแอปพลิเคชันหรือเซอร์วิสดับหายไปเฉย ๆ
  - Disk I/O Saturation: ดูเวลารอคอย (Wait Time / Queue Length) หากระบบค้างเฉพาะหน้าเว็บหรือฟังก์ชันที่มีการเขียน-อ่านฐานข้อมูล แต่หน้าเว็บทั่วไปที่อ่านจากแคชยังทำงานได้ปกติ แสดงว่าคอขวดอยู่ที่ดิสก์
  - Network Saturation: สังเกตจากอัตราแพ็กเก็ตตกหล่น (Dropped Packets) การส่งข้อมูลซ้ำ (Retransmissions) และคิวรับส่งที่เต็ม ทำให้ผู้ใช้รู้สึกว่าระบบช้าแบบไม่สม่ำเสมอ บาง Request ส่งผ่าน บาง Request หลุดหรือค้าง

### USE / RED / Golden Signals

สามเช็กลิสต์ที่ตอบคนละคำถาม ใช้ผิดชุดจะหาไม่เจอ

#### 1. USE Method
- พัฒนาโดย: Brendan Gregg
- ขอบเขตการใช้งาน: ใช้กับทรัพยากร (Resource-centric) โดยวิเคราะห์เจาะลึกทีละทรัพยากร: CPU, หน่วยความจำ, ดิสก์, เครือข่าย
- องค์ประกอบ:
  - Utilisation: ใช้งานไปกี่เปอร์เซ็นต์ (ความจุหรือเวลาที่ถูกใช้งาน)
  - Saturation: มีงานรอคิวอยู่เท่าไร (งานที่รอรับบริการเมื่อทรัพยากรเต็ม)
  - Errors: มีงานที่ล้มเหลวกี่ครั้ง (ข้อผิดพลาดของตัวอุปกรณ์หรือฮาร์ดแวร์)

#### 2. RED Method
- พัฒนาโดย: Tom Wilkie
- ขอบเขตการใช้งาน: ใช้กับบริการ (Service-centric / Request-driven) เหมาะสำหรับ Microservices, Web API หรือบริการที่รับคำขอจากภายนอก
- องค์ประกอบ:
  - Rate: จำนวนคำขอต่อวินาที (Request Rate / Throughput)
  - Errors: จำนวนคำขอที่ล้มเหลวต่อวินาที (Error Rate)
  - Duration: การกระจายเวลาตอบสนองของคำขอ (Latency / Request Duration)

#### 3. Golden Signals
- พัฒนาโดย: Google SRE (ตามหนังสือ Google SRE Book บทที่ 6: Monitoring Distributed Systems)
- ขอบเขตการใช้งาน: ใช้กับทุกอย่างที่ผู้ใช้สัมผัส ครอบคลุมภาพรวมทั้งหมดของระบบ
- องค์ประกอบ:
  - Latency: เวลาที่ใช้ในการตอบสนองคำขอ (แยกแยะระหว่างเวลาของคำขอที่สำเร็จกับคำขอที่ล้มเหลว)
  - Traffic: ปริมาณความต้องการหรือโหลดที่เข้ามายังระบบ (เช่น HTTP requests/sec หรือ Network I/O rate)
  - Errors: อัตราคำขอที่ล้มเหลว ไม่ว่าจะล้มเหลวแบบชัดเจน (HTTP 500) หรือล้มเหลวแบบซ่อนเร้น (HTTP 200 แต่เนื้อหาผิดพลาด)
  - Saturation: ความอิ่มตัวของระบบและทรัพยากรที่ใช้รองรับบริการ ซึ่งเป็นตัวชี้วัดคาดการณ์ล่วงหน้าก่อนที่ระบบจะล่ม

#### หลักการจำและบูรณาการใช้งาน
- RED บอกว่าผู้ใช้กำลังเจ็บ (Symptom: วัดอาการภายนอกที่ผู้ใช้ได้รับผลกระทบ)
- USE บอกว่าทรัพยากรตัวไหนทำให้เจ็บ (Cause: ชี้เป้าทรัพยากรภายในที่เป็นต้นเหตุของปัญหา)
- Golden Signals เปรียบเหมือนชุดสมบูรณ์ที่นำแกนของ RED มารวมเข้ากับ Saturation
- ในการทำงานจริงของ SRE ต้องใช้ทั้งสองชุดร่วมกันเสมอ จึงจะสามารถระบุอาการและแก้ปัญหาได้ตรงจุด

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- ปัญหาโลกจริงในองค์กร (Dev vs. Infra Silo):
  - บ่อยครั้งทีม Infrastructure และทีม Developer ไม่คุยกัน หรือมองคนละมิติ เมื่อระบบช้า ทีม Infra มักดูแค่ Utilization พื้นฐานแล้วแจ้งว่า CPU/RAM ยังเหลือ หรือถ้าระบบช้าก็แก้ปัญหาแบบปลายเหตุด้วยการขอซื้อ RAM เพิ่ม หรือเปลี่ยนไปใช้ดิสก์ราคาแพง (SSD/NVMe)
  - ตัวอย่างระบบลงทะเบียนเรียน: เมื่อมีนักศึกษาเข้าใช้งานพร้อมกันจำนวนมาก ระบบช้าและค้าง หากไม่ดู Golden Signals หรือแยกแยะระหว่าง Symptom กับ Cause ผู้ดูแลอาจคิดว่าเซิร์ฟเวอร์สเปกไม่พอ ทั้งที่สาเหตุที่แท้จริงเกิดจากโค้ดของแอปพลิเคชันที่เขียน Query แบบวนลูปดึงข้อมูลซ้ำ ๆ โดยไม่มีระบบ Caching ส่งผลให้เกิด I/O Saturation ที่ฐานข้อมูล
  - หน้าที่ของ SRE คือการเป็นสะพานเชื่อมระหว่างโค้ดและอินฟราสตรักเจอร์ โดยใช้ตัวชี้วัดเหล่านี้ในการระบุต้นตออย่างเป็นระบบ
- คำแนะนำสำหรับการทำโครงงาน (Project / Capstone):
  - การติดตั้งเครื่องมือ Monitoring เช่น Prometheus หรือ Grafana เป็นเรื่องทางเทคนิคที่ทำตามคู่มือได้ไม่ยาก แต่สิ่งที่มีมูลค่าสูงคือ "การกำหนดว่าจะวัดอะไร และตั้ง Alert อย่างไรให้มีความหมาย"
  - การระบุ SLI/SLO และการออกแบบ Dashboard ที่สะท้อน USE และ RED ถือเป็นจุดเด่นสำคัญสำหรับพอร์ตโฟลิโอการสมัครงานสาย SRE, DevOps และ Systems Engineer

### เครื่องมือที่ใช้จริงบน Linux

จำไม่กี่ตัวก็พอ แต่ต้องรู้ว่าแต่ละตัวตอบคำถามอะไร

| คำสั่ง | ตอบคำถามว่า | สิ่งที่ต้องดูเป็นอันดับแรก |
|---|---|---|
| `uptime` / `top` | ระบบมีงานค้างมากแค่ไหน | Load average เทียบกับจำนวนคอร์ ถ้าเกินจำนวนคอร์แปลว่ามีคิวรอ |
| `vmstat 1` | หน่วยความจำและ CPU กำลังอึดอัดไหม | คอลัมน์ `r` (คิวรอ CPU) และ `si`/`so` (การใช้ swap-in / swap-out) |
| `iostat -xz 1` | ดิสก์เป็นคอขวดหรือไม่ | `%util` และ `await` ถ้า `await` สูงกว่า `svctm` มากคือมีคิวหน่วงสะสม |
| `ss -s` / `ss -tin` | เครือข่ายมีปัญหาอะไร | จำนวน connection ค้าง, retransmit และขนาดคิวรับส่ง |
| `dmesg -T \| tail` | เคอร์เนลบ่นอะไรไว้บ้าง | ข้อความ OOM killer, ดิสก์ error และการรีเซ็ตฮาร์ดแวร์/อุปกรณ์ |
| `pidstat 1` | กระบวนการไหนกินทรัพยากร | เรียงตาม CPU และ I/O แล้วดูว่าเป็น Process ที่คาดไว้หรือไม่ |

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- แนวทางการใช้คำสั่ง Linux ในการวิเคราะห์ปัญหาจริง:
  - ไม่จำเป็นต้องจำคำสั่งจำนวนมหาศาล แต่ต้องเข้าใจเป้าหมายของแต่ละเครื่องมือ
  - ตรวจสอบ `uptime`: ดูค่า Load Average 3 ค่า (1, 5, 15 นาที) เทียบกับจำนวน CPU Cores หากเครื่องมี 2 คอร์ แต่ Load Average พุ่งไปที่ 4.0 หมายความว่ามี Process รอคิวประมวลผลเฉลี่ย 2 ตัวตลอดเวลา
  - ตรวจสอบ `vmstat 1`: ดูคอลัมน์ `r` (Runnable processes) หากสูงกว่าจำนวนคอร์แสดงว่า CPU Saturation และสังเกตคอลัมน์ `si` (Swap In) และ `so` (Swap Out) หากมีตัวเลขวิ่งต่อเนื่อง แสดงว่า RAM ไม่พอจนต้องสลับหน้าความจำกับดิสก์
  - ตรวจสอบ `dmesg -T`: ข้อความจาก Kernel Ring Buffer มักเป็นจุดชี้ขาดเมื่อเกิดปัญหาฮาร์ดแวร์ล้มเหลว บล็อกข้อมูลเสียหาย หรือการทำงานของ OOM Killer

### เดินเรื่องการวินิจฉัยด้วย USE (Worked Diagnosis)

สถานการณ์จำลอง: ผู้ใช้แจ้งว่าระบบลงทะเบียนช้าลงตั้งแต่ 09:00 น.

1. เริ่มจากฝั่งผู้ใช้ก่อนเสมอ
   - ดู RED ของบริการ: p99 Latency เพิ่มขึ้นจาก 400 ms เป็น 3.2 วินาที แต่ Error Rate ยังเป็น 0% แปลว่าระบบแค่ทำงานช้าลง ไม่ใช่ระบบล่มหรือพัง
2. ไล่ลงไปทีละชั้น (Downstream Isolation)
   - ตรวจสอบตามลำดับสถาปัตยกรรม: ชั้น Web ปกติ, ชั้น API พบว่า p99 Latency สูง, ชั้น Database พบว่า p99 Latency สูงตาม แปลว่าต้นตออยู่ที่ฐานข้อมูลหรือชั้นที่ต่ำกว่านั้น
3. ใช้ USE กับเครื่องฐานข้อมูล
   - CPU Utilization อยู่ที่ 45% ซึ่งดูปกติ แต่เมื่อตรวจสอบด้วย `iostat -xz 1` พบว่า `%util` อยู่ที่ 98% และค่า `await` พุ่งสูงถึง 180 ms แสดงว่าดิสก์คือคอขวดที่แท้จริง
4. หาว่าอะไรเปลี่ยน (Root Cause Analysis)
   - ตรวจสอบข้อความแจ้งเตือนในเคอร์เนลผ่าน `dmesg` พบว่าคอนโทรลเลอร์ RAID ปรับโหมดการทำงานจาก Write-back เป็น Write-through อัตโนมัติ เนื่องจากแบตเตอรี่สำรองของแคช (Battery Backup Unit - BBU) เสื่อมสภาพ ทำให้ระบบต้องเขียนข้อมูลตรงลงจานแม่เหล็กโดยไม่ผ่านแคช ส่งผลให้ความเร็วการเขียนตกลงถึง 10 เท่า
5. บรรเทาก่อน แล้วค่อยแก้ราก (Mitigate before Root-Cause Fix)
   - ในสถานการณ์วิกฤตที่มีผู้ใช้หนาแน่น ห้ามสั่งดับระบบเพื่อเปลี่ยนแบตเตอรี่ทันที ให้ทำการบรรเทาปัญหา (Mitigation) ด้วยการโยกย้ายทราฟฟิกการอ่าน (Read Traffic) ไปยังเครื่อง Replica หรือเซิร์ฟเวอร์สำรองเพื่อลดภาระงานของดิสก์ จากนั้นจึงวางแผนเปลี่ยนแบตเตอรี่ในช่วงเวลาปิดปรับปรุงระบบนอกเวลาทำการ (Maintenance Window)

#### ข้อสังเกตสำคัญ
- ไม่มีขั้นตอนใดที่เริ่มจากการเดา ทุกขั้นตอนมีตัวเลขและเครื่องมือวัดผลรองรับอย่างชัดเจน
- ลำดับความสำคัญในการกู้คืนระบบ: ต้องเน้นการบรรเทาปัญหาให้ระบบกลับมาให้บริการได้ก่อน แล้วจึงดำเนินการแก้ไขที่สาเหตุรากเหง้า (Root Cause) ในภายหลัง

## ส่วนที่ 2: ทำไมระบบถึงพังตอนที่ยังดู "ไม่เต็ม"

ทฤษฎีแถวคอยเบื้องต้น และเส้นแบ่งที่ 80%

### Utilization, คิว และ Latency

ความสัมพันธ์นี้ไม่เป็นเส้นตรง (Non-linear relationship) และนั่นคือสาเหตุที่ระบบพังแบบกะทันหัน

- กราฟความสัมพันธ์ Utilization กับ Latency (The Knee at ~80%):
  - ใช้งาน 50% -> ช้าเป็น 2 เท่า ของเวลาพื้นฐาน
  - ใช้งาน 80% -> ช้าเป็น 5 เท่า ของเวลาพื้นฐาน
  - ใช้งาน 90% -> ช้าเป็น 10 เท่า ของเวลาพื้นฐาน
- Little's Law:
  - สูตร: L = λ × W
  - ความยาวคิวเฉลี่ย (L) = อัตราคำขอเข้าสู่ระบบ (λ) × เวลาเฉลี่ยที่แต่ละคำขออยู่ในระบบ (W)
  - ตัวอย่างการคำนวณ: อัตราคำขอเข้ามา 200 ครั้ง/วินาที แต่ละคำขอใช้เวลาอยู่ในระบบ 0.25 วินาที  
    คำนวณ: L = 200 × 0.25 = 50 คำขอที่ค้างสะสมอยู่ในระบบ
- ข้อคิดสำคัญ:
  - การเพิ่มโหลดอีก 10% ในขณะที่ระบบมี Utilization อยู่ที่ 50% ผู้ใช้แทบจะไม่รู้สึกถึงความเปลี่ยนแปลง
  - แต่การเพิ่มโหลด 10% เท่ากันในขณะที่ระบบแตะระดับ 80% เวลาตอบสนองจะกระโดดเพิ่มขึ้นเป็นเท่าตัวทันที

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- พฤติกรรมแบบฮอกกี้สติ๊ก (Hockey-stick Curve):
  - กราฟความสัมพันธ์ระหว่าง Utilization และ Latency จะมีลักษณะค่อย ๆ ลาดเอียงในช่วง 0–60% แต่เมื่อเข้าใกล้ 80% (จุดที่เรียกว่า "The Knee") ความชันจะเปลี่ยนเป็นทวีคูณแบบเอ็กซ์โพเนนเชียล
  - สาเหตุที่ระบบมักล่มโดยไม่มีใครคาดคิด: ผู้ดูแลระบบมักชะล่าใจเมื่อเห็นตัวเลขมอนิเตอร์อยู่ที่ 70% หรือ 80% โดยคิดว่า "ยังเหลือพื้นที่ว่างอีกตั้ง 20–30%" แต่ในทางทฤษฎีแถวคอย เมื่อเกินจุด Knee ไปแล้ว ทรัพยากรส่วนที่เหลือจะถูกกลืนหายไปภายในเวลาไม่กี่วินาที และคิวจะสะสมจนระบบค้างก่อนที่ทีมงานจะเข้าไปแก้ไขได้ทัน
  - ดังนั้น เกณฑ์ 80% จึงถือเป็นเส้นแบ่งอันตรายที่ต้องตั้งค่าแจ้งเตือน (Threshold Alert) เพื่อป้องกันไม่ให้ระบบก้าวข้ามไปสู่จุดวิกฤต

---

### แล้วควรเผื่อไว้เท่าไร: การคำนวณ Headroom ที่ใช้ได้จริง

ขั้นตอนการคำนวณขีดความสามารถรองรับ (Headroom Calculation):

1. วัดโหลดสูงสุดที่เคยเจอ (Peak Load):
   - เก็บค่าโหลดสูงสุดรายวันย้อนหลัง 90 วัน ห้ามใช้ค่าเฉลี่ย -> สมมุติวัดได้ 1,200 คำขอ/วินาที
2. บวกการเติบโตที่คาดไว้ (Expected Growth):
   - ประมาณการอัตราเติบโต เช่น เพิ่มขึ้น 15% ต่อภาคการศึกษา -> 1,200 × 1.15 = 1,380 คำขอ/วินาที
3. เผื่อการสูญเสียหนึ่งโหนด (N-1 Redundancy):
   - หากระบบมีเซิร์ฟเวอร์ทั้งหมด 3 เครื่อง ออกแบบให้ระบบยังคงทำงานได้ตามปกติเมื่อเครื่องใดเครื่องหนึ่งดับไป นั่นคือ 2 เครื่องที่เหลือต้องแบกรับโหลดทั้งหมดได้ จึงนำไปหารด้วย 2 (ไม่ใช่หารด้วย 3) -> 1,380 ÷ 2 = 690 คำขอ/วินาทีต่อเครื่อง
4. ป้องกันไม่ให้เกินเส้นวิกฤต 80%:
   - นำค่าโหลดที่แต่ละเครื่องต้องรับได้มาหารด้วย 0.8 เพื่อให้อยู่ในกรอบ 80% Utilization -> 690 ÷ 0.8 = 863 คำขอ/วินาทีต่อเครื่อง

สรุปการตัดสินใจ:
- หากเครื่องเซิร์ฟเวอร์หนึ่งเครื่องมีสมรรถนะรองรับจริงได้เพียง 700 คำขอ/วินาที แต่ผลการคำนวณระบุว่าต้องการ 863 คำขอ/วินาทีต่อเครื่อง แปลว่าเราต้องเพิ่มจำนวนเครื่องล่วงหน้าทันที ไม่ใช่รอให้ระบบช้าหรือพังก่อนแล้วค่อยแก้ไข

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- ความหมายของ Headroom:
  - เปรียบเทียบกับคำว่า Headroom ในห้องเรียน (ระยะห่างจากศีรษะถึงเพดาน) หรือ Headroom ภายในห้องโดยสารรถยนต์ รถตู้จะมี Headroom สูงทำให้โปร่งสบาย ส่วนรถสปอร์ตมี Headroom ต่ำเพื่อเน้นความเร็ว
  - ในระบบไอที การมี Headroom มากเกินไปทำให้ระบบสิ้นเปลืองงบประมาณเกินความจำเป็น แต่หากมีน้อยเกินไประบบจะเปราะบาง
- กฎเหล็ก: ห้ามใช้ค่าเฉลี่ย (Average) ในการคำนวณความจุเด็ดขาด:
  - ค่าเฉลี่ยจะเกลี่ยกลบช่วงเวลาที่โหลดพุ่งสูงสุด (Traffic Spikes) ทิ้งไป หากเราเตรียมระบบตามค่าเฉลี่ย เมื่อถึงเวลาที่ผู้ใช้แห่กันเข้ามาใช้งานจริง ระบบจะล่มทันที
- การนำไปใช้ในชีวิตจริงและโครงงาน:
  - เมื่อต้องขอโควตาทรัพยากรระบบหรือสร้าง VM สำหรับโครงการ ให้คำนวณขนาดตามสมการนี้อย่างมีหลักการ มีตัวเลขรองรับว่าเพราะเหตุใดจึงต้องการสเปกและจำนวนเครื่องเท่านี้ ไม่ใช่การกะประมาณหรือขอทรัพยากรเผื่อไว้เกินจริง

## ส่วนที่ 3: โหมดความล้มเหลวของระบบกระจาย

ความล้มเหลวไม่ได้เกิดทีเดียวทั้งระบบ แต่ไหลจากชั้นหนึ่งไปอีกชั้นหนึ่ง

### Cascading Failure — ความล้มเหลวที่ไหลขึ้นข้างบน

ไม่มีชั้นไหนพังเองเลย แต่ทั้งเส้นทางล่ม บริการที่ช้าลงเพียงตัวเดียว ทำให้ทุกชั้นเหนือมันล้มได้อย่างไร:

1. ฐานข้อมูลเริ่มช้าลง: คำสั่งค้นข้อมูลช้าลง ยังไม่มีอะไรล้มเหลว เพียงแต่ตอบสนองใน 3 วินาที แทนที่จะเป็น 0.2 วินาที
2. เธรดใน API สะสมค้าง: ทุกคำขอที่รออยู่ถือเธรดไว้จนพูลเธรดเต็ม คำขอใหม่ต้องเข้าคิวต่อท้าย
3. ไคลเอนต์หมดเวลาแล้วส่งซ้ำ: คำขอซ้ำเข้ามาขณะที่คำขอเดิมยังทำงานไม่เสร็จ โหลดเพิ่มขึ้นเป็นสองเท่า และสามเท่า
4. ทั้งเส้นทางล่ม: ชั้นเว็บอิ่มตัวตามไปด้วย Health check ไม่ผ่าน เครื่องถูกระบบสั่งรีสตาร์ตวนซ้ำไม่รู้จบ

#### จุดตัดวงจรความล้มเหลว (Circuit Breaking Points)
- ตั้ง Timeout ให้สั้นกว่าความอดทนของผู้เรียก
- การ Retry แบบ Backoff และ Jitter
- จำกัดงบการ Retry (Retry Budget)
- ติดตั้ง Circuit Breaker เพื่อตัดวงจรทันทีเมื่อบริการปลายทางไม่ตอบสนอง
- ทิ้งโหลดที่ขอบระบบ (Load Shedding) ตัดคำขอที่ไม่สำคัญออกเพื่อรักษาการทำงานของระบบหลัก

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- กลไกการเกิด Cascading Failure:
  - ปัญหาในระบบกระจายมักไม่ได้เริ่มจากการที่ระบบดับไปทั้งหมดในทันที แต่มักเริ่มจากจุดเล็ก ๆ เช่น เซอร์วิสฐานข้อมูลตอบสนองช้าลงจาก 200 ms เป็น 3 วินาที
  - เมื่อฝั่ง Client หรือ Web Layer ไม่ได้รับการตอบสนองตามเวลาที่คาดหวัง ระบบ Client จะเริ่มส่งคำขอซ้ำ (Retries) ในขณะที่คำขอเดิมยังประมวลผลค้างอยู่ในเธรด โหลดจึงทวีคูณเป็น 2 เท่า และ 3 เท่า
  - เมื่อ Web Server ทำงานจน Connection และ Memory เต็ม การตรวจสอบสถานะการทำงาน (Health Check) จะล้มเหลว ทำให้ Container Orchestrator (เช่น Kubernetes) สั่งรีสตาร์ต Pods หรือ Nodes ใหม่อย่างต่อเนื่อง ซึ่งโหนดที่เพิ่งบูตขึ้นมาใหม่จะถูกทราฟฟิกมหาศาลที่ค้างอยู่ถล่มซ้ำจนดับไปอีกครั้ง กลายเป็นปรากฏการณ์ตายวนซ้ำไม่รู้จบ (Death Spiral)
- Circuit Breaker: การตัดโหลดอย่างเด็ดขาดโดยไม่ประนีประนอม เพื่อปกป้องระบบส่วนรวมและเปิดโอกาสให้เซอร์วิสด้านหลังมีเวลาฟื้นตัวกลับคืนมา

### Timeout Budget และ Retry ที่ไม่ทำให้แย่ลง

ตัวอย่างการคำนวณที่ต้องทำก่อนตั้งค่าจริง:

- งบเวลาต้องหารจากบนลงล่าง (Top-down Timeout Budgeting):
  - ผู้ใช้ยอมรอ 3 วินาที -> ชั้นเว็บตั้ง Timeout 2.5 วินาที -> API ตั้ง Timeout 2 วินาที -> ฐานข้อมูลตั้ง Timeout 1.5 วินาที
  - ข้อห้าม: ห้ามให้ชั้นล่างตั้งเวลานานกว่าชั้นบน เพราะหากชั้นบนตัดการเชื่อมต่อไปแล้ว แต่ชั้นล่างยังคงประมวลผลต่อ จะทำให้ระบบสูญเสียทรัพยากรไปกับการประมวลผลคำขอที่ไม่มีใครรอรับผลลัพธ์แล้ว
- Retry ต้องมีงบจำกัด (Retry Budget):
  - อนุญาตให้ Retry ได้ไม่เกิน 10% ของคำขอทั้งหมด
  - หากอัตราความผิดพลาดเกิน 10% แปลว่าระบบปลายทางกำลังประสบปัญหาจริง การฝืนส่งซ้ำจะยิ่งซ้ำเติมให้ระบบพังทลายเร็วยิ่งขึ้น
- Backoff ต้องมี Jitter:
  - หากทุกไคลเอนต์ใช้ระยะเวลารอคงที่เท่ากัน (เช่น รอ 1 วินาทีเท่ากันแล้วส่งซ้ำพร้อมกัน) จะเกิดคลื่นโหลดกระแทกซ้ำอย่างรุนแรง (Thundering Herd Problem)
  - จำเป็นต้องเพิ่มการสุ่มเวลา (Random Jitter) เข้าไปในสูตร Exponential Backoff เพื่อกระจายช่วงเวลาที่คำขอจะส่งเข้ามายังระบบ
- บางคำขอห้าม Retry โดยเด็ดขาด:
  - คำขอที่ไม่เป็น Idempotent (การกระทำซ้ำแล้วผลลัพธ์เปลี่ยนแปลง) เช่น คำสั่งตัดเงิน หรือการกดยืนยันลงทะเบียน
  - ต้องมีการใช้งาน Idempotency Key กำกับ เพื่อให้ระบบสามารถตรวจสอบได้ว่าคำขอนี้เคยประมวลผลไปแล้วหรือไม่ ก่อนที่จะอนุญาตให้ส่งซ้ำได้อย่างปลอดภัย

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- ความน่าเชื่อถือ 100% ไม่มีอยู่จริง:
  - ในงาน SRE เราไม่สามารถทำให้ระบบปราศจาก Error ได้ 100% ระบบที่ไม่มี Error ย่อมแปลว่าไม่มีใครใช้งาน
  - เป้าหมายของการตั้งค่า Timeout, Retry Budget และ Jitter ไม่ใช่การกำจัดข้อผิดพลาดให้เหลือศูนย์ แต่เป็นการควบคุมความเสี่ยงไม่ให้ข้อผิดพลาดเล็กน้อยลุกลามกลายเป็นหายนะของทั้งระบบ
- กรณีศึกษาเรื่องธุรกรรมการเงิน:
  - ความรู้สึกของผู้ใช้เวลาตัดบัตรเครดิตหรือโอนเงินแล้วหน้าจอหมุนค้าง ผู้ใช้จะเกิดความวิตกกังวลว่าเงินถูกตัดไปแล้วหรือไม่ หากไม่มี Idempotency Key และระบบปล่อยให้กดยืนยันซ้ำ ผู้ใช้อาจถูกหักเงินซ้ำซ้อน ซึ่งถือเป็นความผิดพลาดร้ายแรงของระบบธุรกรรม

### ตู้ Rack ก็เป็นระบบกระจายเหมือนกัน

การนำทฤษฎีภาคเช้ามาปรับใช้กับงานภาคบ่าย:

| มิติเชิงระบบ | โลกกายภาพของตู้ Rack |
|---|---|
| Single Point of Failure | PSU สองชุดที่เสียบเข้า PDU ตัวเดียวกัน คือความซ้ำซ้อนปลอม เหมือนบริการสองตัวที่รันอยู่บนเครื่องเดียวกัน |
| Cascading Failure | การถอดสวิตช์เครือข่ายตัวเดียวผิดจังหวะ ทำให้ทุกอุปกรณ์ที่ต่อผ่านมันหายไปพร้อมกัน เหมือนฐานข้อมูลช้าแล้วพังลามขึ้นบน |
| Saturation | PDU ที่โหลด 85% ยังจ่ายไฟได้ แต่ไม่เหลือพื้นที่รองรับกระแสกระชาก (Inrush current) ตอนเปิดเครื่องพร้อมกัน |
| Blast Radius | ก่อนถอดทุกชิ้น ต้องตอบได้ว่าอะไรดับตามและใครเดือดร้อน ซึ่งคือผลจากการทำ Dependency Map ใน Lab 1 |
| Rollback | ภาพถ่ายและป้ายระบุสายคือแผนย้อนกลับในโลกกายภาพ หากไม่มีบันทึกไว้ จะไม่สามารถประกอบกลับสภาพเดิมได้ |

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- กายภาพกับซอฟต์แวร์คือเรื่องเดียวกัน:
  - Single Point of Failure: เซิร์ฟเวอร์ระดับ Enterprise มักมี Power Supply Unit (PSU) 2 ชุดเพื่อทำ Redundancy แต่หากผู้ดูแลเสียบสายไฟทั้งสองเส้นเข้ากับรางไฟ (Power Distribution Unit - PDU) ตัวเดียวกัน เมื่อเบรกเกอร์ของ PDU ตัวนั้นตัด ไฟจะดับทั้งเครื่องทันที การต่อลักษณะนี้จึงเรียกว่า "ความซ้ำซ้อนปลอม"
  - Inrush Current: PDU ที่จ่ายไฟอยู่ระดับ 85% อาจดูเหมือนยังทำงานได้ปกติ แต่ในจังหวะที่เซิร์ฟเวอร์หลายเครื่องบูตพร้อมกัน จะมีกระแสไฟกระชากช่วงเริ่มต้น ซึ่งจะทำให้เบรกเกอร์ทริปตัดการจ่ายไฟทั้งตู้ทันที
  - ข้อจำกัดด้านพลังงานและความร้อน: ภายใน Data Center การติดตั้งอุปกรณ์ไม่ได้ดูแค่ว่ามีช่องว่างในตู้ (Rack Units - U) เหลือหรือไม่ แต่ต้องคำนวณภาระโหลดไฟฟ้าและการระบายความร้อนของเครื่องปรับอากาศด้วย หากติดตั้งอุปกรณ์ที่กินไฟสูง (เช่น เครื่องที่มีการ์ดจอ GPU หลายใบ) เกินโควตาที่ PDU จ่ายได้ เจ้าหน้าที่ศูนย์ข้อมูลมีอำนาจสั่ง Shutdown ปิดตู้ทันทีตามมาตรฐานความปลอดภัย

### สถานีทำรายการครุภัณฑ์

การทำงานจัดเป็นสายพาน ไม่ใช่ต่างคนต่างจด

- สถานีที่ 1 — รับของ: รับอุปกรณ์จากทีมถอด ตรวจสอบว่ามีป้ายหมายเลขติดมาแล้ว ถ้าไม่มีให้ตีกลับทันที
- สถานีที่ 2 — อ่านและบันทึก: อ่านหมายเลข Serial และเลขครุภัณฑ์ออกเสียง อีกคนหนึ่งเป็นผู้กรอกลง INV-01 แล้วอ่านทวนกลับเพื่อยืนยันความถูกต้อง
- สถานีที่ 3 — ถ่ายภาพ: ถ่ายภาพสภาพและป้ายหมายเลข อย่างน้อยหนึ่งภาพต่อชิ้น ตั้งชื่อไฟล์ให้ตรงตามหมายเลขป้าย
- สถานีที่ 4 — จัดกลุ่มปลายทาง: ติดป้ายสีตามประเภท
  - สีเขียว = เก็บไว้ใช้
  - สีน้ำเงิน = คืนพัสดุ
  - สีแดง = ปลดระวาง
  - จากนั้นวางแยกตามโซนที่กำหนด

กฎพิเศษสำหรับสื่อบันทึกข้อมูล: ของที่มีดิสก์ต้องแวะสถานีที่ 2 สองรอบ:
- รอบแรก: บันทึกตัวเครื่องลง INV-01
- รอบที่สอง: บันทึกรายละเอียดดิสก์ทีละชิ้นลง MED-01

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- การแบ่งหน้าที่แบบสายพาน (Assembly Line):
  - การทำงานแบบสายพานช่วยลดความผิดพลาดและป้องกันความสับสน การแบ่งคนให้ชัดเจน (คนถอด, คนขนส่ง, คนอ่าน, คนเขียน, คนถ่ายภาพ) ช่วยให้การทำงานไหลลื่นและรวดเร็วกว่าการต่างคนต่างทำ
  - การอ่านออกเสียงและอ่านทวนซ้ำ (Readback Verification) เป็นมาตรฐานสากลในการจัดการข้อมูลที่มีความสำคัญสูงเพื่อป้องกันข้อผิดพลาดจากการได้ยินผิด
  - อุปกรณ์จัดเก็บข้อมูล (SAN Storage / Hard Disks): ดิสก์ที่ถอดออกมาจะต้องจัดเก็บลงในกล่องหรือภาชนะที่ปิดล็อกอย่างแน่นหนา เพื่อให้เป็นไปตามมาตรฐานการควบคุมสื่อบันทึกข้อมูล (Media Sanitization) ในสัปดาห์ถัดไป

### กฎการบันทึกหน้างาน

ข้อผิดพลาดที่พบทุกปีและวิธีป้องกัน:

#### สิ่งที่ต้องทำ
- บันทึกทันทีที่ถอดอุปกรณ์ ไม่ใช่จำแล้วมาจดทีหลัง
- หนึ่งชิ้นบันทึกหนึ่งบรรทัด แม้จะเป็นรุ่นเดียวกันสิบเครื่องก็ตาม
- ถ้าอ่าน Serial ไม่ออก ให้ถ่ายภาพระยะใกล้แล้วเขียนว่า "อ่านไม่ออก" ห้ามเดาตัวเลข
- ช่องที่ไม่มีข้อมูล ให้เขียนเครื่องหมายขีด (-) ห้ามปล่อยว่าง
- ผู้บันทึกและผู้ตรวจสอบต้องเป็นคนละคนกัน

#### สิ่งที่ห้ามทำ
- ห้ามใช้ดินสอ ให้ใช้ปากกาเท่านั้น
- ห้ามลบด้วยน้ำยาลบคำผิด หากเขียนผิดให้ขีดฆ่าด้วยเส้นตรงหนึ่งเส้นแล้วเซ็นชื่อกำกับ
- ห้ามยกของออกจากห้องก่อนกรอกบรรทัดข้อมูลครบถ้วน
- ห้ามถ่ายภาพหน้าจอที่มีข้อมูลรับรองตัวตน
- ห้ามถอดดิสก์ออกจากเครื่องโดยไม่บันทึกลง MED-01

#### เหตุผลที่กฎมีความเข้มงวด
- เอกสารชุดนี้ใช้เป็นหลักฐานประกอบการส่งคืนครุภัณฑ์และการตรวจสอบตามข้อควบคุม ISO/IEC 27001 Annex A ข้อ A.5.9
- หากตัวเลขในเอกสารไม่ตรงกับของจริง ผู้ที่ลงลายมือชื่อจะต้องเป็นผู้รับผิดชอบ
- การขีดฆ่าแล้วเซ็นกำกับเป็นข้อกำหนดของเอกสารเชิงหลักฐานทางกฎหมายและการตรวจสอบ ไม่ใช่เรื่องความสวยงามเป็นระเบียบ

#### บันทึกเพิ่มเติมจากผู้สอน (Instructor Notes)
- ความสำคัญของเอกสารเชิงหลักฐาน (Audit Trail):
  - ในโลกการทำงานจริงตามมาตรฐานสากล เอกสารที่ใช้บันทึกทรัพย์สินถือเป็นเอกสารที่มีผลทางกฎหมาย การใช้ดินสอหรือน้ำยาลบคำผิดทำให้เอกสารขาดความน่าเชื่อถือทันที เพราะเปิดช่องให้เกิดการแก้ไขเปลี่ยนแปลงย้อนหลังได้
  - การขีดฆ่าเส้นเดียวแล้วลงลายมือชื่อกำกับ เป็นวิธีปฏิบัติสากลที่ยืนยันว่าข้อมูลเดิมถูกแก้ไขโดยใครและแสดงความโปร่งใสในการตรวจสอบ

## สรุปสามประโยคของวันนี้

1. Utilization บอกว่าใช้ไปเท่าไร แต่ Saturation คือตัวที่บอกว่ากำลังจะพัง — ต้องดูทั้งคู่เสมอ

3. ตู้ Rack ที่เรารื้อบ่ายนี้ มีทั้ง Single Point of Failure, Blast Radius และแผนย้อนกลับ เหมือนระบบซอฟต์แวร์ทุกประการ
