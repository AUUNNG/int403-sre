## หมวดที่ 1: SLI, SLO และงบประมาณความผิดพลาด (Error Budget)

### 1.1 สูตรตัวชี้วัดระดับการให้บริการ (Service Level Indicator: SLI)

$$\text{SLI} = \frac{\sum \text{Good Events}}{\sum \text{Valid Events}} \times 100\%$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{SLI}$ | สัดส่วนความสำเร็จของการให้บริการจริงจากมุมมองผู้ใช้ | เปอร์เซ็นต์ ($\%$) |
| $\sum \text{Good Events}$ | จำนวนเหตุการณ์ที่ผ่านเกณฑ์คุณภาพ (เช่น ตอบกลับสำเร็จภายในเวลาที่กำหนด) | จำนวนครั้ง (Events/Requests) |
| $\sum \text{Valid Events}$ | จำนวนเหตุการณ์ที่ถูกต้องทั้งหมดที่เข้าเกณฑ์การประเมิน (ไม่นับคำขอผิดฟอร์แมตจากผู้ใช้) | จำนวนครั้ง (Events/Requests) |

**ตัวอย่างโจทย์สั้น:**
ในรอบ 30 วัน ระบบประมวลผลคำขอทั้งหมด $2,000,000$ ครั้ง พบว่ามีคำขอที่ตอบกลับสำเร็จด้วยรหัส HTTP 200 ภายในเวลา 500 ms จำนวน $1,990,000$ ครั้ง จงคำนวณค่า SLI

**วิธีคำนวณ:**
$$\text{SLI} = \frac{1,990,000}{2,000,000} \times 100\% = \frac{199}{200} \times 100\% = 99.5\%$$
*ตอบ:* ค่า SLI ของระบบอยู่ที่ $99.5\%$

---

### 1.2 สูตรงบประมาณความผิดพลาด (Error Budget)

$$\text{Error Budget} = 100\% - \text{SLO}$$

$$\text{Allowed Downtime} = \text{Error Budget} \times T_{\text{window}}$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{Error Budget}$ | สัดส่วนความล้มเหลวสูงสุดที่ยอมรับได้ตามข้อตกลง | เปอร์เซ็นต์ ($\%$) |
| $\text{SLO}$ | เป้าหมายระดับการให้บริการที่ตกลงร่วมกัน | เปอร์เซ็นต์ ($\%$) |
| $\text{Allowed Downtime}$ | ระยะเวลาสูงสุดที่ระบบสามารถหยุดทำงานได้โดยไม่ผิดข้อตกลง | นาที (Minutes) หรือ ชั่วโมง (Hours) |
| $T_{\text{window}}$ | ความยาวของหน้าต่างเวลาที่ใช้ประเมิน (มาตรฐาน 30 วัน $\approx 43,000$ นาที) | นาที (Minutes) หรือ วัน (Days) |

**ตัวอย่างโจทย์สั้น:**
ระบบกำหนดเป้าหมาย SLO ไว้ที่ $99.9\%$ สำหรับหน้าต่างเวลา 30 วัน จงคำนวณ Error Budget และเวลาหยุดทำงานที่ยอมให้เกิดขึ้นได้ (Allowed Downtime)

**วิธีคำนวณ (คิดในใจ):**
1. $\text{Error Budget} = 100\% - 99.9\% = 0.1\%$
2. หน้าต่างเวลา 30 วัน ปัดเป็นเลขกลมๆ ในใจเท่ากับ $43,000$ นาที
3. $\text{Allowed Downtime} = 0.1\% \times 43,000 = \frac{0.1}{100} \times 43,000 = 43 \text{ นาทีต่อเดือน}$
*ตอบ:* มีงบประมาณความผิดพลาด $0.1\%$ หรือเทียบเท่ากับเวลาหยุดทำงานไม่เกิน $43$ นาทีต่อเดือน

## หมวดที่ 2: ความพร้อมใช้งานของระบบแบบผสม (Composite Availability)

### 2.1 ระบบเชื่อมต่อแบบอนุกรม (Series System)

$$A_{\text{total}} = \prod_{i=1}^{n} A_i = A_1 \times A_2 \times \dots \times A_n$$

$$\text{Error}_{\text{total}} \approx \sum_{i=1}^{n} \text{Error}_i \quad (\text{สูตรประมาณการในใจ})$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $A_{\text{total}}$ | ความพร้อมใช้งานรวมของทั้งระบบ | อัตราส่วน ($0-1$) หรือ เปอร์เซ็นต์ ($\%$) |
| $A_i$ | ความพร้อมใช้งานของบริการย่อยลำดับที่ $i$ | อัตราส่วน ($0-1$) หรือ เปอร์เซ็นต์ ($\%$) |
| $\text{Error}_i$ | อัตราความผิดพลาดของบริการย่อยลำดับที่ $i$ ($1 - A_i$) | เปอร์เซ็นต์ ($\%$) |

**ตัวอย่างโจทย์สั้น:**
ระบบเว็บประกอบด้วย 3 บริการที่ต้องทำงานต่อกันตามลำดับคือ Web Server ($99.9\%$), API Gateway ($99.9\%$), และ Database ($99.9\%$) จงหาความพร้อมใช้งานรวมของระบบ

**วิธีคำนวณ (คิดในใจ):**
1. แต่ละตัวมี Error เท่ากับ $100\% - 99.9\% = 0.1\%$
2. ระบบต่ออนุกรม Error จะบวกสะสมกัน: $\text{Error}_{\text{total}} \approx 0.1\% + 0.1\% + 0.1\% = 0.3\%$
3. $A_{\text{total}} \approx 100\% - 0.3\% = 99.7\%$
*ตอบ:* ความพร้อมใช้งานรวมลดลงเหลือประมาณ $99.7\%$ (ต่ำกว่าจุดที่อ่อนแอที่สุด)

---

### 2.2 ระบบเชื่อมต่อแบบขนาน / ความซ้ำซ้อน (Parallel / Redundant System)

$$U_{\text{total}} = \prod_{i=1}^{n} U_i = (1 - A_1) \times (1 - A_2) \times \dots \times (1 - A_n)$$

$$A_{\text{total}} = 1 - U_{\text{total}}$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $U_{\text{total}}$ | อัตราความไม่พร้อมใช้งานรวม (Unavailability) | อัตราส่วน ($0-1$) |
| $U_i$ | อัตราความไม่พร้อมใช้งานของโหนดลำดับที่ $i$ ($1 - A_i$) | อัตราส่วน ($0-1$) |
| $A_{\text{total}}$ | ความพร้อมใช้งานรวมหลังทำ Redundancy | เปอร์เซ็นต์ ($\%$) |

**ตัวอย่างโจทย์สั้น:**
เครื่องแม่ข่ายเว็บ 2 เครื่องทำงานขนานกันแบบ Active-Active แต่ละเครื่องมีความพร้อมใช้งานเดี่ยวอยู่ที่ $99\%$ ($U = 0.01$) จงหาความพร้อมใช้งานรวมหากเครื่องใดเครื่องหนึ่งพัง อีกเครื่องสามารถรับงานแทนได้ทันที

**วิธีคำนวณ:**
1. อัตราที่ทั้งสองเครื่องจะพังพร้อมกัน: $U_{\text{total}} = 0.01 \times 0.01 = 0.0001$ ($0.01\%$)
2. ความพร้อมใช้งานรวม: $A_{\text{total}} = 1 - 0.0001 = 0.9999 = 99.99\%$
*ตอบ:* การทำ Redundancy 2 เครื่อง ช่วยยกระดับความพร้อมใช้งานจาก Two Nines ($99\%$) ขึ้นเป็น Four Nines ($99.99\%$)

## หมวดที่ 3: อัตราการเผาผลาญงบประมาณ (Burn Rate & Exhaustion)

### 3.1 การคำนวณ Burn Rate

$$\text{Burn Rate} = \frac{\text{อัตราความผิดพลาดจริงในปัจจุบัน}}{\text{อัตราความผิดพลาดสูงสุดที่ยอมรับได้ตาม SLO}} = \frac{1 - \text{Current SLI}}{1 - \text{SLO}}$$

$$\text{Time to Exhaustion} = \frac{\text{ความยาวหน้าต่างเวลาทั้งหมด}}{\text{Burn Rate}}$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{Burn Rate}$ | ความเร็วสัมพัทธ์ในการใช้ Error Budget เทียบกับอัตราปกติ | ตัวคูณเท่า (Unitless ratio, เช่น $1\times, 14.4\times$) |
| $\text{Current SLI}$ | ค่าความสำเร็จจริง ณ หน้าต่างเวลานั้น | อัตราส่วน ($0-1$) |
| $\text{SLO}$ | ค่าเป้าหมายตามข้อตกลง | อัตราส่วน ($0-1$) |
| $\text{Time to Exhaustion}$ | เวลาที่เหลืออยู่ก่อนที่งบประมาณความผิดพลาดจะหมดเกลี้ยง | วัน (Days) หรือ ชั่วโมง (Hours) |

**ตัวอย่างโจทย์สั้น:**
ระบบตั้ง SLO ไว้ที่ $99\%$ (ยอมรับ Error ได้ $1\%$) ในหน้าต่างเวลา 30 วัน ขณะนี้ระบบกำลังเกิดปัญหาและมี Error Rate พุ่งขึ้นเป็น $5\%$ จงคำนวณ Burn Rate และระบุว่างบประมาณ 30 วันจะหมดลงภายในกี่วัน

**วิธีคำนวณ:**
1. $\text{Burn Rate} = \frac{5\%}{1\%} = 5$
2. $\text{Time to Exhaustion} = \frac{30 \text{ วัน}}{5} = 6 \text{ วัน}$
*ตอบ:* ระบบกำลังเผางบประมาณเร็วกว่าปกติ $5$ เท่า และงบประมาณความผิดพลาดทั้งเดือนจะหมดลงภายใน $6$ วัน

## หมวดที่ 4: ทฤษฎีแถวคอยและสูตรคำนวณ Headroom สำรองโหนด (N-1 และเพดาน 80%)

### 4.1 กฎของลิตเติล (Little's Law)

$$L = \lambda \times W$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $L$ | จำนวนงานหรือคำร้องเฉลี่ยที่ตกค้างรออยู่ในระบบ (Queue Length / Concurrency) | คำขอ (Requests) หรือ ชิ้นงาน (Tasks) |
| $\lambda$ (Lambda) | อัตราเฉลี่ยของงานที่ไหลเข้ามาในระบบ (Arrival Rate) | คำขอต่อวินาที (Requests/sec: RPS) |
| $W$ | เวลาเฉลี่ยที่งานหนึ่งชิ้นใช้ชีวิตอยู่ในระบบตั้งแต่เข้าจนเสร็จ (Residence/Response Time) | วินาที (Seconds) |

**ตัวอย่างโจทย์สั้น:**
มีคำร้องส่งเข้ามาที่ระบบเฉลี่ย $200$ คำขอต่อวินาที ($\lambda = 200$) และคำร้องแต่ละตัวใช้เวลาในการประมวลผลเฉลี่ย $0.25$ วินาที ($W = 0.25$) จงหาจำนวนคำร้องที่ค้างอยู่ในระบบ

**วิธีคำนวณ:**
$$L = 200 \times 0.25 = 50 \text{ คำขอ}$$
*ตอบ:* มีคำขอค้างอยู่ในระบบ ณ เวลาใดเวลาหนึ่งเฉลี่ย $50$ คำขอ

---

### 4.2 สูตรการคำนวณความจุสำรองแบบ 4 ขั้นตอน (Headroom 4-Step Sizing)

$$\text{Capacity ต่อเครื่อง} = \frac{\text{Peak Load} \times (1 + \text{Growth Rate})}{(N - 1) \times 0.80}$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{Peak Load}$ | โหลดสูงสุดจริงที่เคยวัดได้ในรอบ 90 วัน (ห้ามใช้ค่าเฉลี่ย) | คำขอต่อวินาที (RPS) |
| $\text{Growth Rate}$ | อัตราการเติบโตของทราฟฟิกที่คาดการณ์ไว้ (เช่น $15\% = 0.15$) | เปอร์เซ็นต์ ($\%$) |
| $N$ | จำนวนเครื่องเซิร์ฟเวอร์ทั้งหมดที่มีอยู่ในระบบปัจจุบัน | เครื่อง (Nodes/Servers) |
| $N - 1$ | จำนวนเครื่องที่เหลือทำงานได้จริงเมื่อมีเครื่องล่ม 1 เครื่อง | เครื่อง (Nodes/Servers) |
| $0.80$ | ค่าเพดานปลอดภัยสูงสุด เพื่อไม่ให้เกินจุดหักศอกของคิว (The Knee Curve 80%) | อัตราส่วน ($80\%$) |

**ตัวอย่างโจทย์สั้น:**
ระบบลงทะเบียนมีโหลดสูงสุดในรอบ 90 วันอยู่ที่ $1,200$ RPS คาดว่าเทอมหน้าจะโตขึ้น $15\%$ ปัจจุบันมีเซิร์ฟเวอร์รันอยู่ $3$ เครื่อง จงคำนวณว่าแต่ละเครื่องต้องมีความจุเท่าใดจึงจะรองรับโหลดได้ตามเกณฑ์ $N-1$ โดยไม่เกินเพดาน $80\%$

**วิธีคำนวณ:**
1. โหลดที่คาดการณ์: $1,200 \times 1.15 = 1,380 \text{ RPS}$
2. เผื่อเครื่องพัง 1 เครื่อง ($N-1 = 3-1 = 2$ เครื่อง): $\frac{1,380}{2} = 690 \text{ RPS ต่อเครื่อง}$
3. ควบคุมไม่ให้เกินเส้น $80\%$: $\frac{690}{0.80} = 862.5 \approx 863 \text{ RPS ต่อเครื่อง}$
*ตอบ:* เซิร์ฟเวอร์แต่ละเครื่องต้องรองรับโหลดจริงได้อย่างน้อย $863$ RPS (หากสเปกเครื่องรับได้เพียง $700$ RPS แปลว่าต้องจัดหาเครื่องที่ 4 เพิ่มทันที)

---

## หมวดที่ 5: งบเวลาและนโยบายคำสั่งส่งซ้ำ (Timeout & Retry Budget)

### 5.1 การกระจายงบเวลาจากบนลงล่าง (Top-Down Timeout Budget)

$$T_{\text{Client}} > T_{\text{Web}} > T_{\text{API}} > T_{\text{Database}}$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $T_{\text{Client}}$ | เวลาที่ผู้ใช้ยินดีรอคอยก่อนที่จะกดปิดหรือกดยกเลิก | วินาที (Seconds) |
| $T_{\text{Layer}}$ | ค่า Timeout ที่กำหนดไว้ในแต่ละชั้นของสถาปัตยกรรม | วินาที (Seconds) |

**กฎทางวิศวกรรม:**
ห้ามกำหนดให้ชั้นล่างมีค่า Timeout นานกว่าชั้นบนเด็ดขาด มิเช่นนั้นชั้นบนจะตัดการเชื่อมต่อไปแล้ว แต่ชั้นล่างยังคงทำงานค้างอยู่ทำให้สูญเสียทรัพยากรฟรี

**ตัวอย่างโจทย์สั้น:**
ผู้ใช้ยอมรอคอยผลการทำงานได้สูงสุด $3$ วินาที จงออกแบบค่า Timeout ของชั้น Web, API และ Database ให้ถูกต้องตามหลักวิศวกรรม

**แนวทางการกำหนดค่า:**
- ผู้ใช้ยอมรอ: $3.0$ วินาที
- ชั้น Web ตั้ง Timeout: $2.5$ วินาที
- ชั้น API ตั้ง Timeout: $2.0$ วินาที
- ชั้น Database ตั้ง Timeout: $1.5$ วินาที

---

### 5.2 งบประมาณคำสั่งส่งซ้ำ (Retry Budget Constraint)

$$\text{Retry Request Rate} \le 10\% \times \text{Total Request Rate}$$

$$\text{Backoff Time} = \min(T_{\text{max}}, T_{\text{base}} \times 2^{\text{attempt}}) \pm \text{Jitter}$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{Retry Rate}$ | อัตราคำร้องที่อนุญาตให้ส่งซ้ำได้ | คำขอต่อวินาที (RPS) |
| $10\%$ | เพดานความปลอดภัยสูงสุด เพื่อป้องกันการเกิด Retry Storm | สัดส่วน ($0.10$) |
| $\text{Backoff Time}$ | เวลาหน่วงก่อนส่งคำขอซ้ำในแต่ละรอบ | มิลลิวินาที (ms) หรือ วินาที (s) |
| $\text{Jitter}$ | ค่าสุ่มเวลาเพื่อกระจายคลื่นทราฟฟิก ไม่ให้ไคลเอนต์ยิงมาพร้อมกัน | มิลลิวินาที (ms) |

**ตัวอย่างโจทย์สั้น:**
ระบบมีทราฟฟิกรวม $5,000$ RPS เกิดปัญหาเครือข่ายกระตุกชั่วคราว ไคลเอนต์พยายามส่งคำขอซ้ำ ระบบควรอนุญาตให้มีปริมาณคำขอส่งซ้ำ (Retry) ได้สูงสุดไม่เกินกี่ RPS

**วิธีคำนวณ:**
$$\text{Max Retry Allowed} = 5,000 \times 10\% = 500 \text{ RPS}$$
*ตอบ:* อนุญาตให้ส่งคำขอซ้ำได้ไม่เกิน $500$ RPS หากเกินกว่านี้ระบบต้องปฏิเสธคำขอ (Fail Fast) ทันทีเพื่อป้องกันระบบล่มทั้งยวง

## หมวดที่ 6: เมตริก, การคำนวณ Cardinality และพื้นที่จัดเก็บ TSDB

### 6.1 การคำนวณจำนวน Time Series รวม (Cardinality Multiplication)

$$\text{Total Series} = \prod_{i=1}^{m} |L_i| = |L_1| \times |L_2| \times \dots \times |L_m|$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{Total Series}$ | จำนวนเส้นกราฟข้อมูลเวลาทั้งหมดที่ Prometheus ต้องสร้างและดูแลใน RAM | เส้น (Time Series) |
| $|L_i|$ | จำนวนค่าที่เป็นไปได้ทั้งหมด (Cardinality) ของ Label ตัวที่ $i$ | จำนวนค่า (Values) |

**ตัวอย่างโจทย์สั้น:**
เมตริก `api_http_requests_total` มี Label พื้นฐานดังนี้:
- `method`: มี 4 ค่า (`GET`, `POST`, `PUT`, `DELETE`)
- `handler`: มี 25 เส้นทาง API
- `status`: มี 10 รหัสสถานะ HTTP
หากวิศวกรเผลอใส่ `user_id` ซึ่งมีผู้ใช้ $50,000$ คนเข้าไปเป็น Label เพิ่ม จงหาจำนวน Time Series ที่เกิดขึ้น

**วิธีคำนวณ:**
1. จำนวน Series ปกติ: $4 \times 25 \times 10 = 1,000 \text{ Series}$
2. เมื่อเพิ่ม `user_id`: $1,000 \times 50,000 = 50,000,000 \text{ Series}$ (50 ล้านเส้น)
*ตอบ:* จำนวน Series จะพุ่งขึ้นเป็น $50$ ล้านเส้น ทำให้ RAM ของ Prometheus หมดและเกิด OOM Killer Crash ทันที

---

### 6.2 การคำนวณพื้นที่จัดเก็บบนดิสก์ของ TSDB (Prometheus Disk Sizing)

$$\text{Disk Space} = \text{Total Series} \times \left( \frac{\text{Retention Seconds}}{\text{Scrape Interval Seconds}} \right) \times \text{Bytes per Sample}$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{Disk Space}$ | พื้นที่ฮาร์ดดิสก์ทั้งหมดที่ต้องจัดเตรียมไว้ | ไบต์ (Bytes) หรือ กิกะไบต์ (GB) |
| $\text{Total Series}$ | จำนวน Time Series ทั้งหมดที่ถูกจัดเก็บ | เส้น (Series) |
| $\text{Retention Seconds}$ | ระยะเวลาที่ต้องการเก็บข้อมูลย้อนหลัง (เช่น 15 วัน $= 1,296,000$ วินาที) | วินาที (Seconds) |
| $\text{Scrape Interval}$ | ความถี่ในการดึงข้อมูลตัวอย่าง (เช่น ทุกๆ 15 วินาที) | วินาที (Seconds) |
| $\text{Bytes per Sample}$ | ขนาดเฉลี่ยหลังบีบอัดข้อมูลต่อ 1 ตัวอย่าง (ตามสถิติ Prometheus $\approx 1.5$ Bytes) | ไบต์ต่อตัวอย่าง (Bytes/sample) |

**ตัวอย่างโจทย์สั้น:**
มี Time Series รวม $100,000$ เส้น ดึงข้อมูลทุก $15$ วินาที ต้องการเก็บข้อมูลย้อนหลัง $15$ วัน จงคำนวณขนาดพื้นที่ดิสก์ที่ต้องใช้

**วิธีคำนวณ (คิดในใจ):**
1. ใน 1 วันมี $86,400$ วินาที $\approx 86,000$ วินาที ดึงทุก 15 วินาที จะได้ประมาณ $86,000 / 15 \approx 5,760 \approx 6,000$ ครั้งต่อวัน
2. เก็บ 15 วัน: $6,000 \times 15 = 90,000$ ตัวอย่างต่อ 1 Series
3. จำนวนตัวอย่างรวม: $100,000 \times 90,000 = 9,000,000,000$ ตัวอย่าง ($9 \times 10^9$)
4. พื้นที่ดิสก์: $9 \times 10^9 \times 1.5 \text{ Bytes} = 13.5 \times 10^9 \text{ Bytes} \approx 13.5 \text{ GB}$
*ตอบ:* ต้องเตรียมพื้นที่ดิสก์ประมาณ $13.5$ ถึง $14$ GB

## หมวดที่ 7: ระบบไฟฟ้าตู้ Rack, กฎ De-rating 80% และกระแสกระชาก (Inrush Current)

### 7.1 กำลังไฟฟ้าและกฎการลดพิกัด 80% (PDU Electrical De-rating)

$$P_{\text{rated}} = V \times I_{\text{rated}}$$

$$I_{\text{continuous\_max}} = I_{\text{rated}} \times 0.80$$

$$P_{\text{usable}} = V \times I_{\text{continuous\_max}} = V \times (I_{\text{rated}} \times 0.80)$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $P_{\text{rated}}$ | กำลังไฟฟ้าสูงสุดตามสเปกของราง PDU | วัตต์ (Watts: W) |
| $V$ | แรงดันไฟฟ้ากระแสสลับมาตรฐาน (ประเทศไทยคือ 230V) | โวลต์ (Volts: V) |
| $I_{\text{rated}}$ | พิกัดกระแสไฟฟ้าสูงสุดของเบรกเกอร์ PDU (เช่น 16A หรือ 32A) | แอมแปร์ (Amperes: A) |
| $I_{\text{continuous\_max}}$ | กระแสไฟฟ้าสูงสุดที่อนุญาตให้ใช้งานต่อเนื่อง (กฎ 80% De-rating) | แอมแปร์ (Amperes: A) |
| $P_{\text{usable}}$ | กำลังไฟฟ้าต่อเนื่องสูงสุดที่ปลอดภัย | วัตต์ (W) หรือ กิโลวัตต์ (kW) |

**ตัวอย่างโจทย์สั้น:**
ตู้ Rack ติดตั้งรางไฟ PDU ขนาด $230\text{V} / 16\text{A}$ จงคำนวณกำลังไฟสูงสุดที่พิกัด และกำลังไฟต่อเนื่องที่ปลอดภัยตามมาตรฐานความปลอดภัยทางวิศวกรรม

**วิธีคำนวณ:**
1. กำลังไฟฟ้าตามพิกัด: $P_{\text{rated}} = 230\text{V} \times 16\text{A} = 3,680 \text{ Watts} \approx 3.7 \text{ kW}$
2. พิกัดกระแสต่อเนื่องสูงสุด (กฎ 80%): $16\text{A} \times 0.80 = 12.8 \text{A}$
3. กำลังไฟฟ้าต่อเนื่องที่ปลอดภัย: $230\text{V} \times 12.8\text{A} = 2,944 \text{ Watts} \approx 2.94 \text{ kW}$
*ตอบ:* พิกัดสูงสุดคือ $3,680$ W แต่ใช้งานจริงต่อเนื่องได้ไม่เกิน $12.8$ A หรือประมาณ $2,944$ W (ราว 3 kW)

---

### 7.2 กระแสกระชากขณะเริ่มเดินเครื่อง (Inrush Current Peak)

$$I_{\text{inrush\_total}} = \sum_{j=1}^{K} (k_{\text{inrush}} \times I_{\text{running}, j})$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $I_{\text{inrush\_total}}$ | กระแสไฟฟ้ารวมชั่วขณะตอนเปิดเครื่องพร้อมกันทั้งหมด | แอมแปร์ (A) |
| $k_{\text{inrush}}$ | ตัวคูณกระแสกระชากของภาคจ่ายไฟเซิร์ฟเวอร์ (เฉลี่ยอยู่ที่ $3$ ถึง $5$ เท่า) | ตัวคูณ (Unitless ratio) |
| $I_{\text{running}, j}$ | กระแสไฟฟ้าที่เครื่องเซิร์ฟเวอร์ตัวที่ $j$ ใช้งานในสภาวะปกติ | แอมแปร์ (A) |

**ตัวอย่างโจทย์สั้น:**
เซิร์ฟเวอร์ 8 เครื่อง แต่ละเครื่องกินกระแสไฟปกติ $1.5\text{A}$ เสียบอยู่บน PDU ขนาด $16\text{A}$ หากเกิดไฟดับแล้วไฟกลับมาพร้อมกัน (Cold Boot) โดยมีตัวคูณกระแสกระชาก $k = 4$ เท่า จงคำนวณกระแสกระชากรวมและระบุผลลัพธ์ที่จะเกิดขึ้น

**วิธีคำนวณ:**
1. กระแสใช้งานปกติรวม: $8 \times 1.5\text{A} = 12\text{A}$ (ผ่านเกณฑ์ De-rating 12.8A ในสภาวะปกติ)
2. กระแสกระชากตอนสตาร์ตพร้อมกัน: $12\text{A} \times 4 = 48\text{A}$
3. เปรียบเทียบกับพิกัดเบรกเกอร์: $48\text{A} > 16\text{A}$
*ตอบ:* กระแสกระชากพุ่งสูงถึง $48$ A ทำให้เบรกเกอร์ของ PDU ตัดวงจร (Trip) ทันที ต้องแก้ไขด้วยการตั้งค่าเปิดเครื่องแบบหน่วงเวลาเป็นขั้นบันได (Staggered Power-on Delay)

## หมวดที่ 8: อัตราส่วนการจองใช้เครือข่ายเกินพิกัด (Network Oversubscription Ratio)

### 8.1 อัตราส่วนการเชื่อมต่อสวิตช์ประจำตู้ (Top of Rack: ToR)

$$\text{Oversubscription Ratio} = \frac{\text{Total Downlink Bandwidth}}{\text{Total Uplink Bandwidth}} = \frac{N_{\text{ports}} \times B_{\text{down}}}{M_{\text{uplinks}} \times B_{\text{up}}}$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{Oversubscription}$ | อัตราส่วนแบนด์วิดท์ฝั่งเครื่องลูกข่ายเทียบกับแบนด์วิดท์ฝั่งขาขึ้นแกนหลัก | สัดส่วนต่อหนึ่ง ($X : 1$) |
| $N_{\text{ports}}$ | จำนวนพอร์ต Downlink ที่เสียบใช้งานจริงไปยังเซิร์ฟเวอร์ | พอร์ต (Ports) |
| $B_{\text{down}}$ | ความเร็วของพอร์ต Downlink แต่ละพอร์ต (เช่น 10 Gbps) | กิกะบิตต่อวินาที (Gbps) |
| $M_{\text{uplinks}}$ | จำนวนพอร์ต Uplink ที่เชื่อมต่อไปยัง Core/Spine Switch | เส้น/พอร์ต (Uplinks) |
| $B_{\text{up}}$ | ความเร็วของพอร์ต Uplink แต่ละพอร์ต (เช่น 40 Gbps) | กิกะบิตต่อวินาที (Gbps) |

**ตัวอย่างโจทย์สั้น:**
สวิตช์ ToR เชื่อมต่อเซิร์ฟเวอร์ 24 เครื่องด้วยพอร์ต $10\text{Gbps}$ มีสาย Uplink เชื่อมต่อขึ้น Core Switch จำนวน 2 เส้น ความเร็วเส้นละ $40\text{Gbps}$ จงหาอัตราส่วน Oversubscription ในสภาวะปกติ และในสภาวะที่สาย Uplink ขาดไป 1 เส้น ($N-1$)

**วิธีคำนวณ:**
1. แบนด์วิดท์ฝั่งเซิร์ฟเวอร์ (Downlink): $24 \times 10\text{Gbps} = 240\text{Gbps}$
2. สภาวะปกติ Uplink มี 2 เส้น: $2 \times 40\text{Gbps} = 80\text{Gbps}$
   $$\text{Ratio}_{\text{ปกติ}} = \frac{240}{80} = 3 : 1$$
3. สภาวะ $N-1$ เหลือ Uplink 1 เส้น: $1 \times 40\text{Gbps} = 40\text{Gbps}$
   $$\text{Ratio}_{N-1} = \frac{240}{40} = 6 : 1$$
*ตอบ:* สภาวะปกติมีอัตราส่วน $3:1$ แต่เมื่อเกิดเหตุขัดข้อง $N-1$ อัตราส่วนจะพุ่งเป็น $6:1$ ซึ่งอาจทำให้เกิดคอขวดและแพ็กเก็ตตกหล่นหากทราฟฟิกหนาแน่น

---

## หมวดที่ 9: ประสิทธิภาพการใช้พลังงานศูนย์ข้อมูล (PUE) และการสุ่ม Trace

### 9.1 ประสิทธิภาพการใช้พลังงาน (Power Usage Effectiveness: PUE)

$$\text{PUE} = \frac{\text{Total Facility Energy}}{\text{IT Equipment Energy}}$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{PUE}$ | ดัชนีประสิทธิภาพการใช้พลังงานของศูนย์ข้อมูล (ค่าอุดมคติคือ $1.0$) | ตัวคูณ (Unitless ratio, $\ge 1.0$) |
| $\text{Total Facility Energy}$ | พลังงานไฟฟ้าทั้งหมดที่จ่ายเข้าศูนย์ข้อมูล (รวมระบบแอร์ ชิลเลอร์ ไฟฟ้าส่องสว่าง UPS) | กิโลวัตต์-ชั่วโมง (kWh) |
| $\text{IT Equipment Energy}$ | พลังงานไฟฟ้าที่ถูกนำไปใช้เลี้ยงอุปกรณ์ประมวลผลจริง (เซิร์ฟเวอร์ สตอเรจ สวิตช์) | กิโลวัตต์-ชั่วโมง (kWh) |

**ตัวอย่างโจทย์สั้น:**
ห้อง Data Center จ่ายไฟฟ้ารวมทั้งหมด $150\text{ kW}$ โดยมีเซิร์ฟเวอร์และอุปกรณ์ไอทีดึงไฟใช้งานจริง $100\text{ kW}$ (ส่วนที่เหลือ $50\text{ kW}$ เสียไปกับระบบแอร์และไฟส่องสว่าง) จงคำนวณค่า PUE

**วิธีคำนวณ:**
$$\text{PUE} = \frac{150\text{ kW}}{100\text{ kW}} = 1.5$$
*ตอบ:* ค่า PUE เท่ากับ $1.5$ (หมายความว่า ทุกๆ 1 วัตต์ที่ส่งให้ไอที ต้องเสียไฟเพิ่มอีก 0.5 วัตต์ให้กับระบบอำนวยความสะดวก)

---

### 9.2 การสุ่มเก็บข้อมูลร่องรอยการทำงาน (Trace Sampling Rate)

$$\text{Ingested Traces} = (\text{Total Requests} \times R_{\text{normal}}) + (\text{Failed Requests} \times R_{\text{error}})$$

| ตัวแปร | ความหมาย | หน่วย |
| :--- | :--- | :--- |
| $\text{Ingested Traces}$ | ปริมาณ Trace ทั้งหมดที่ถูกส่งไปบันทึกบนระบบจัดเก็บ (เช่น Jaeger / Tempo) | รายการ (Traces) |
| $R_{\text{normal}}$ | อัตราการสุ่มคำขอปกติที่ไม่มี Error (เช่น $1\% = 0.01$) | สัดส่วน ($0-1$) |
| $R_{\text{error}}$ | อัตราการสุ่มคำขอที่มี Error หรือ Latency สูง (ตามหลัก Tail Sampling จะเก็บ $100\% = 1.0$) | สัดส่วน ($0-1$) |

**ตัวอย่างโจทย์สั้น:**
ระบบมีทราฟฟิก $1,000,000$ คำร้องต่อวัน มีอัตราข้อผิดพลาด $0.5\%$ ($5,000$ คำร้อง) หากใช้นโยบาย Tail Sampling โดยเก็บคำขอปกติ $1\%$ และเก็บคำขอผิดพลาด $100\%$ จงหาจำนวน Trace ที่ต้องบันทึกต่อวัน

**วิธีคำนวณ:**
1. คำขอปกติ: $995,000 \times 1\% = 9,950 \text{ Traces}$
2. คำขอที่มี Error: $5,000 \times 100\% = 5,000 \text{ Traces}$
3. รวม Trace ทั้งหมด: $9,950 + 5,000 = 14,950 \text{ Traces ต่อวัน}$
