# ข้อที่ 2: วินิจฉัยปัญหาประสิทธิภาพจากอาการที่คลุมเครือ (Performance Diagnosis)

- ผลลัพธ์การเรียนรู้ที่ครอบคลุม: SLO 3.1, 3.2, 3.3, 3.4
- สัปดาห์ที่เกี่ยวข้อง: สัปดาห์ที่ 3 (การวินิจฉัยระบบ, เมธอด USE/RED, คำสั่ง Linux, Little's Law, Cascading Failures)
- สัดส่วนคะแนน: 10 คะแนน (แนวคิด 4, ประยุกต์ 3, ทฤษฎี 2, สื่อสาร/เวลา 1)

## 1. แนวคิดหลักและทฤษฎีที่ต้องหยิบมาใช้ (Core Theory)

### 1.1 ลำดับขั้นการสืบค้นแบบ 2 ขา (RED สู่ USE)
- **เริ่มต้นที่มุมมองผู้ใช้งานด้วย RED Method** (Tom Wilkie):
  - **Rate**: ปริมาณคำร้องต่อวินาที (มี Traffic พุ่งผิดปกติหรือไม่)
  - **Errors**: อัตราคำร้องที่ล้มเหลว (หาก Error ยังเป็น 0 แสดงว่าระบบ "ช้า" ไม่ใช่ "พัง")
  - **Duration**: การกระจายตัวของเวลาตอบสนอง โดยดูที่ **p95 หรือ p99 Latency**
- **ไล่สถาปัตยกรรมจากบนลงล่าง (Top-Down Traversal)**:
  - ฝั่ง Web ปกติ $\rightarrow$ ฝั่ง API ค่า p99 พุ่งสูง $\rightarrow$ ฝั่ง Database ค่า p99 พุ่งสูงตาม $\rightarrow$ บ่งชี้ว่าคอขวดอยู่ที่ฐานข้อมูลหรือต่ำกว่านั้น
- **ตรวจสอบทรัพยากรเครื่องด้วย USE Method** (Brendan Gregg):
  - ตรวจสอบทรัพยากรหลัก 4 ชนิด: CPU, Memory, Disk I/O, Network
  - **Utilization**: ใช้งานไปกี่เปอร์เซ็นต์ (บอกว่าใช้ไปเท่าไหร่)
  - **Saturation**: มีงานรอคิวอยู่มากเพียงใด (บอกว่ากำลังจะพังหรือไม่)
  - **Errors**: มีข้อผิดพลาดในระดับฮาร์ดแวร์/ไดรเวอร์หรือไม่

### 1.2 ตารางคำสั่ง Linux Triage ที่ต้องระบุในคำตอบ
| คำสั่ง | สิ่งที่ตอบคำถาม | จุดที่ต้องสังเกตเป็นอันดับแรก |
| :--- | :--- | :--- |
| `uptime` หรือ `top` | ระบบมีงานค้างรอมากเพียงใด | ดู Load Average ย้อนหลัง 1, 5, 15 นาที เทียบกับจำนวน CPU Core (ถ้าเกิน แปลว่ามีคิวรอ) |
| `vmstat 1` | ซีพียูและหน่วยความจำกำลังอึดอัดหรือไม่ | ดูคอลัมน์ `r` (คิวรอ CPU) และคอลัมน์ `si`/`so` (การสลับหน้า Swap ไปมา) |
| `iostat -xz 1` | ดิสก์เป็นคอขวดหรือไม่ | ดู `%util` และค่าหน่วงเวลา `await` เทียบกับ `svctm` (ถ้า `await` สูงกว่ามาก แสดงว่าคิวหนาแน่น) |
| `ss -s` หรือ `ss -tin` | เครือข่ายมีปัญหาการเชื่อมต่อหรือไม่ | ดูจำนวน Connection ที่ค้าง, ค่า RTT, และอัตราการส่งซ้ำ (TCP Retransmit) |
| `dmesg -T \| tail` | เคอร์เนลตรวจพบความผิดปกติอะไร | ดูข้อความ OOM Killer, ข้อผิดพลาดของคอนโทรลเลอร์ดิสก์/RAID, ฮาร์ดแวร์รีเซ็ต |
| `pidstat 1` | กระบวนการใดที่แย่งใช้ทรัพยากร | เรียงลำดับตามการใช้งาน CPU และ I/O เพื่อหาโปรเซสต้นตอ |

### 1.3 ทฤษฎีแถวคอยและปรากฏการณ์ The Knee Curve
- **Little's Law**: $L = \lambda \times W$ (ปริมาณงานที่ค้างในระบบ $=$ อัตรางานที่เข้ามา $\times$ เวลาที่งานอยู่ในระบบ)
- เมื่อการใช้งานทรัพยากรเกิน 80% (จุด Knee) เวลาในการรอคิวจะไม่ได้เพิ่มขึ้นแบบเส้นตรง แต่จะพุ่งสูงขึ้นแบบกึ่งเอกซ์โพเนนเชียล ทำให้ระบบตอบสนองช้าลงกะทันหัน แม้โหลดจะเพิ่มขึ้นเพียงเล็กน้อย

### 1.4 ปรากฏการณ์ความล้มเหลวแบบลูกโซ่ (Cascading Failure)
- ฐานข้อมูลช้าเพียงตัวเดียว $\rightarrow$ เธรดในชั้น API ค้างรอจนเต็ม Connection Pool $\rightarrow$ ไคลเอนต์หน้าเว็บรอไม่ไหวเกิด Timeout $\rightarrow$ ผู้ใช้กดรีเฟรชซ้ำกลายเป็น Retry Storm $\rightarrow$ ทั้งระบบล่มสลาย
- *การแก้ไข*: ต้องมี Circuit Breaker, การตั้ง Timeout Budget ให้สั้นลงจากบนลงล่าง, และหลักการ "บรรเทาปัญหาก่อน แล้วค่อยหาสาเหตุที่แท้จริง" (Mitigate first, root-cause later)

## 2. โครงสร้างการตอบปากเปล่าภายใน 4 นาที (Speaking Structure)

1. **นาทีที่ 1: ตรวจสอบอาการและคัดแยกด้วย RED (Symptoms & RED Analysis)**
   - พูดถึงอาการที่โจทย์ให้ (เช่น ผู้ใช้บ่นว่าช้า) และอธิบายว่าต้องดู p99 Duration ก่อน เพื่อแยกว่าระบบช้าหรือระบบล่ม
   - ไล่สถาปัตยกรรมทีละชั้นเพื่อตีกรอบหาเซิร์ฟเวอร์เจ้าปัญหา
2. **นาทีที่ 2: วินิจฉัยเชิงลึกด้วย USE Method และคำสั่ง Linux (USE & Linux CLI)**
   - ระบุทรัพยากรที่สงสัย พร้อมยกคำสั่ง Linux อย่างน้อย 3-4 คำสั่ง (เช่น `iostat`, `vmstat`, `dmesg`)
   - เน้นย้ำความแตกต่างระหว่าง Utilization (ดูปกติ) กับ Saturation (คิวพุ่งสูง)
3. **นาทีที่ 3: เชื่อมโยงทฤษฎีแถวคอยและความล้มเหลวลูกโซ่ (Queueing & Cascading)**
   - อธิบาย Little's Law และ The Knee Curve (จุด 80%) ว่าทำไมคิวถึงระเบิด
   - เตือนเรื่องผลกระทบที่จะลามขึ้นชั้นบนผ่าน Retry Storm
4. **นาทีที่ 4: มาตรการบรรเทาผลกระทบและแผนแก้ไขระยะยาว (Mitigation & Action)**
   - เสนอทางแก้เฉพาะหน้าเพื่อลดโหลดทันที (เช่น ย้ายทราฟฟิกอ่านไป Read Replica, ทำ Load Shedding)
   - วางแผนแก้ปัญหาถาวรนอกเวลาทำงาน

## 3. ตัวอย่างบทพูดตอบข้อสอบที่ได้คะแนนเต็ม (Sample High-Scoring Transcript)

"สวัสดีครับอาจารย์ สำหรับข้อที่ 2 ในกรณีที่ได้รับแจ้งว่าระบบเริ่มมีอาการช้าลงตั้งแต่ช่วงเช้าโดยไม่มีข้อผิดพลาดปรากฏชัดเจน กระบวนการวินิจฉัยตามหลักวิศวกรรม SRE มีดังนี้ครับ

ในขั้นแรก เราต้องไม่เริ่มจากการเดาสุ่ม แต่ต้องเริ่มจากมุมมองของผู้ใช้งานด้วยเมธอด RED (Rate, Errors, Duration) ครับ เราจะตรวจสอบอัตราคำร้อง (Rate) และอัตราข้อผิดพลาด (Errors) ซึ่งถ้า Errors ยังต่ำ แปลว่าระบบไม่ได้พัง แต่เป็นปัญหาความหน่วงเวลา โดยเราต้องดูที่ค่าเปอร์เซ็นไทล์ p95 หรือ p99 Duration จากนั้นทำการไล่ตรวจสอบสถาปัตยกรรมทีละชั้น (Top-Down) หากพบว่าฝั่ง Web ทำงานปกติ แต่ค่า Latency ของฝั่ง API และ Database พุ่งสูงขึ้นตามกันอย่างมีนัยสำคัญ เราจะจำกัดขอบเขตของปัญหาไปที่ชั้นฐานข้อมูลทันทีครับ

ในขั้นที่สอง เมื่อเข้าสู่เครื่องฐานข้อมูล เราจะใช้เมธอด USE (Utilization, Saturation, Errors) ตรวจสอบทรัพยากรหลักทั้ง 4 ด้าน โดยใช้คำสั่ง Linux เฉพาะทาง:
1. ใช้คำสั่ง `uptime` หรือ `top` เพื่อดูค่า Load Average เทียบกับจำนวนคอร์ของ CPU
2. ใช้คำสั่ง `vmstat 1` เพื่อดูคอลัมน์ `r` ว่ามีโปรเซสรันรอคิว CPU หรือไม่ และดู `si`/`so` เพื่อตรวจสอบว่าเกิดปัญหาหน่วยความจำไม่พอจนต้องสลับหน้าข้อมูลลง Swap หรือไม่
3. ใช้คำสั่ง `iostat -xz 1` เพื่อตรวจดูดิสก์ หากพบว่าค่า `%util` สูงถึง 98% และค่าหน่วงเวลา `await` สูงกว่าค่า `svctm` มากๆ แสดงว่าปัญหาคอขวดเกิดจากดิสก์ I/O แน่นอนครับ
4. ใช้คำสั่ง `dmesg -T | tail` ตรวจสอบบันทึกเคอร์เนล เช่น การ์ด RAID Controller อาจตัดเข้าสู่โหมด Write-Through เนื่องจากแบตเตอรี่สำรองแคชเสื่อมสภาพ ทำให้การเขียนข้อมูลช้าลงทันทีสิบเท่า

ในแง่ของทฤษฎี สถานการณ์นี้อธิบายได้ด้วย ทฤษฎีแถวคอยและกฎของลิตเติล ($L = \lambda \times W$) ร่วมกับปรากฏการณ์ The Knee Curve ครับ เมื่อการใช้งานทรัพยากรเกินระดับ 80% คิวรอจะเพิ่มขึ้นแบบกึ่งเอกซ์โพเนนเชียล ส่งผลให้เธรดบนชั้น API ค้างรอและลุกลามกลายเป็น Cascading Failure และหากผู้ใช้พยายามกดย้ำๆ จะเกิดเป็น Retry Storm ซ้ำเติมระบบให้หยุดการทำงานได้

สำหรับแนวทางการแก้ไข เราต้องยึดหลัก 'บรรเทาผลกระทบก่อน แล้วค่อยแก้รากปัญหา' (Mitigate first, root-cause later) ครับ ในระยะสั้นเราสามารถตัดวงจรความล้มเหลวด้วยการใช้ Circuit Breaker, ย้ายทราฟฟิกคำสั่งอ่านข้อมูลไปยัง Read Replica เพื่อลดภาระของดิสก์ตัวหลัก หรือทำ Load Shedding ทิ้งคำขอที่ไม่สำคัญที่ขอบระบบ จากนั้นจึงวางแผนเปลี่ยนอุปกรณ์ฮาร์ดแวร์หรือปรับแต่งคอนฟิกนอกเวลาทำการต่อไปครับ"
