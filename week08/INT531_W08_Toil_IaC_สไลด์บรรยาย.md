## 2. งานที่ไร้คุณค่าระยะยาวคืออะไร และวัดอย่างไร (What is Toil and How to Measure It)

นิยามสำคัญของ **Toil**: คืองานปฏิบัติการที่เมื่อทำเสร็จสิ้นแล้ว ระบบไม่ได้มีพัฒนาการที่ดีขึ้นอย่างถาวร และยิ่งระบบมีขนาดเติบโตขึ้น ปริมาณงานประเภทนี้จะยิ่งเพิ่มขึ้นเป็นสัดส่วนเชิงเส้น (Linear Scaling)

### 2.1 หกลักษณะของ Toil (Six Characteristics of Toil)
งานใดก็ตามที่มีลักษณะตรงกับ 6 ข้อนี้ ยิ่งตรงหลายข้อ ยิ่งจัดว่าเป็น Toil ในระดับสูง:

| ลักษณะของงาน (Characteristic) | ความหมายทางวิศวกรรม | ตัวอย่างจริงจากห้องปฏิบัติการของหลักสูตร |
| :--- | :--- | :--- |
| **ทำด้วยมือ (Manual)** | ต้องใช้มนุษย์ลงมือคลิก พิมพ์ หรือดำเนินการด้วยตัวเอง | นั่งพิมพ์เลขรหัสครุภัณฑ์ลงสเปรดชีตทีละบรรทัด |
| **ทำซ้ำซาก (Repetitive)** | ต้องทำขั้นตอนเดิมซ้ำเรื่อยๆ ไม่ใช่งานที่ทำครั้งเดียวจบ | คลิกสร้างเครื่องเสมือน (VM) ทีละกลุ่มจนครบ 20 กลุ่ม |
| **เครื่องทำแทนได้ (Automatable)** | มีตรรกะชัดเจนจนสามารถเขียนโปรแกรมให้เครื่องจักรทำแทนได้ | ตั้งค่า Virtual LAN (VLAN) ให้พอร์ตสวิตช์ตามตารางที่มีอยู่แล้ว |
| **เชิงรับ/แก้ปัญหาเฉพาะหน้า (Tactical)** | ตอบสนองต่อเหตุการณ์ที่เกิดขึ้นเฉพาะหน้า ขาดการวางแผนปรับปรุงโครงสร้าง | การรีสตาร์ตบริการที่ค้างอยู่ทุกเช้า |
| **ไม่มีคุณค่าคงทนยาวนาน (No enduring value)** | ทำเสร็จแล้วระบบไม่ได้มีความทนทาน เสถียรภาพ หรือประสิทธิภาพดีขึ้นกว่าเดิม | การคอยลบไฟล์ล็อกหรือเคลียร์ดิสก์ที่เต็มซ้ำๆ ทุกสัปดาห์ |
| **ขยายตัวตามขนาดระบบ (Scales with service)** | เมื่อระบบขยายตัวขึ้น ปริมาณงานจะเพิ่มขึ้นตามขนาดระบบทันที | เมื่อมีเครื่องเซิร์ฟเวอร์เพิ่มหนึ่งเครื่อง ปริมาณงานตั้งค่าก็เพิ่มขึ้นอีกหนึ่งชุด |

### 2.2 เพดาน 50% ของเวลาทำงานทีม (50% Toil Budget Ceiling)
อ้างอิงตามหลักการของ Google SRE (*Site Reliability Engineering Book, บทที่ 5*):
- **กฎเกณฑ์**: งานประเภท Toil ควรกินเวลาของทีมวิศวกร SRE **ไม่เกิน 50%** ของเวลาทำงานทั้งหมด
- เวลาที่เหลืออย่างน้อย 50% ต้องถูกนำไปใช้ในงานวิศวกรรมจริง (Engineering Work) เช่น การพัฒนาระบบอัตโนมัติ, การปรับปรุงสถาปัตยกรรม, การเพิ่มเสถียรภาพ และการขจัดสาเหตุรากเหง้าของปัญหา

```
[สัดส่วนเวลาทำงานของทีม SRE ตามมาตรฐาน Google]

ทีม ก: [====== Toil 35% ======][============= งานวิศวกรรม 65% =============] -> ปกติ มีเวลาทำงานอัตโนมัติ
ทีม ข: [========= Toil 50% =========][========= งานวิศวกรรม 50% =========] -> แตะเพดานพอดี
ทีม ค: [============ Toil 75% ============][== งานวิศวกรรม 25% ==] -> วิกฤต Toil กำลังกลืนกินทีม
                              ^
                       เพดาน 50% ที่ Google กำหนด
```

> **ข้อคิดทางวิศวกรรม**: ถ้าเวลา Toil เกินครึ่งหนึ่งของทีม ปริมาณ Toil จะขยายตัวเร็วกว่าความสามารถที่มนุษย์ในทีมจะสร้างระบบอัตโนมัติขึ้นมาทดแทนได้ทัน เพราะทุกๆ เครื่องเซิร์ฟเวอร์และบริการที่เพิ่มเข้ามาในระบบ จะพ่วงเอาภาระ Toil ใหม่เข้ามาด้วยเสมอ จนทีมกลายสภาพเป็นฝ่ายสนับสนุนที่คอยดับเพลิงไปวันๆ (Ticket-driven Ops)

### 2.3 การคำนวณความคุ้มทุนในการทำอัตโนมัติ (Payback ROI Calculation)
ในการทำงานจริง การทำระบบอัตโนมัติมีต้นทุนในการพัฒนา (Engineering Cost) จึงต้องมีการวิเคราะห์ความคุ้มทุน โดยเน้นที่ **"วิธีคิดและสมมติฐาน"** ไม่ใช่ตัวเลขตายตัว

#### กรณีศึกษาตัวอย่าง: การสร้างและดูแลเครื่องเสมือน (VM) 20 เครื่องสำหรับ 20 กลุ่มนักศึกษาทุกภาคการศึกษา

```
ตารางการเปรียบเทียบต้นทุนเวลา (Payback Analysis):

1. เวลาที่ทำด้วยมือต่อรอบ:
   = 15 นาทีต่อกลุ่ม x 20 กลุ่ม
   ≈ 5 ชั่วโมงต่อรอบ

2. ความถี่ในการดำเนินการ:
   = สร้างใหม่ต้นภาคการศึกษา + แก้ไข/ปรับแต่งระหว่างภาคการศึกษา
   ≈ 4 รอบต่อปี

3. เวลาที่สูญเสียจากการทำด้วยมือต่อปี (Manual Cost):
   = 5 ชั่วโมง x 4 รอบ
   ≈ 20 ชั่วโมงต่อปี

4. เวลาลงทุนสร้างโค้ดอัตโนมัติครั้งแรก (Initial Investment):
   = เขียนโค้ด OpenTofu/Ansible + ทดสอบความถูกต้อง + เขียนเอกสาร
   ≈ 12 ชั่วโมง

5. ต้นทุนเวลาในการดูแลรักษาโค้ดต่อปี (Ongoing Maintenance):
   = อัปเดตเวอร์ชันซอฟต์แวร์ และแก้ไขเมื่อมีการเปลี่ยนต้นแบบระบบปฏิบัติการ
   ≈ 4 ชั่วโมงต่อปี
```

**ผลลัพธ์การวิเคราะห์**:
- ในปีแรก: ใช้เวลาสร้างโค้ดและบำรุงรักษา $12 + 4 = 16$ ชั่วโมง ซึ่งน้อยกว่าการทำด้วยมือที่ต้องใช้ถึง $20$ ชั่วโมง ทำให้ **"คุ้มทุนตั้งแต่ปีแรก (Payback within Year 1)"**
- ในปีถัดไป: ประหยัดเวลาได้ถึง $20 - 4 = 16$ ชั่วโมงต่อปี
- **มิติที่สำคัญกว่าเวลา**: คือ **"ความสม่ำเสมอถูกต้อง 100% (Consistency & Reproducibility)"** เพราะเครื่องเสมือนทั้ง 20 เครื่องจะถูกสร้างขึ้นมาเหมือนกันทุกประการตามสเปก ซึ่งการคลิกสร้างด้วยมือไม่มีทางรับประกันความถูกต้องได้โดยปราศจาก Human Error

## 3. บันไดห้าขั้นของการทำอัตโนมัติ (Five Levels of Automation Ladder)

วิวัฒนาการของการพัฒนาระบบปฏิบัติการมีลักษณะเป็นลำดับขั้น ยิ่งไต่ระดับสูงขึ้น Toil จะลดลงอย่างมหาศาล แต่วงความเสียหายเมื่อเกิดข้อผิดพลาด (Blast Radius) จะยิ่งกว้างขึ้นและเกิดความเสียหายรวดเร็วขึ้นเป็นเงาตามตัว

### 3.1 ลำดับขั้นจาก Manual สู่ Autonomous

```
[บันได 5 ขั้นของการทำอัตโนมัติ vs วงความเสียหาย]

ขั้นที่ 5: Autonomous (ระบบทำงานเองทั้งหมดตามเงื่อนไขหรือการตรวจจับ)
           |-- ความเสี่ยง: เกิดความผิดพลาดพร้อมกันทุกเครื่องทันที (กรณี CrowdStrike 2024)
ขั้นที่ 4: Self-service (ผู้ใช้สั่งงานผ่านพอร์ทัล มีระบบตรวจสอบเงื่อนไขก่อนลงมือจริง)
           |-- จุดเปลี่ยน: มี Guardrails ตรวจสอบ Input ก่อนยอมให้คำสั่งทำงาน
ขั้นที่ 3: Scripted (มนุษย์เป็นคนสั่งรันสคริปต์ และส่งค่าตัวแปรเข้าไปเอง)
           |-- ความเสี่ยง: คนป้อนพารามิเตอร์ผิดเพียงตัวเดียว ลามทั้งระบบ (กรณี AWS S3 2017)
ขั้นที่ 2: Documented (มีเอกสารและคู่มือปฏิบัติการ Runbook เป็นลายลักษณ์อักษร)
ขั้นที่ 1: Manual (ทำตามความจำและทักษะเฉพาะตัวของวิศวกร)

<< ยิ่งขั้นสูง Toil ยิ่งลด แต่วงความเสียหาย (Blast Radius) ยิ่งกว้าง >>
```

- **ช่วงหัวเลี้ยวหัวต่อสำคัญ**: รอยต่อจาก **ขั้นที่ 3 (Scripted) ไปยัง ขั้นที่ 4 (Self-service)** คือจุดที่ต้องเริ่มใส่ **"กลไกการตรวจสอบ (Validation & Safeguards)"** อย่างเข้มงวด เพราะสคริปต์ที่รันโดยไม่มีการตรวจสอบคือเครื่องมือเร่งความฉิบหายให้เกิดเร็วขึ้น

---

### 3.2 กลไกป้องกัน 5 ประการที่สคริปต์ต้องมี (Five Script Safeguards)
การทำระบบอัตโนมัติโดยไม่มีกลไกป้องกัน คือการทำให้ระบบพังพินาศได้เร็วขึ้นและกว้างขึ้น วิศวกรจึงต้องบรรจุกลไก 5 ประการนี้ลงในระบบอัตโนมัติทุกชุด:

1. **ทดสอบผลลัพธ์จำลองก่อนลงมือจริงเสมอ (Dry Run Mode)**:
   - สคริปต์ต้องสามารถแสดงส่วนต่างของการเปลี่ยนแปลง (Diff) ให้มนุษย์ตรวจสอบก่อนแก้ไขระบบจริง
   - *ตัวอย่างเครื่องมือ*: คำสั่ง `tofu plan` ใน OpenTofu หรือคำสั่ง `ansible-playbook --check --diff` ใน Ansible
2. **จำกัดขอบเขตความเสียหายสูงสุด (Blast Radius Limit)**:
   - กำหนดเพดานจำนวนโหนดหรือทรัพยากรสูงสุดที่อนุญาตให้คำสั่งแก้ไขหรือทำลายได้ในหนึ่งครั้ง เช่น อนุญาตให้ปิดเครื่องได้ไม่เกินครั้งละ 5 เครื่อง หากพารามิเตอร์ส่งผลเกินกว่านี้ ระบบต้องตัดการทำงานและส่งเสียงเตือนถามยืนยัน
3. **ทยอยดำเนินการเป็นรอบ (Staged / Canary Rollout)**:
   - ดำเนินการกับเครื่องนำร่อง 1 เครื่องก่อน เฝ้าดูผลลัพธ์และตัวชี้วัดความเสถียร จากนั้นจึงค่อยๆ ทยอยขยายไปยังเครื่องชุดถัดไป ห้ามรันคำสั่งแก้ไขทุกเครื่องพร้อมกันในเสี้ยววินาที
4. **ยืนยันเป้าหมายและสภาพแวดล้อมให้ชัดเจนก่อนลงมือ (Target & Environment Confirmation)**:
   - แสดงชื่อเครื่อง สภาพแวดล้อม (Production vs Staging) และพารามิเตอร์วิกฤตบนหน้าจอให้เห็นชัดเจน ก่อนจะเรียกใช้คำสั่งที่ไม่สามารถย้อนกลับได้ (Irreversible Commands)
5. **ทดสอบตัวกลไกป้องกันอย่างสม่ำเสมอ (Test the Safeguards Themselves)**:
   - ตัวกลไกป้องกันก็คือซอฟต์แวร์ที่มีโอกาสแฝงบั๊กได้เช่นกัน ดังกรณีศึกษาของ Facebook ปี 2564 ที่ตัวตรวจสอบคำสั่งมีข้อผิดพลาดเสียเองจนยอมให้คำสั่งที่ถอนเส้นทางเครือข่าย BGP หลุดเข้าไปทำงาน

## 4. หลักการของโครงสร้างพื้นฐานในรูปแบบโค้ด (IaC Principles)

ปรัชญาพื้นฐานของ Infrastructure as Code: **"เขียนระบุสภาพปลายทางที่ต้องการ แล้วปล่อยให้เครื่องมือค้นหาเส้นทางเพื่อไปถึงสภาพนั้นด้วยตัวเอง"**

### 4.1 สั่งแบบขั้นตอน vs สั่งแบบบอกผลลัพธ์ (Imperative vs Declarative)

```
เปรียบเทียบคำสั่งสองรูปแบบในการสร้างเครื่องเสมือน (VM) กลุ่มที่ 1:

[Imperative — สั่งบอกขั้นตอนทีละสเต็ป]
--------------------------------------------------------------------------------
# สคริปต์ต้องระบุขั้นตอนตามลำดับอย่างละเอียด
qm clone 9000 101 --name int531-g01
qm set 101 --cores 4 --memory 8192
qm set 101 --net0 virtio,bridge=vmbr0,tag=101
qm start 101
# ...จากนั้นต้องเขียนซ้ำแบบเดิมอีก 19 รอบ และภาวนาไม่ให้พิมพ์ ID ผิดพลาด
--------------------------------------------------------------------------------
ข้อจำกัด:
- วิศวกรต้องจำลำดับขั้นตอนเองทั้งหมด
- หากสั่งรันซ้ำ คำสั่ง clone จะล้มเหลวเพราะเครื่อง ID 101 มีอยู่แล้ว
- การวนทำ 20 รอบ เท่ากับเปิดโอกาสให้เกิดการพิมพ์ผิด 20 ครั้ง


[Declarative — สั่งบอกสภาพปลายทางที่ต้องการ]
--------------------------------------------------------------------------------
# ระบุเพียงสภาพสุดท้าย (End State) ที่ต้องการให้เป็น
resource "proxmox_vm_qemu" "group" {
  for_each = var.groups
  cores    = 4
  memory   = 8192
  # ... สเปกเครือข่ายและระบบจัดเก็บข้อมูล
}
# ปล่อยให้เครื่องมือ (Tooling) คำนวณความต่างและดำเนินการเอง
--------------------------------------------------------------------------------
จุดเด่น:
- เครื่องมือจะเปรียบเทียบสภาพจริงปัจจุบันกับสภาพที่ประกาศไว้ในโค้ด
- ลงมือทำเฉพาะส่วนที่ยังขาดหรือส่วนที่แตกต่าง
- รันซ้ำกี่ครั้งก็ได้ผลลัพธ์ปลายทางที่ถูกต้องเท่าเดิมเสมอ
```

---

### 4.2 คุณสมบัติความไม่เปลี่ยนรูปเมื่อทำซ้ำ (Idempotency)
**Idempotency** คือคุณสมบัติของระบบหรือคำสั่ง ที่ไม่ว่าจะถูกสั่งให้ทำงานซ้ำกี่ครั้งก็ตาม ผลลัพธ์สุดท้ายของระบบจะยังคงเหมือนเดิมทุกประการ และไม่ทำให้เกิดผลข้างเคียงที่ไม่พึงประสงค์เพิ่มเติม

```
ตัวอย่างผลการรัน Ansible Playbook สองรอบ:

$ ansible-playbook -i hosts.ini web.yml        # การรันรอบที่ 1
TASK [install nginx] ************************* changed: [g01]
TASK [deploy site config] ******************** changed: [g01]
TASK [enable and start nginx] **************** changed: [g01]
PLAY RECAP  g01 : ok=4  changed=3  unreachable=0  failed=0

$ ansible-playbook -i hosts.ini web.yml        # การรันรอบที่ 2 (ทันทีหลังจากรอบแรก)
TASK [install nginx] ************************* ok: [g01]
TASK [deploy site config] ******************** ok: [g01]
TASK [enable and start nginx] **************** ok: [g01]
PLAY RECAP  g01 : ok=4  changed=0  unreachable=0  failed=0
```

> **หัวใจสำคัญของการตรวจรับ Lab 6**: ในการรันรอบที่สอง ค่าตัวแปร `changed=0` คือเครื่องพิสูจน์คุณสมบัติ Idempotency อย่างแท้จริง หากการรันรอบสองยังคงมีค่า `changed > 0` แสดงว่ามีคำสั่งหรือทาสก์ที่แฝงพฤติกรรม Non-idempotent อยู่ ซึ่งขัดกับหลักการ SRE

### 4.3 สถานะและการเบี่ยงเบนของระบบ (State and Drift)
- **State File (ไฟล์สถานะ)**: คือฐานข้อมูลที่บันทึกความสัมพันธ์ระหว่าง "โค้ดที่ประกาศไว้" กับ "ทรัพยากรจริงที่มีอยู่บนระบบคลาวด์/ไฮเปอร์ไวเซอร์"
  - *กฎความปลอดภัย*: ต้องเก็บ State File ไว้ที่ศูนย์กลาง (Remote Backend เช่น S3, Consul หรือ GitLab Managed State), ต้องเปิดระบบป้องกันการทำงานชนกัน (State Locking) และ **ห้ามคอมมิต State File ลงใน Git เด็ดขาด** เพราะภายในไฟล์อาจมีข้อมูลความลับ (Secrets) เช่น รหัสผ่านหรือคีย์ชั่วคราว
- **Configuration Drift (การเบี่ยงเบนของการตั้งค่า)**: ปรากฏการณ์ที่ทรัพยากรจริงในระบบมีสภาพไม่ตรงกับโค้ด ซึ่งมักเกิดจากการที่มีมนุษย์แอบเข้าไปคลิกแก้ไขด้วยมือผ่านเว็บคอนโซล

```
[ตัวอย่างการตรวจจับ Drift ด้วย OpenTofu]
โค้ดระบุ: 4 Cores, 8 GB RAM
แต่มีผู้ดูแลระบบแอบไปเพิ่มสเปกใน Proxmox Web UI เป็น 8 Cores, 16 GB RAM

$ tofu plan
proxmox_vm_qemu.group["g07"]: Refreshing state...

# proxmox_vm_qemu.group["g07"] will be updated in-place
~ resource "proxmox_vm_qemu" "group" {
    name   = "int531-g07"
  ~ memory = 16384 -> 8192
  ~ cores  = 8 -> 4
}

Plan: 0 to add, 1 to change, 0 to destroy.
# เครื่องมือแจ้งเตือนความต่างทันที และพร้อมจะปรับสภาพกลับมาให้ตรงกับโค้ดต้นฉบับ
```

---

### 4.4 โครงสร้างพื้นฐานแบบปรับเปลี่ยนได้ vs แบบไม่เปลี่ยนแปลง (Mutable vs Immutable Infrastructure)

| มิติการเปรียบเทียบ | โครงสร้างพื้นฐานแบบปรับเปลี่ยนได้ (Mutable) | โครงสร้างพื้นฐานแบบไม่เปลี่ยนแปลง (Immutable) |
| :--- | :--- | :--- |
| **วิธีการปรับปรุงระบบ** | ล็อกอินเข้าไปอัปเดตแพ็กเกจหรือแก้คอนฟิกบนเครื่องเดิมที่กำลังเปิดใช้งานอยู่ | สร้างเครื่องใหม่ขึ้นมาจาก Image ต้นแบบรุ่นใหม่ล่าสุด แล้วสลับทราฟฟิกมาเครื่องใหม่ |
| **ความสม่ำเสมอของเครื่อง** | แต่ละเครื่องจะค่อยๆ มีคอนฟิกผิดเพี้ยนไปทีละนิดตามกาลเวลา (Snowflake Servers) | ทุกเครื่องในระบบถูกรับประกันว่าเหมือนกัน 100% ตามต้นแบบ |
| **ความยากง่ายในการย้อนกลับ (Rollback)** | ย้อนกลับยากมาก เพราะไม่รู้แน่ชัดว่าสภาพเดิมก่อนหน้ามีแพ็กเกจและคอนฟิกอะไรอยู่ | ย้อนกลับง่ายและรวดเร็ว เพียงแค่เปลี่ยนสลับการชี้กลับไปยังเครื่องหรือ Image รุ่นก่อนหน้า |
| **การจัดการข้อมูล (Data Persistence)** | ข้อมูลมักปะปนอยู่บนเครื่องเซิร์ฟเวอร์ | ต้องแยกพื้นที่เก็บข้อมูล (Persistent Storage/DB) ออกจากตัวเครื่องประมวลผลอย่างเด็ดขาด |
| **ความเหมาะสมในการใช้งาน** | เหมาะกับเครื่องเซิร์ฟเวอร์แบบดั้งเดิมที่สร้างใหม่ได้ยาก | เป็นหัวใจของระบบ Cloud-Native, Virtual Machines และ Containers |

> **บทเรียนราคาแพงระดับโลก - กรณี Knight Capital ปี 2555 (2012)**: วิศวกรนำโค้ดใหม่ไปติดตั้งด้วยมือบนเครื่องเซิร์ฟเวอร์จำนวน 8 เครื่อง แต่ทำสำเร็จเพียง 7 เครื่อง โดยหลงลืมเครื่องที่ 8 ทำให้เครื่องที่แปดยังคงรันโค้ดเก่าที่นำฟังก์ชันเดิมมาใช้ใหม่โดยไม่ได้ตั้งใจ จนส่งคำสั่งซื้อขายหุ้นผิดพลาดเข้าสู่ตลาดหลักทรัพย์ คิดเป็นมูลค่าความเสียหาย **460 ล้านดอลลาร์สหรัฐ ภายในเวลาเพียง 45 นาที** และทำให้บริษัทล้มละลายในเวลาต่อมา

## 5. ตัวอย่างการประยุกต์ใช้งานและเครื่องมือ (Tools and Practical Implementations)

### 5.1 บทบาทของเครื่องมือในสายธาร IaC (Tool Ecosystem)
การสร้างและจัดการโครงสร้างพื้นฐานยุคใหม่แบ่งแยกหน้าที่ของเครื่องมืออย่างชัดเจน:

| หน้าที่การทำงาน | เครื่องมือยอดนิยม | วัตถุประสงค์และกรณีการใช้งาน |
| :--- | :--- | :--- |
| **สร้างทรัพยากร (Provisioning)** | OpenTofu, Terraform, Pulumi | สร้างเครื่องเสมือน (VM), เครือข่าย (VLAN/Subnet), และระบบจัดเก็บข้อมูล (Storage) ให้มีอยู่ตามที่เขียนไว้ |
| **ตั้งค่าภายในเครื่อง (Configuration)** | Ansible, cloud-init | ติดตั้งแพ็กเกจซอฟต์แวร์, จัดวางไฟล์คอนฟิกูเรชัน, และสั่งเปิดการทำงานของเซอร์วิส |
| **สร้างต้นแบบเครื่อง (Image Building)** | Packer | ประกอบ Image/Template มาตรฐานของระบบปฏิบัติการที่มีการอัปเดตความปลอดภัยเตรียมไว้ล่วงหน้า |
| **จัดเก็บความลับ (Secrets Management)** | OpenBao, HashiCorp Vault, SOPS | จัดเก็บรหัสผ่าน, API Tokens, และใบรับรอง TLS โดยแยกออกจากโค้ดอย่างเด็ดขาด |
| **ตรวจโค้ดก่อนนำไปใช้ (Scanning & Linting)** | Checkov, tflint, ansible-lint | สแกนหาช่องโหว่ความปลอดภัย, พฤติกรรมเสี่ยง, และข้อผิดพลาดทางไวยากรณ์ก่อนขึ้นระบบจริง |

### 5.3 ตัวอย่างแอปพลิเคชันที่ 1: สร้าง VM 20 กลุ่มด้วย OpenTofu บน Proxmox VE
ตัวอย่างโค้ดภาษา HCL ในการสร้างเครื่องเสมือนจำนวน 20 กลุ่ม พร้อมการแท็กเครือข่าย VLAN 101–120 แยกขาดจากกัน:

```hcl
# กำหนดตัวแปรสำหรับสร้างกลุ่ม g01 ถึง g20 พร้อมแมป VLAN 101 ถึง 120
variable "groups" {
  type = map(number)
  default = {
    for i in range(1, 21) :
    format("g%02d", i) => 100 + i
  }
}

# ทรัพยากรสร้าง VM สำหรับแต่ละกลุ่ม
resource "proxmox_vm_qemu" "group" {
  for_each    = var.groups
  name        = "int531-${each.key}"
  target_node = "pve01"
  clone       = "ubuntu-24-template"
  cores       = 4
  memory      = 8192

  network {
    model  = "virtio"
    bridge = "vmbr0"
    tag    = each.value # VLAN 101 ถึง 120 ถูกผูกให้แต่ละกลุ่มอัตโนมัติ
  }
}
```

**คำอธิบายกลไกสำคัญในโค้ด**:
1. `for_each = var.groups`: โค้ดชุดเดียววนสร้าง 20 เครื่องเหมือนกันทุกประการ ตัดปัญหาการก็อปปี้โค้ดซ้ำซ้อน
2. `tag = each.value`: ผูกกลุ่มที่ 1 เข้ากับ VLAN 101 ไล่ไปจนถึงกลุ่มที่ 20 บน VLAN 120 อย่างแม่นยำตามตารางแผนผังเครือข่าย
3. `clone = "ubuntu-24-template"`: ทุกกลุ่มเริ่มต้นจากโกลเด้นอิมเมจเดียวกัน จึงมีความเสถียรเท่าเทียมกัน
4. **ไม่มีการฮาร์ดโค้ดรหัสผ่าน**: ข้อมูลการยืนยันตัวตนกับ Proxmox จะถูกส่งผ่านตัวแปรสภาพแวดล้อม (Environment Variables) เสมอ

### 5.4 ตัวอย่างแอปพลิเคชันที่ 2: ติดตั้งและตั้งค่า Web Server ด้วย Ansible
ตัวอย่างไฟล์ `web.yml` ที่ยึดมั่นในหลักการ Idempotency โดยหลีกเลี่ยงการใช้คำสั่ง shell โดยตรง:

```yaml
- name: web server for each group
  hosts: groups
  become: true
  tasks:
    - name: install nginx
      ansible.builtin.apt:
        name: nginx
        state: present

    - name: deploy site config
      ansible.builtin.template:
        src: site.conf.j2
        dest: /etc/nginx/sites-enabled/default
      notify: reload nginx

    - name: enable and start nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
```

**หลักการทำงานที่ทำให้เกิด Idempotency**:
- `state: present`: ตรวจสอบก่อน หากแพ็กเกจถูกติดตั้งอยู่แล้วจะไม่ทำอะไรซ้ำ หากยังไม่มีจึงจะทำการติดตั้ง
- `ansible.builtin.template`: จะเขียนไฟล์ทับเฉพาะเมื่อเนื้อหาในเทมเพลตมีส่วนต่างจากไฟล์ปลายทางเท่านั้น
- `notify` และ `handlers`: คำสั่งรีโหลด Nginx จะถูกกระตุ้นให้ทำงานเฉพาะเมื่อไฟล์คอนฟิกมีการเปลี่ยนแปลงเนื้อหาจริงเท่านั้น หากไม่มีการเปลี่ยนคอนฟิก เซอร์วิสจะไม่ถูกรบกวนเลย
- **เหตุผลที่ไม่ใช้โมดูล shell**: เพราะคำสั่งแบบเชลล์ไม่สามารถรับรู้สถานะภายในของระบบได้เอง ทำให้ต้องรันคำสั่งซ้ำทุกรอบและทำลายคุณสมบัติ Idempotency

### 5.5 ตัวอย่างแอปพลิเคชันที่ 3: เส้นทางจากโค้ดสู่ระบบจริง (Safe Deployment Pipeline)
หัวใจที่ทำให้ IaC มีความปลอดภัยกว่าการคลิกผ่านหน้าเว็บ ไม่ใช่เพราะมันถูกเขียนเป็นไฟล์โค้ด แต่เป็นเพราะ **"กระบวนการทบทวนและตรวจสอบก่อนถูกนำไปใช้งานจริง (Peer Review & Gatekeeping)"**

```
[สายธารการส่งมอบโครงสร้างพื้นฐานอย่างปลอดภัย: 5 ขั้นตอน]

[1. Commit] -> [2. Plan] -> [3. Review] -> [4. Apply] -> [5. Verify]
```

1. **Commit**: วิศวกรแก้ไขไฟล์ `.tf` บน Git Feature Branch ของตนเอง
2. **Plan**: ระบบ CI/CD ทำงานอัตโนมัติ รันคำสั่ง `tofu plan` แล้วส่งผลสรุปการเปลี่ยนแปลง (Diff) แนบลงใน Pull Request
3. **Review**: วิศวกรอีกคนเข้ามาอ่านผลลัพธ์ plan ตรวจสอบความถูกต้องและผลกระทบ (ไม่ใช่แค่อ่านโค้ด แต่ดูว่ากระทบทรัพยากรใดบ้าง)
   - *มาตรฐานการควบคุม*: Pull Request ที่แนบผล plan ทำหน้าที่เป็น **"ใบขออนุมัติการเปลี่ยนแปลง (Change Authorization Request)"** ในตัวอย่างสมบูรณ์ สอดคล้องตามข้อกำหนดมาตรฐานความปลอดภัย **ISO/IEC 27001:2022 ข้อควบคุม A.8.32 (Change Management)** โดยเก็บบันทึกประวัติชัดเจนว่าใครเปลี่ยน อะไร เมื่อไหร่ เพราะเหตุใด
4. **Apply**: ระบบ CI/CD ดำเนินการรัน apply **เฉพาะผล plan ฉบับที่ผ่านการอนุมัติแล้วเท่านั้น**
   - *กฎเหล็ก*: **ห้ามวิศวกร apply โค้ดตรงจากแล็ปท็อปของตนเองเด็ดขาด** เพื่อป้องกันสภาวะความลับรั่วไหลและการแก้ไขที่ไม่ผ่านการตรวจสอบ
5. **Verify**: ระบบมอนิเตอร์ทำการตรวจสอบค่าตัวชี้วัด เช่น `up == 1` บน Prometheus/Grafana แดชบอร์ด เพื่อยืนยันว่าบริการกลับมาออนไลน์อย่างสมบูรณ์

### 5.6 การจัดการความลับไม่ให้อยู่ในโค้ด (Secrets Management)
จากงานวิจัยเชิงประจักษ์เรื่อง *"The Seven Sins: Security Smells in Infrastructure as Code Scripts"* (การประชุมวิชาการนานาชาติ ICSE 2019):
- ผู้วิจัยตรวจพบการ **ฮาร์ดโค้ดรหัสผ่านและคีย์ลับฝังอยู่ในไฟล์ IaC ถึง 1,326 จุด** และที่เลวร้ายที่สุดคือความลับเหล่านั้น **คงค้างอยู่ในระบบเฉลี่ยยาวนานถึง 98 เดือน (มากกว่า 8 ปี)**

```hcl
# รูปแบบที่พบได้บ่อยและเป็นข้อห้ามเด็ดขาด (Insecure Pattern - DO NOT USE)
provider "proxmox" {
  pm_api_url  = "https://10.20.250.11:8006/api2/json"
  pm_user     = "root@pam"
  pm_password = "Int531@2026" # ห้ามฝังรหัสผ่านลงในโค้ดอย่างเด็ดขาด
}

# รูปแบบที่ถูกต้องตามหลักความมั่นคงปลอดภัย (Secure Pattern)
provider "proxmox" {
  pm_api_url = var.pm_api_url
  # ข้อมูลยืนยันตัวตนให้อ่านผ่านตัวแปรสภาพแวดล้อม (Environment Variables)
  # PM_API_TOKEN_ID และ PM_API_TOKEN_SECRET
}
```

- **หลักปฏิบัติความปลอดภัย**: ให้ใช้งาน **API Token** ที่จำกัดสิทธิ์เฉพาะเท่าที่จำเป็น (Principle of Least Privilege) แทนการใช้บัญชีระดับผู้ดูแลระบบสูงสุด (`root@pam`) เสมอ

### 6.1 ข้อค้นพบจากงานวิจัยด้านวิศวกรรมซอฟต์แวร์ (Key Research Findings)
การสร้างระบบอัตโนมัติต้องอิงอยู่บนหลักฐานเชิงประจักษ์จากการวิเคราะห์ข้อมูลจริง:

| ชื่องานวิจัยและแหล่งตีพิมพ์ | ข้อมูลและวิธีการวิเคราะห์ | ข้อค้นพบสำคัญทางวิศวกรรม | ข้อคิดและการนำมาปรับใช้กับเรา |
| :--- | :--- | :--- | :--- |
| **The Seven Sins**<br>*(Rahman et al., ICSE 2019)* | วิเคราะห์สคริปต์ IaC จำนวน 15,232 ไฟล์จากโครงการจริง | พบกลิ่นอันตรายด้านความปลอดภัย (Security Smells) 7 แบบ โดยเฉพาะการฝังความลับและการเปิดพอร์ตเชื่อมต่อทิ้งไว้ | ห้ามฝังรหัสผ่าน และห้ามตั้งค่าให้เซอร์วิสเปิดรับการเชื่อมต่อจากทุกเครือข่ายโดยไม่มีการป้องกัน |
| **Gang of Eight**<br>*(Rahman et al., ICSE 2020)* | ศึกษารูปแบบความผิดพลาดของ IaC เชิงลึก | จำแนกข้อบกพร่องออกเป็น 8 หมวดหมู่หลัก โดยหนึ่งในหมวดที่ร้ายแรงที่สุดคือ **การขาดคุณสมบัติ Idempotency** | ในการทดสอบระบบ ต้องพิสูจน์ Idempotency ด้วยการรันสคริปต์ซ้ำสองรอบเสมอ |
| **Ansible vs Chef Study**<br>*(TOSEM 2021)* | เปรียบเทียบข้อผิดพลาดข้ามเครื่องมือ IaC สองค่ายใหญ่ | ข้อผิดพลาดและการตั้งค่าที่ไม่ปลอดภัยเกิดขึ้นในสัดส่วนใกล้เคียงกันทั้งใน Ansible และ Chef | **การเปลี่ยนเครื่องมือไม่ได้ช่วยแก้ปัญหาความปลอดภัย** หากผู้ใช้งานยังขาดความเข้าใจในหลักการทางวิศวกรรม |
| **Cloud Outage Study**<br>*(Gunawi et al., SoCC 2016)* | วิเคราะห์เหตุการณ์ระบบหยุดทำงาน 597 ครั้งจาก 32 ผู้ให้บริการคลาวด์ | ความซ้ำซ้อนของฮาร์ดแวร์ (Redundancy) ไม่สามารถป้องกันระบบล่มจากการกระจายการตั้งค่าที่ผิดพลาด (Misconfiguration) ได้ | เมื่อคำสั่งที่ผิดพลาดถูกสั่งรัน มันจะทำลายระบบหลักและระบบสำรองให้พังพร้อมกันทันที |

### 6.2 ห้ากรณีศึกษาระบบล่มระดับโลกกับห้าหลักการความปลอดภัย (Five Case Studies)
ทุกเหตุการณ์ถอดบทเรียนมาจากรายงานวิเคราะห์ผลกระทบหลังเกิดเหตุ (Post-Incident Review: PIR) ที่องค์กรเปิดเผยต่อสาธารณะ:

| เหตุการณ์และปี | สิ่งที่เกิดขึ้นจริง (What Happened) | ผลกระทบที่เกิดขึ้น | หลักการทางวิศวกรรมที่ขาดหายไป |
| :--- | :--- | :--- | :--- |
| **AWS S3**<br>*(พ.ศ. 2560 / 2017)* | วิศวกรต้องการนำเซิร์ฟเวอร์ระบบจัดเก็บบิลไม่กี่ตัวออกจากระบบเพื่อแก้ไข จึงป้อนคำสั่งสคริปต์แต่ **พิมพ์พารามิเตอร์ผิดเพียงตัวเดียว** ทำให้คำสั่งไปถอดเซิร์ฟเวอร์ย่อยที่เป็นกลไกหลักของ S3 ออกมาเป็นจำนวนมหาศาล | บริการ S3 ภูมิภาค us-east-1 หยุดทำงาน ส่งผลให้เว็บไซต์และบริการอินเทอร์เน็ตทั่วโลกเป็นอัมพาตหลายชั่วโมง | **ขีดจำกัดความเสียหายในสคริปต์ (Blast Radius Limit)**: สคริปต์ไม่ควรยอมให้ลบหรือปิดเครื่องเกินเพดานที่ปลอดภัยโดยไม่มีการยับยั้ง |

## 7. ปฏิบัติการ Lab 6: โครงสร้างพื้นฐานในรูปแบบโค้ด (Lab 6 Guide & Acceptance Criteria)

### 7.1 ลำดับงาน 7 ขั้นตอนของ Lab 6
ในห้องปฏิบัติการจริง อุปกรณ์ฮาร์ดแวร์บางส่วนยังอยู่ในพื้นที่เตรียมการ (Staging Area) การทดลองจึงดำเนินการบนสภาพแวดล้อมทดสอบก่อน โดยโค้ดชุดเดียวกันนี้จะถูกนำไปรันบนคลัสเตอร์จริงเมื่อติดตั้งฮาร์ดแวร์เสร็จสมบูรณ์

```
[ขั้นตอนการปฏิบัติการ Lab 6: 7 ขั้นตอน]

[1. เขียนโค้ด] -> [2. Plan & Apply] -> [3. สร้าง Drift] -> [4. ตรวจจับ] -> [5. ตั้งค่า] -> [6. รันซ้ำ] -> [7. ทำลายและสร้างใหม่]
```

1. **เขียนไฟล์ `main.tf`**: เขียนโค้ดกำหนดทรัพยากรเครื่องเสมือน 1 เครื่องต่อ 1 กลุ่ม พร้อมผูกหมายเลข VLAN ประจำกลุ่ม
2. **รัน Plan และ Apply**: ประมวลผลสร้างเครื่องเสมือนจริงขึ้นมาจากไฟล์โค้ด
3. **สร้างความเบี่ยงเบน (Create Drift)**: แอบล็อกอินเข้าหน้าเว็บคอนโซล Proxmox แล้วแก้ไขสเปกเครื่องเสมือน 1 เครื่องด้วยมือ (เช่น เพิ่ม RAM หรือ CPU Cores)
4. **ตรวจจับการเบี่ยงเบน (Detect Drift)**: รันคำสั่ง `tofu plan` เพื่อแสดงให้เห็นว่าเครื่องมือสามารถตรวจจับส่วนต่างระหว่างโค้ดกับระบบจริงได้
5. **ตั้งค่าบริการด้วย Ansible**: ใช้ Ansible Playbook เข้าไปติดตั้งแพ็กเกจ Nginx Web Server และจัดวางไฟล์คอนฟิก
6. **รันซ้ำเพื่อพิสูจน์ Idempotency**: รันคำสั่ง Ansible Playbook ซ้ำอีกรอบ และต้องได้ผลลัพธ์ `changed=0`
7. **ทำลายแล้วสร้างใหม่ (Destroy & Re-create)**: รันคำสั่งทำลายทรัพยากรทั้งหมด แล้วสั่งสร้างใหม่จากโค้ด เพื่อพิสูจน์ว่าระบบสภาพแวดล้อมที่สร้างขึ้นใหม่มีสภาพเหมือนเดิมทุกประการ 100%

### 8.1 สรุปสามประโยคของวันนี้ (Three Key Takeaways)
