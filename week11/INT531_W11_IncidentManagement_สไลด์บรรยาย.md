## 1. แผนการเรียนและผลลัพธ์การเรียนรู้ประจำคาบ (Agenda & SLOs)

### 1.1 วาระการเรียนรู้ (Agenda)
- **ช่วงเช้า**: วางกระบวนการรับมือเหตุการณ์ผิดปกติ การจัดลำดับความรุนแรง และการกำหนดบทบาทหน้าที่
- **ช่วงบ่าย**: นำกระบวนการไปใช้รับมือกับปัญหาที่กำลังเกิดขึ้นจริงในห้องปฏิบัติการระหว่างการติดตั้ง Proxmox VE บนเซิร์ฟเวอร์

```
[แผนการเรียนรู้ 6 หัวข้อหลัก]
01: Incident คืออะไร และต่างจาก Alert อย่างไร (เกณฑ์การประกาศ และเหตุผลที่ต้องประกาศให้ชัด)
02: วงจรชีวิตของเหตุการณ์ (Detect, Triage, Mitigate, Resolve, Learn)
03: บทบาทในทีมตอบสนอง (IC, OL, CL, Scribe และกฎที่ทำให้ได้ผลจริง)
04: ระดับความรุนแรงและการยกระดับ (SEV1 ถึง SEV4 และเงื่อนไขการเรียกคนเพิ่ม)
05: การบรรเทาและการสื่อสาร (เทคนิคที่ใช้บ่อย และ Status Update ที่ใช้งานได้จริง)
06: ปัจจัยด้านมนุษย์และปฏิบัติการ (ความกดดัน การส่งต่อเวร และการตั้งกระบวนการของกลุ่ม)
```

### 1.2 ผลลัพธ์การเรียนรู้ประจำคาบ (Specific Learning Outcomes: SLOs)
- **SLO 1**: อธิบายวงจรชีวิตของเหตุการณ์ผิดปกติได้ครบห้าขั้น (CLO6)
- **SLO 2**: ระบุบทบาทและความรับผิดชอบใน Incident Command System ได้อย่างถูกต้อง (CLO6, CLO7)
- **SLO 3**: จัดระดับความรุนแรง และตัดสินใจยกระดับเหตุการณ์ได้อย่างเหมาะสม (CLO6)
- **SLO 4**: เขียนรายงานสถานะ (Status Update) ที่ชัดเจน ตรงเวลา และเหมาะสมกับผู้รับสารแต่ละกลุ่ม (CLO6, CLO7)
- **SLO 5**: ให้ความสำคัญกับการบรรเทาผลกระทบก่อนการค้นหาสาเหตุที่แท้จริง (CLO6)
- **SLO 6**: ปฏิบัติหน้าที่ในทีมตอบสนองเหตุการณ์ได้อย่างมีประสิทธิภาพภายใต้สถานการณ์จริง (CLO6, CLO7)

## 2. การทำความเข้าใจ Incident และความแตกต่างจาก Alert และ Problem (Incident Definitions)

> **หลักการพื้นฐาน**: *"ไม่ใช่ทุก Alert คือ Incident และไม่ใช่ทุก Incident เริ่มต้นจาก Alert"*

### 2.1 คำนิยามสามคำที่มักสับสน (Alert, Incident, Problem)
การสื่อสารในภาวะฉุกเฉินมักล้มเหลวเพราะสมาชิกในทีมและผู้เกี่ยวข้องใช้ศัพท์ปะปนกันโดยไม่เข้าใจขอบเขต:

| คำศัพท์ | คำจำกัดความทางวิศวกรรม SRE | ลักษณะสำคัญ |
| :--- | :--- | :--- |
| **การแจ้งเตือน (Alert)** | สัญญาณจากระบบตรวจวัด (Monitoring System) แจ้งว่ามีค่าชี้วัดบางอย่างเข้าเงื่อนไขที่กำหนดไว้ | อาจเป็นสัญญาณเตือนที่เกิดขึ้นจริง (True Positive) หรือสัญญาณลวง (False Positive) ก็ได้ |
| **เหตุการณ์ผิดปกติ (Incident)** | เหตุการณ์ที่ส่งผลกระทบต่อผู้ใช้งานแล้ว หรือมีความเสี่ยงสูงที่จะกระทบในระยะเวลาอันใกล้ | ต้องมีมนุษย์เข้าไปลงมือปฏิบัติการเพื่อแก้ไขหรือบรรเทาผลกระทบในทันที |
| **ปัญหาเชิงระบบ / สาเหตุต้นตอ (Problem)** | สาเหตุรากเหง้าเบื้องหลัง (Underlying Cause) ที่ยังไม่ได้รับการแก้ไขอย่างถาวร | เป็นบ่อเกิดที่ทำให้เกิด Incident ซ้ำซากได้อีกเรื่อย ๆ หากไม่ได้รับการแก้ไข |

### 2.2 ความสัมพันธ์เชิงระบบของทั้งสามส่วน
- **Alert สิบครั้งอาจเป็น Incident เดียว**: สัญญาณเตือนที่ยิงเข้ามาต่อเนื่องกันจำนวนมากจากบริการหลายตัว อาจชี้เป้าไปที่เหตุการณ์ความผิดปกติเดียวกันของระบบ
- **Incident หลายครั้งอาจมาจาก Problem เดียวกัน**: หากระบบเกิดเหตุขัดข้องซ้ำซากในจุดเดิม แสดงว่ายังไม่ได้แก้ไขปัญหาเชิงระบบที่ต้นตอ
- **ตัวอย่างเชิงปฏิบัติการในการติดตั้งระบบ**:
  - หน่วยความจำ (RAM) บนเซิร์ฟเวอร์ไม่เพียงพอ จัดเป็น **Problem**
  - การที่เครื่องของกลุ่มหนึ่งใช้งานไม่ได้หรือติดตั้งระบบไม่สำเร็จในวันนั้น จัดเป็น **Incident**

### 2.3 เกณฑ์การตัดสินใจประกาศ Incident (When to Declare an Incident)
> **กฎการตัดสินใจ**: *"ถ้าลังเลใจว่าควรประกาศเป็น Incident หรือไม่ แปลว่าควรประกาศทันที"*

การประเมินสถานการณ์ว่าควรประกาศ Incident หรือไม่ ให้ตรวจสอบจากเงื่อนไข 5 ข้อดังต่อไปนี้:

1. **ผู้ใช้ได้รับผลกระทบแล้ว หรือกำลังจะได้รับผลกระทบภายในเวลาอันใกล้**: ระบบหยุดทำงาน ความล่าช้าพุ่งสูง หรือแนวโน้มการใช้ทรัพยากรใกล้แตะขีดจำกัดสูงสุด
2. **ต้องมีคนมากกว่าหนึ่งคนเข้ามาช่วยกันแก้ไข**: ขอบเขตของปัญหาใหญ่เกินกว่าที่ผู้ดูแลคนเดียวจะรับมือได้ไหว
3. **ต้องมีการสื่อสารออกไปภายนอกทีม**: มีผู้ใช้งาน ผู้บริหาร หรือทีมอื่น ๆ รอคอยคำชี้แจงสถานะ
4. **ใช้เวลาแก้ไขนานเกินกว่าที่คนคนเดียวจะจัดการได้ในเวลาอันสั้น**: จำเป็นต้องเริ่มกระบวนการจัดสรรเวลาและทรัพยากรบุคคล
5. **ไม่แน่ใจว่าเข้าเกณฑ์หรือไม่**: ให้ประกาศไว้ก่อนในระดับเบื้องต้น แล้วสามารถปรับลดระดับความรุนแรง (Downgrade) ในภายหลังได้เมื่อตรวจสอบข้อเท็จจริงชัดเจนแล้ว

```
[การเปรียบเทียบต้นทุนของการตัดสินใจ]
ต้นทุนของการประกาศแล้วพบว่าไม่ใช่เรื่องใหญ่ = เสียเวลาบุคลากรไป 10 นาที
ต้นทุนของการไม่ยอมประกาศทั้งที่ควรประกาศ = ไม่มีใครรับรู้ว่าระบบกำลังพังทลายจนสายเกินแก้
```

## 3. วงจรชีวิตของเหตุการณ์ผิดปกติ (Incident Lifecycle)

วงจรชีวิตของเหตุการณ์หนึ่งครั้งประกอบด้วย 5 ขั้นตอนหลักที่ต้องดำเนินไปตามลำดับ โดยแต่ละขั้นตอนมีคำถามสำคัญที่ทีมต้องตอบให้ได้:

```
[วงจรชีวิตของเหตุการณ์ 5 ขั้นตอน]
1. Detect (ตรวจพบ) ---------> 2. Triage (คัดกรอง) ---------> 3. Mitigate (บรรเทา)
   [ใช้เวลาเท่าไรกว่าจะรู้?]       [ควรปลุกคนหรือไม่?]           [ผู้ใช้หยุดเดือดร้อนก่อน]
                                                                     |
5. Learn (เรียนรู้) <-------- 4. Resolve (คลี่คลาย) <----------------+
   [บันทึกก่อนจะลืม]             [ยืนยันด้วยตัวเลข]
```

### 3.1 ห้าขั้นตอนของวงจรชีวิตเหตุการณ์ (Detect, Triage, Mitigate, Resolve, Learn)

1. **ตรวจพบ (Detect)**:
   - เกิดสัญญาณเตือน (Alert) จากระบบตรวจวัด หรือมีรายงานแจ้งเข้ามาจากผู้ใช้งาน
   - คำถามสำคัญทางวิศวกรรม: *"ระบบใช้เวลาเท่าไรในการตรวจพบ นับตั้งแต่ความผิดปกติเริ่มเกิดขึ้น (Time to Detect: TTD)"*
2. **คัดกรองและประเมิน (Triage)**:
   - ประกาศ Incident จัดระดับความรุนแรง และมอบหมายบทบาทหน้าที่รับผิดชอบ
   - คำถามสำคัญทางวิศวกรรม: *"ความผิดปกตินี้ร้ายแรงเพียงใด ต้องตามคนหรือปลุกคนในทีมเข้ามาทันทีหรือไม่"*
3. **บรรเทาผลกระทบ (Mitigate)**:
   - ดำเนินการทุกวิถีทางเพื่อให้ผู้ใช้หยุดเดือดร้อนและระบบกลับมาให้บริการได้ก่อน
   - คำถามสำคัญทางวิศวกรรม: *"จะทำให้บริการฟื้นคืนสภาพโดยเร็วที่สุดได้อย่างไร โดยไม่ต้องเสียเวลารอหาสาเหตุที่แท้จริง"*
4. **ยืนยันการคลี่คลาย (Resolve)**:
   - ยืนยันว่าเหตุการณ์สิ้นสุดลงแล้วอย่างสมบูรณ์
   - คำถามสำคัญทางวิศวกรรม: *"มีตัวเลขชี้วัดทางสถิติ (Metrics) ยืนยันว่าระบบกลับสู่สภาวะปกติจริงหรือไม่ โดยไม่ใช้เพียงความรู้สึก"*
5. **เรียนรู้และถอดบทเรียน (Learn)**:
   - บันทึกข้อเท็จจริง ลำดับเวลา (Timeline) และข้อมูลทางเทคนิคไว้ในขณะที่ทุกคนยังจำรายละเอียดได้
   - คำถามสำคัญทางวิศวกรรม: *"เกิดอะไรขึ้น ระบบล้มเหลวอย่างไร และเราจะป้องกันไม่ให้เกิดขึ้นซ้ำได้อย่างไรในอนาคต"*

### 3.2 หลักการสำคัญ: บรรเทาก่อน วินิจฉัยทีหลัง
> **คำขวัญ SRE**: *"บรรเทามาก่อนวินิจฉัย — บริการที่กลับมาเปิดทำงานได้ภายใน 10 นาทีโดยที่ยังไม่รู้สาเหตุ ดีกว่าคำอธิบายสาเหตุได้อย่างสมบูรณ์แบบหลังระบบล่มไปแล้วสองชั่วโมง"*

## 4. เทคนิคการบรรเทาผลกระทบเฉพาะหน้า (Mitigation Techniques)

เมื่อเกิดเหตุการณ์ขึ้น เป้าหมายสูงสุดคือการลดผลกระทบต่อผู้ใช้ให้เร็วที่สุด การบรรเทาผลกระทบ (Mitigation) มีเทคนิคที่นิยมใช้ในระบบวิศวกรรม เรียงตามความเร็วในการให้ผลดังนี้:

### 4.1 ห้าเทคนิคการบรรเทาที่ใช้บ่อยและข้อควรระวัง

| เทคนิคการบรรเทา | บริบทและเงื่อนไขที่นำมาใช้ | ข้อควรระวังและความเสี่ยง |
| :--- | :--- | :--- |
| **ย้อนกลับเวอร์ชัน (Rollback)** | อาการผิดปกติเริ่มเกิดขึ้นทันทีหลังจากการปรับใช้ซอฟต์แวร์หรือการเปลี่ยนแปลงล่าสุด | ต้องมั่นใจว่ากลไกการย้อนกลับทำได้จริง และโครงสร้างข้อมูล (Database Schema) ไม่เสียหาย |
| **ปิดฟีเจอร์ด้วยสวิตช์ (Feature Flagging)** | ความผิดปกติจำกัดอยู่เฉพาะความสามารถหรือฟังก์ชันใหม่ตัวใดตัวหนึ่ง | ต้องมีการเตรียม Feature Flag ไว้ล่วงหน้าในโค้ด ไม่สามารถสร้างขึ้นใหม่ได้ตอนเกิดเหตุ |
| **สลับไปใช้ชุดสำรอง (Failover)** | ส่วนประกอบหรือเครื่องเซิร์ฟเวอร์หลักชำรุด แต่มีระบบสำรอง (Redundant System) พร้อมใช้งาน | ต้องเคยผ่านการซ้อมสลับระบบมาก่อน หากไม่เคยทดสอบ อาจเจอปัญหาใหม่ซ้อนทับทันที |
| **ตัดทราฟฟิกออกจากส่วนที่เสีย (Traffic Drain / Shedding)** | เกิดความเสียหายเฉพาะบางเครื่อง หรือบาง Availability Zone | เครื่องหรือโซนส่วนที่เหลือต้องมีขีดความสามารถรองรับโหลดไหว มิฉะนั้นจะล่มต่อเนื่องกันหมด (Cascading Failure) |
| **ขยายความจุชั่วคราว (Scale Up / Scale Out)** | อาการผิดปกติเกิดจากภาระงานล้นเกินพิกัดของระบบ (Overload) | การเพิ่มเครื่องต้องใช้เวลาบูตช้ากว่าที่คาดเสมอ ต้องนำไปใช้ควบคู่กับการจำกัดอัตราคำขอ (Rate Limiting) |

### 4.2 กฎความพร้อมก่อนเกิดเหตุ (Preparation & Rehearsal)
> **กฎเหล็กวิศวกรรม**: *"ทุกเทคนิคข้างต้นต้องเตรียมการและซักซ้อมไว้ก่อนเกิดเหตุเสมอ สิ่งใดที่ไม่เคยผ่านการซ้อม จะไม่สามารถนำมาใช้งานได้จริงในนาทีวิกฤต"*

---

## 5. โครงสร้างบทบาทในทีมตอบสนองเหตุการณ์ (Incident Response Roles)

> **หลักการบริหาร**: *"ความชัดเจนของบทบาท สำคัญกว่าความเก่งเฉพาะตัวของแต่ละบุคคล"*

โครงสร้างการจัดทีมรับมือเหตุการณ์ของ SRE พัฒนามาจากแบบจำลอง Incident Command System (ICS) ที่ใช้งานในหน่วยงานดับเพลิงและกู้ภัยฉุกเฉินระดับสากล เนื่องจากมีเงื่อนไขสถานการณ์กดดันและเวลาจำกัดเหมือนกัน:

### 5.1 สี่บทบาทตามแบบแผน Incident Command System (ICS)

```
                       +-------------------------------+
                       |   ผู้บัญชาการเหตุการณ์ (IC)    |
                       |      Incident Commander       |
                       |  [ตัดสินใจ มอบหมาย คุมภาพรวม]  |
                       +---------------+---------------+
                                       |
        +------------------------------+------------------------------+
        |                              |                              |
+-------v-------+              +-------v-------+              +-------v-------+
| หัวหน้าปฏิบัติการ |              | หัวหน้าการสื่อสาร |              |   ผู้บันทึก   |
|      (OL)     |              |      (CL)     |              |    (Scribe)   |
| Operations    |              | Communication |              | บันทึกลำดับ   |
| Lead          |              | Lead          |              | เหตุการณ์     |
| [แตะระบบคนเดียว]|              | [กันเสียงรบกวน]|              | [ลงเวลาครบถ้วน]|
+---------------+              +---------------+              +---------------+
```

| บทบาทหน้าที่ | หน้าที่ความรับผิดชอบหลัก | กฎเหล็กประจำตำแหน่ง |
| :--- | :--- | :--- |
| **ผู้บัญชาการเหตุการณ์ (Incident Commander: IC)** | ตัดสินใจขั้นเด็ดขาด มอบหมายภารกิจ คุมภาพรวมของสถานการณ์ และกำหนดทิศทางการแก้ปัญหา | **ไม่ลงมือพิมพ์คำสั่งเอง** ทำหน้าที่สั่งการและประสานงานเท่านั้น |
| **หัวหน้าปฏิบัติการ (Operations Lead: OL)** | เป็นบุคคลเพียงคนเดียวที่มีสิทธิ์แตะต้องระบบ ลงมือคอนฟิก หรือออกคำสั่งในเซิร์ฟเวอร์ | **ต้องรายงานทุกการเปลี่ยนแปลงให้ IC รับทราบ** ก่อนและหลังลงมือทำ |
| **หัวหน้าการสื่อสาร (Communications Lead: CL)** | สื่อสารรายงานสถานะให้ผู้ใช้งาน ผู้บริหาร และบุคคลภายนอกรับทราบสถานการณ์ | **ทำหน้าที่เป็นเกราะป้องกัน** สกัดกั้นคำถามไม่ให้เข้ามารบกวนทีมปฏิบัติการ |
| **ผู้บันทึก (Scribe)** | บันทึกลำดับเหตุการณ์ ข้อเท็จจริง การตัดสินใจ และคำสั่งที่เกิดขึ้นตามเวลาจริง (Real-time Timeline) | **ลงเวลาให้ครบถ้วนตามจริง และไม่ตัดสินความถูกผิดของใคร** |

### 5.2 กฎเหล็ก: มือของ IC ต้องไม่อยู่บนแป้นพิมพ์
> **สัจธรรมในการบัญชาการ**: *"มือของ IC ต้องไม่อยู่บนแป้นพิมพ์ — นาทีที่ผู้บัญชาการเหตุการณ์เริ่มก้มหน้าไล่แก้ปัญหาด้วยตนเอง คือนาทีที่ระบบทั้งหมดไม่มีใครคอยบัญชาการ"*

### 5.3 การปรับโครงสร้างบทบาทสำหรับทีมขนาดเล็ก
สำหรับทีมงานขนาดเล็ก (เช่น สมาชิก 3 คนในการทำแล็บหรือเฝ้าระวังระบบ):
- **คนที่ 1**: รับบทบาท **Incident Commander (IC)** ควบคุมภาพรวมและสั่งการ
- **คนที่ 2**: รับบทบาท **Operations Lead (OL)** ลงมือปฏิบัติการบนระบบเพียงคนเดียว
- **คนที่ 3**: ควบรวมบทบาท **Communications Lead (CL)** และ **Scribe** ทำหน้าที่ทั้งสื่อสารภายนอกและบันทึกไทม์ไลน์

## 6. การยกระดับและการส่งต่อเวรปฏิบัติการ (Escalation & Handover)

สองจุดวิกฤตที่เหตุการณ์มักทวีความรุนแรงและยืดเยื้อโดยไม่จำเป็น คือ **การลังเลที่จะยกระดับ** และ **การส่งต่อเวรที่ไร้ประสิทธิภาพ**:

### 6.1 เกณฑ์การยกระดับเหตุการณ์ (Escalation Criteria)
การตัดสินใจยกระดับเหตุการณ์ (Escalation) ต้องทำขึ้นภายใต้เงื่อนไขที่เป็นรูปธรรม:
- **เวลาล่วงเลยเกินเกณฑ์ที่กำหนด**: เมื่อแก้ปัญหาไประยะหนึ่งตามที่กำหนดไว้ในคู่มือแล้ว แต่ระบบยังไม่มีสัญญาณตอบสนองที่ดีขึ้น
- **ขอบเขตความเสียหายขยายวงกว้าง**: ปัญหาเริ่มลุกลามไปยังระบบข้างเคียง หรือส่งผลกระทบต่อบริการสำคัญอื่น ๆ
- **ต้องการสิทธิ์หรืออำนาจที่ตนเองไม่มี**: จำเป็นต้องอาศัยสิทธิ์การเข้าถึงระดับสูง หรือต้องการการตัดสินใจในเชิงธุรกิจจากผู้บริหาร

### 6.2 ทัศนคติทางวัฒนธรรม: การยกระดับไม่ใช่ความล้มเหลว
> **วัฒนธรรมเชิงบวกในองค์กร SRE**: *"การยกระดับไม่ใช่การยอมแพ้ แต่เป็นการตัดสินใจที่ถูกต้องตามกระบวนการ — องค์กรที่ชอบลงโทษคนที่ตัดสินใจยกระดับเหตุการณ์ จะได้ผลลัพธ์เป็นเหตุการณ์ที่ล่มยาวนานขึ้นเสมอ"*

### 6.3 แบบแผนการส่งต่อเวรที่มีประสิทธิภาพ (Shift Handover)
เมื่อเหตุการณ์ยืดเยื้อจนต้องเปลี่ยนเวรผู้ปฏิบัติงาน ให้ปฏิบัติตามกฎสองประการ:
1. **การทวนความเข้าใจย้อนกลับ**: ผู้รับมอบงานต้องสรุปสิ่งที่ตนเองเข้าใจกลับไปให้ผู้ส่งมอบงานฟังจนแน่ชัด ก่อนที่ผู้ส่งมอบงานจะออกจากระบบ
2. **สี่สิ่งที่ต้องส่งต่อให้ครบถ้วน**:
   - **สถานะปัจจุบัน (Current Status)**: ระบบอยู่ในสภาพใด มีบริการใดใช้งานได้หรือไม่ได้บ้าง
   - **สิ่งที่ทดลองทำไปแล้วและผลลัพธ์ (Actions Taken & Results)**: เพื่อป้องกันไม่ให้คนใหม่ทำซ้ำในสิ่งที่ล้มเหลวไปแล้ว
   - **สิ่งที่กำลังดำเนินการอยู่ (In-flight Actions)**: กระบวนการใดที่กำลังรันค้างอยู่
   - **สิ่งที่ยังไม่ทราบแน่ชัด (Unknowns / Open Hypotheses)**: ข้อสงสัยหรือสมมติฐานที่ยังรอการพิสูจน์

> **บทเรียนราคาแพง**: *"การส่งต่อเวรที่ทำแบบลวก ๆ จะทำให้ผู้ปฏิบัติงานคนใหม่ต้องเริ่มต้นนับหนึ่งจากศูนย์ และมักเสียเวลาไปลองทำในสิ่งที่คนก่อนหน้าลองแล้วล้มเหลว"*

## 7. การจัดระดับความรุนแรงของเหตุการณ์ (Severity Levels & Categorization)

> **หลักการสำคัญ**: *"ตกลงเกณฑ์ระดับความรุนแรงไว้ล่วงหน้าตั้งแต่ตอนที่ระบบยังปกติ เพื่อไม่ต้องมานั่งถกเถียงกันในนาทีที่เกิดเหตุ"*

ระดับความรุนแรง (Severity) คำนวณจากสูตร:
$$\text{Severity} = \text{ระดับความรุนแรงของผลกระทบ (Impact)} \times \text{ขอบเขตของผู้ใช้ที่ได้รับผลกระทบ (Scope)}$$

### 7.1 เมทริกซ์ระดับความรุนแรง SEV1 ถึง SEV4

| ระดับ | ผลกระทบและขอบเขตความเสียหาย | การระดมพลและเงื่อนไขการเรียกคน | ความถี่ในการส่ง Status Update |
| :--- | :--- | :--- | :--- |
| **SEV1** | ผู้ใช้งานส่วนใหญ่ของทั้งระบบไม่สามารถใช้งานบริการได้เลย | **ปลุกทันที** · ระดมกำลังคนทั้งทีมเข้ามาในห้องบัญชาการ | อัปเดตทุก **30 นาที** |
| **SEV2** | ฟังก์ชันการทำงานหลักเสียหาย หรือมีผู้ใช้จำนวนมากได้รับผลกระทบ | **ปลุกทันที** · เรียกผู้รับผิดชอบระบบหลักเข้ามาแก้ปัญหา | อัปเดตทุก **1 ชั่วโมง** |
| **SEV3** | ฟังก์ชันการทำงานรองเสียหาย แต่ยังมีช่องทางเลี่ยง (Workaround) ให้ใช้งานต่อได้ | เปิดคำร้องแจ้งซ่อม (Ticket) ดำเนินการแก้ไขในเวลาทำการปกติ | อัปเดต **วันละ 1 ครั้ง** |
| **SEV4** | ข้อผิดพลาดด้านความสวยงาม (UI/Cosmetic) หรือผลกระทบจำกัดอยู่เฉพาะภายในทีม | นำเข้าคิวงานพัฒนาตามรอบปกติ (Backlog) | **ไม่ต้องส่งอัปเดตสถานะ** |

### 7.2 สิ่งที่ตามมาจากการกำหนดระดับความรุนแรง
ระดับความรุนแรงไม่ได้ทำหน้าที่เพียงแค่บอกว่าปัญหานั้นหนักหนาสาหัสเพียงใด แต่เป็นเครื่องมือกำหนดนโยบายปฏิบัติการว่า:
- ใครบ้างที่ต้องถูกตามตัว (Who gets paged)
- ต้องระดมทรัพยากรมากน้อยเพียงใด
- ต้องรายงานความคืบหน้าบ่อยเพียงใด

> **ข้อเตือนใจ**: *"ตกลงเส้นแบ่งเหล่านี้ตอนที่ยังไม่มีใครตื่นตระหนก การมานั่งเถียงกันเรื่องเลือกระดับความรุนแรงตอนเกิดเหตุ เป็นการเผาผลาญเวลาอันมีค่าที่ระบบไม่มีให้เสีย"*

## 8. การสื่อสารในภาวะวิกฤตและการรายงานสถานะ (Crisis Communication & Status Updates)

> **หลักการสื่อสาร**: *"คนที่รออยู่ภายนอกไม่ได้ต้องการรายละเอียดทางเทคนิคที่ซับซ้อน แต่ต้องการทราบความจริงว่า ณ ตอนนี้สถานการณ์เป็นอย่างไร"*

### 8.1 โครงสร้างข้อความ Status Update ที่ใช้งานได้จริง
ข้อความรายงานสถานะที่มีประสิทธิภาพ ต้องประกอบด้วยองค์ประกอบหลัก 4 ประการเสมอ:
1. **ผู้ใช้เห็นอะไร (User Impact)**: สรุปผลกระทบที่เกิดขึ้นจากมุมมองของผู้ใช้งาน
2. **เรากำลังทำอะไร (Current Actions)**: อธิบายขั้นตอนที่ทีมกำลังดำเนินการแก้ไขอยู่ในขณะนี้
3. **ยังไม่รู้อะไร (Current Unknowns)**: ระบุข้อเท็จจริงหรือสาเหตุที่ยังตรวจสอบไม่พบอย่างโปร่งใส
4. **กำหนดเวลาอัปเดตครั้งถัดไป (Next Update Time)**: ระบุเวลาที่ทีมจะรายงานความคืบหน้าครั้งต่อไปอย่างชัดเจน

### 8.2 การเปรียบเทียบการสื่อสาร: ตัวอย่างที่มีประสิทธิภาพ vs ตัวอย่างที่ไม่ช่วยแก้ปัญหา


### 8.3 ความต้องการของผู้รับสารแต่ละกลุ่ม (Audience-specific Communication)
ข้อความเดียวที่ส่งกราดให้ทุกคน มักไม่สามารถตอบโจทย์ความต้องการของใครได้เลย จึงต้องปรับแต่งสารให้ตรงกับกลุ่มเป้าหมาย:

| กลุ่มผู้รับสาร | ข้อมูลที่ต้องการรับทราบ | แนวทางการสื่อสาร |
| :--- | :--- | :--- |
| **ภายในทีมที่กำลังแก้ไข** | รายละเอียดเชิงลึกทางเทคนิค, สิ่งที่ทดลองทำไปแล้ว, และสมมติฐานปัจจุบัน | สื่อสารอย่างตรงไปตรงมา เน้นข้อมูลดิบ ตัวเลข และหลักฐานเชิงประจักษ์ |
| **ผู้บริหาร (Executive)** | ระบบกระทบส่วนใดรุนแรงแค่ไหน, ต้องใช้เวลาอีกเท่าไร, และต้องการให้ผู้บริหารตัดสินใจเรื่องใดหรือไม่ | สื่อสารภาพรวมทางธุรกิจ หลีกเลี่ยงศัพท์เทคนิคเชิงลึก |
| **ผู้ใช้งาน (End-Users)** | ขณะนี้ระบบส่วนไหนใช้ได้ ส่วนไหนใช้ไม่ได้, มีทางเลือกสำรองหรือไม่, และจะแจ้งความคืบหน้าอีกครั้งเมื่อใด | เน้นแนวทางปฏิบัติที่ช่วยให้ผู้ใช้ทำงานต่อได้ ไม่ลงรายละเอียดระบบภายใน |
| **สาธารณชน (Public)** | ข้อเท็จจริงเท่าที่ได้รับการยืนยันอย่างเป็นทางการแล้วเท่านั้น | ไม่คาดเดาสาเหตุลอย ๆ และไม่กล่าวโทษบุคคลหรือผู้ให้บริการภายนอก |

> **กฎความปลอดภัยในการสื่อสาร**: *"อย่าสัญญาเวลาที่ตนเองยังไม่รู้ ให้ระบุเวลาที่จะส่งรายงานอัปเดตครั้งถัดไปแทน เพราะเวลาอัปเดตคือสิ่งที่เราควบคุมได้จริง"*

## 9. ปัจจัยด้านมนุษย์ในภาวะวิกฤต (Human Factors in Incident Management)

> **หลักการออกแบบกระบวนการ**: *"จงออกแบบกระบวนการทำงานโดยตั้งสมมติฐานว่า มนุษย์จะมีความสามารถในการคิดวิเคราะห์ลดลงอย่างมากเมื่อเผชิญเหตุวิกฤต ไม่ใช่คิดได้มากขึ้น"*

### 9.1 สภาพจิตใจและความสามารถในการคิดระหว่างเกิดเหตุ
เมื่อเกิดเหตุการณ์ฉุกเฉิน สภาพร่างกายและจิตใจของวิศวกรจะเผชิญกับอุปสรรค 4 ประการ:

```
[4 สภาพปัญหาด้านจิตวิทยาของมนุษย์ระหว่างวิกฤต]
1. Cognitive Overload (ภาระความคิดสูงขึ้น) ---> จำอะไรไม่ค่อยได้ คิดพร้อมกันหลายเรื่องไม่ได้
2. Tunnel Vision (การมองแบบแคบลง) -----------> ยึดติดกับสมมติฐานแรก ไม่มองความเป็นไปได้อื่น
3. Time Dilation (เวลารู้สึกบิดเบี้ยว) ---------> คิดว่าเพิ่งทำไป 5 นาที ทั้งที่ผ่านไป 40 นาทีแล้ว
4. Fatigue (ความล้าสะสม) ---------------------> ยิ่งเหนื่อยล้ายิ่งตัดสินใจผิดพลาดซ้ำสอง
```

- **ภาระทางความคิดสูงขึ้น (Cognitive Overload)**: ความจำระยะสั้นลดลง ไม่สามารถประมวลผลข้อมูลหลายอย่างพร้อมกันได้ จึงจำเป็นต้องมีคู่มือปฏิบัติการ (Runbook) และเช็กลิสต์ที่เป็นลายลักษณ์อักษร
- **การมองแบบแคบลง (Tunnel Vision)**: ผู้ปฏิบัติงานมักปักใจเชื่อในสมมติฐานแรกที่ผุดขึ้นมาในหัว และมองข้ามความเป็นไปได้อื่น ๆ ผู้บัญชาการเหตุการณ์ (IC) จึงมีหน้าที่คอยตั้งคำถามกระตุ้นเป็นระยะว่า *"เรามีคำอธิบายอื่นสำหรับปัญหานี้หรือไม่"*
- **เวลารู้สึกบิดเบี้ยว (Time Dilation)**: ความรู้สึกตื่นตระหนกทำให้รู้สึกว่าเวลาผ่านไปเพียง 5 นาที ทั้งที่ความเป็นจริงผ่านไปแล้วถึง 40 นาที การมี **ผู้บันทึก (Scribe)** คอยจดบันทึกเวลาจริงจึงมีความสำคัญสูงสุด
- **ความล้าสะสม (Fatigue)**: เมื่อเหตุการณ์ยืดเยื้อยาวนาน สมองจะล้าและนำไปสู่การตัดสินใจที่ผิดพลาด ต้องกำหนดรอบเวลาสลับเปลี่ยนตัวผู้ปฏิบัติงานล่วงหน้า ไม่ปล่อยให้คนเดิมรับผิดชอบจนจบเหตุการณ์

### 9.2 การออกแบบกระบวนการรองรับข้อจำกัดทางสติปัญญา (Runbooks & Checklists)
> **กฎทองของ SRE**: *"ทุกสิ่งที่คุณจำเป็นต้องจำและทำตอนตีสอง ให้เขียนเป็นคู่มือไว้ตั้งแต่ตอนบ่ายสองของวันทำงานปกติ"*

## 10. แนวปฏิบัติการทดลอง Lab 11: การตั้งกระบวนการตอบสนองเหตุการณ์จริง (Lab Guide)

การทดลองในสัปดาห์นี้ เป็นการนำกรอบการทำงาน Incident Management มาปรับใช้กับงานติดตั้งระบบเสมือนจริง Proxmox VE บนฮาร์ดแวร์เซิร์ฟเวอร์ที่กำลังดำเนินการอยู่:

### 10.1 เจ็ดขั้นตอนการปฏิบัติการของกลุ่ม

```
[เจ็ดขั้นตอนการปฏิบัติการแล็บ]
ขั้นที่ 1: ตั้งช่องทางสื่อสารฉุกเฉินของกลุ่ม (Discord / Teams)

ขั้นที่ 4: เตรียมเทมเพลตสำหรับ Status Update และตารางบันทึกเวลา Timeline

```

> **ข้อพึงระลึกประจำห้องปฏิบัติการ**: *"ทุกเหตุการณ์ความผิดปกติที่เกิดขึ้นระหว่างการติดตั้งจริง ให้บันทึกด้วยกระบวนการนี้ตั้งแต่วันแรก เพราะข้อเท็จจริงจากปัญหาจริงมีค่ายิ่งกว่าสถานการณ์จำลองเสมอ"*

### 10.2 เกณฑ์การตรวจรับการทดลอง 6 ข้อ (Acceptance Criteria)
การผ่านการทดลองภาคปฏิบัติการของแต่ละกลุ่ม พิจารณาจากเอกสารหลักฐาน 6 ข้อ:

| ลำดับ | รายการตรวจรับ | หลักฐานที่ต้องส่งมอบในเอกสารของกลุ่ม |
| :---: | :--- | :--- |
| **1** | มีช่องทางการแจ้งเหตุฉุกเฉินเฉพาะของกลุ่ม และสมาชิกทุกคนทราบตำแหน่งการเข้าถึง | ภาพถ่ายหน้าจอช่องทางการแจ้งเหตุ (Screenshot) |
| **2** | มีตารางเกณฑ์ระดับความรุนแรง (SEV1–SEV4) ที่กลุ่มร่างขึ้นเองพร้อมระบุเงื่อนไขการอัปเดต | ตารางเกณฑ์การจัดระดับความรุนแรงที่ใช้งานจริง |
| **3** | มีการมอบหมายบทบาทหน้าที่ครบถ้วน และระบุชัดเจนว่าใครทำอะไรเมื่อเกิดเหตุ | รายชื่อสมาชิกกลุ่มพร้อมบทบาทหน้าที่ที่ได้รับมอบหมาย |
| **4** | มีการบันทึกเหตุการณ์จริงที่เกิดขึ้นอย่างน้อย 1 ครั้ง พร้อมตารางไทม์ไลน์ที่ลงเวลาจริง | เอกสารบันทึกลำดับเหตุการณ์และเวลา (Timeline Document) |
| **5** | มีการส่งรายงานข้อความ Status Update อย่างน้อย 3 ครั้งในระหว่างเหตุการณ์นั้น | ข้อความรายงานสถานะทั้ง 3 ครั้งที่เผยแพร่ออกไปจริง |
| **6** | มีการประกาศปิดเหตุการณ์โดยยืนยันความสำเร็จด้วยตัวเลขทางสถิติ ไม่ใช่ความรู้สึก | ตัวเลขสถิติชี้วัดหรือผลคำสั่งที่ใช้ยืนยันการฟื้นตัวของระบบ |

> **ความเชื่อมโยงสู่สัปดาห์ถัดไป**: *"บันทึกเหตุการณ์ที่จัดทำขึ้นในสัปดาห์นี้ จะถูกนำไปใช้เป็นวัตถุดิบสำคัญในการเขียนรายงาน Blameless Postmortem ในสัปดาห์หน้า กลุ่มที่บันทึกข้อมูลไม่ครบถ้วนจะไม่สามารถเขียน Postmortem ได้"*

## 11. บทสรุปสามประโยค และหัวข้อการเรียนรู้ถัดไป (Summary & Next Steps)

```
[สรุปสาระสำคัญสามประโยค]
1. บรรเทาก่อน วินิจฉัยทีหลัง:
   ผู้ใช้ไม่ได้รอให้เราเข้าใจสาเหตุ และบริการที่กลับมาเปิดทำงานได้ใน 10 นาทีโดยยังไม่รู้สาเหตุ
   ย่อมดีกว่าคำอธิบายสาเหตุได้อย่างสมบูรณ์แบบหลังระบบพังทลายไปแล้วสองชั่วโมง

2. ความชัดเจนของบทบาท สำคัญกว่าความเก่งเฉพาะตัวของแต่ละคน:
   นาทีที่ผู้บัญชาการเหตุการณ์เริ่มก้มหน้าไล่แก้ปัญหาด้วยตนเอง คือนาทีที่ไม่มีใครคอยคุมภาพรวมของระบบ

3. ทุกสิ่งที่ต้องจำตอนตีสอง ให้เขียนไว้ตอนบ่ายสองของวันปกติ:
   มนุษย์ในภาวะวิกฤตจะคิดวิเคราะห์ได้ลดลงเสมอ กระบวนการทางวิศวกรรมจึงต้องออกแบบบนสมมติฐานนี้
```

**หัวข้อการเรียนรู้ในคาบถัดไป**:  
**การชันสูตรเหตุการณ์โดยปราศจากการกล่าวโทษ (Blameless Postmortem)** — เปลี่ยนเหตุการณ์ความผิดปกติที่บันทึกไว้ ให้กลายเป็นโอกาสในการเรียนรู้และเสริมสร้างความน่าเชื่อถือขององค์กร
