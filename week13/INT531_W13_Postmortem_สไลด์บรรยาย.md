## 1. แผนการเรียนและผลลัพธ์การเรียนรู้ประจำคาบ (Agenda & SLOs)

### 1.1 วาระการเรียนรู้ (Agenda)
- **ช่วงเช้า**: ทำความเข้าใจว่าทำไมต้องไม่โทษใคร และโครงสร้างการเขียน Postmortem ที่มีประสิทธิภาพ
- **ช่วงบ่าย**: ลงมือเขียนเอกสารจริงจากเหตุการณ์ที่บันทึกไว้ของกลุ่มตนเอง แล้วแลกเปลี่ยนกันตรวจประเมิน

```
[แผนการเรียนรู้ 6 หัวข้อหลัก]
01: Postmortem มีไว้ทำไม (เรียนรู้ระดับองค์กร ไม่ใช่การหาคนผิด)
02: โครงสร้างของเอกสาร (เจ็ดส่วน และหน้าที่ของแต่ละส่วน)
03: ทำไมการโทษคนจึงไม่ได้ผล (Hindsight Bias, Counterfactual และ Second Story)
04: หาปัจจัยร่วมแทนสาเหตุเดียว (ถามต่อจนพ้นคำว่าคนทำผิด)
05: Action Item ที่ทำให้อะไรเปลี่ยนจริง (มีเจ้าของ มีวันที่ และตรวจได้)
06: วัฒนธรรมและจริยธรรม (ความปลอดภัยทางจิตใจ ความโปร่งใส และความยั่งยืนของทีม)
```

### 1.2 ผลลัพธ์การเรียนรู้ประจำคาบ (Specific Learning Outcomes: SLOs)
เมื่อจบคาบเรียนนี้นักศึกษาจะสามารถ:
- **SLO 1**: เขียน Postmortem ที่มีองค์ประกอบครบตามเทมเพลตมาตรฐาน (CLO6)
- **SLO 2**: วิเคราะห์สาเหตุโดยไม่หยุดที่ความผิดพลาดของคน (CLO6)
- **SLO 3**: อธิบายวัฒนธรรมไม่กล่าวโทษ (Blameless Culture), เรื่องเล่าชั้นที่สอง (Second Story) และอคติมองย้อนหลัง (Hindsight Bias) ได้อย่างถูกต้อง (CLO6, CLO7)
- **SLO 4**: กำหนดสิ่งที่ต้องทำ (Action Item) ที่ระบุผู้รับผิดชอบชัดเจน ตรวจวัดผลได้ และจัดลำดับความสำคัญได้เหมาะสม (CLO6)
- **SLO 5**: อภิปรายประเด็นจริยธรรมของผู้ดูแลระบบที่มีผู้ใช้บริการจำนวนมาก (CLO7)
- **SLO 6**: อธิบายผลกระทบของภาวะหมดไฟ (Burnout) และมาตรการดูแลสุขภาวะของทีมเข้าเวรรับเหตุฉุกเฉิน (On-call Team) (CLO7)

## 2. บทบาทและเป้าหมายของ Postmortem (Purpose of Postmortem)

> **หัวใจสำคัญ**: *"ถ้าเป้าหมายคือหาคนผิด ครั้งหน้าจะไม่มีใครบอกความจริง"*

### 2.1 วัตถุประสงค์ และสิ่งที่ไม่ใช่วัตถุประสงค์
ความเข้าใจผิดเกี่ยวกับเป้าหมายของ Postmortem เป็นบ่อเกิดที่ทำให้เอกสารถูกจัดทำขึ้นอย่างไร้ประโยชน์ตั้งแต่ยังไม่เริ่มเขียน:

| สิ่งที่เป็นวัตถุประสงค์ของ Postmortem (What It Is) | สิ่งที่ไม่ใช่วัตถุประสงค์ของ Postmortem (What It Is Not) |
| :--- | :--- |
| **ทำให้องค์กรเรียนรู้จากเหตุการณ์หนึ่งครั้ง**: เปลี่ยนความสูญเสียให้เป็นความรู้เชิงระบบ | **การหาว่าใครเป็นคนทำให้เกิด**: การสืบสวนเพื่อระบุตัวผู้กระทำความผิด |
| **หาเงื่อนไขในระบบที่ยอมให้เรื่องนี้เกิดขึ้นได้**: วิเคราะห์สภาพแวดล้อม กลไกป้องกัน และข้อจำกัดทางเทคนิค | **เอกสารที่เขียนเพื่อส่งให้ผู้บริหารดูแล้วจบ**: รายงานเชิงพิธีกรรมที่ไม่มีการนำไปปฏิบัติการต่อ |
| **ทำให้คนที่ไม่ได้อยู่ในเหตุการณ์เข้าใจว่าเกิดอะไรขึ้น**: สื่อสารข้อเท็จจริงอย่างโปร่งใสเพื่อสร้างความเข้าใจร่วมกัน | **การบันทึกว่าได้ตักเตือนใครไปแล้วบ้าง**: บันทึกทัณฑ์บนหรือประจานข้อผิดพลาดของบุคคล |
| **สร้างรายการสิ่งที่ต้องแก้ไขที่มีคนรับผิดชอบจริง**: กำหนดมาตรการเชิงระบบที่มีเจ้าของงานและกำหนดเสร็จชัดเจน | **พิธีกรรมที่ทำเพราะกระบวนการกำหนดให้ทำ**: เอกสารตามระเบียบที่ไร้ความหมายต่อความน่าเชื่อถือของระบบ |

> **เกณฑ์ง่าย ๆ ที่ใช้วัดความสำเร็จ**: *"ถ้าคนที่อยู่ในเหตุการณ์อ่านเอกสารแล้ว รู้สึกปลอดภัยพอที่จะเล่าความจริงทั้งหมดในครั้งหน้า แปลว่าเอกสารนั้นเขียนมาถูกทาง"*

### 2.2 เกณฑ์การตัดสินใจเขียน Postmortem (When to Write a Postmortem)
องค์กรวิศวกรรมต้องตกลงเกณฑ์ในการจัดทำ Postmortem ไว้ล่วงหน้าให้ชัดเจน เพื่อไม่ให้เกิดการถกเถียงหรือใช้ดุลยพินิจส่วนบุคคลหลังเกิดเหตุ:

1. **ผู้ใช้ได้รับผลกระทบเกินกว่าเกณฑ์ที่ตกลงกันไว้ (User Impact Exceeds Threshold)**:
   - การให้บริการหยุดชะงัก หรือความล่าช้าส่งผลกระทบต่อประสบการณ์ใช้งานตามข้อตกลงระดับการบริการ (SLA) -> **ต้องเขียนเสมอ**
2. **งบประมาณความผิดพลาดถูกใช้ไปในสัดส่วนที่มีนัยสำคัญ (Significant Error Budget Consumption)**:
   - เหตุการณ์ครั้งเดียวเผาผลาญงบประมาณความผิดพลาด (Error Budget) ไปในสัดส่วนที่สูง เช่น เกินกว่า 20% หรือ 50% ของงวดเวลา -> **ต้องเขียนเสมอ**
3. **ต้องใช้การบรรเทาด้วยมือเพื่อให้บริการกลับมา (Manual Intervention Required for Mitigation)**:
   - กลไกการกู้คืนอัตโนมัติ (Automated Recovery) ล้มเหลว จนวิศวกรต้องเข้าไปสั่งการด้วยตนเอง (Manual Intervention) -> **ต้องเขียนเสมอ**
4. **ตรวจพบช้ากว่าที่ควรจะเป็นมาก (Significant Detection Lag)**:
   - ระบบมีปัญหาเป็นเวลานานก่อนที่ระบบตรวจวัดจะตรวจจับได้ หรือผู้ใช้งานเป็นฝ่ายแจ้งเข้ามาเอง -> **ต้องเขียนเสมอ แม้ผลกระทบต่อระบบจะน้อย**
5. **เกือบเกิดเหตุรุนแรงแต่รอดพ้นได้เพราะโชคช่วย (Near Miss / Lucky Escape)**:
   - เหตุการณ์ที่มีปัจจัยพร้อมจะล่ม แต่บังเอิญไม่พังเพราะเกิดนอกเวลาทำการ หรือมีเงื่อนไขภายนอกช่วยไว้ -> **ควรเขียนอย่างยิ่ง และมักมีประโยชน์ต่อองค์กรมากที่สุด**

> **บทเรียนสำคัญของ Near Miss**: *"เหตุการณ์ที่เกือบเกิด คือสัญญาณเตือนภัยล่วงหน้าที่ระบบมอบให้มาฟรี โดยที่องค์กรยังไม่ต้องจ่ายค่าเสียหายจริง"*

## 3. โครงสร้างมาตรฐานของเอกสาร Postmortem (Document Structure)

เอกสาร Postmortem ที่มีประสิทธิภาพประกอบด้วย 7 ส่วนหลัก โดยแต่ละส่วนมีหน้าที่ตอบคำถามที่เฉพาะเจาะจงและมุ่งตอบสนองกลุ่มผู้มีส่วนได้ส่วนเสียที่แตกต่างกัน:

### 3.1 เจ็ดองค์ประกอบหลักและหน้าที่ของแต่ละส่วน

| องค์ประกอบหลัก | หน้าที่และเนื้อหาที่ต้องระบุ | วัตถุประสงค์และความสำคัญ |
| :--- | :--- | :--- |
| **1. สรุป (Summary)** | เนื้อหา 3 ประโยคที่กระชับ อธิบายภาพรวมเหตุการณ์ ผลกระทบ และการแก้ไขหลัก | คนภายนอกและผู้บริหารจำนวนมากอ่านเฉพาะส่วนนี้เพื่อทำความเข้าใจภาพรวม |
| **2. ผลกระทบ (Impact)** | ข้อมูลเชิงปริมาณ: จำนวนผู้ใช้ที่กระทบ, จำนวนคำขอที่ล้มเหลว, เวลาที่หยุดชะงัก, งบประมาณความผิดพลาดที่ถูกใช้ | บันทึกเป็นตัวเลขสถิติ เพื่อใช้เปรียบเทียบระดับความเสียหายกับเหตุการณ์อื่นได้ |
| **3. ลำดับเหตุการณ์ (Timeline)** | รายการเหตุการณ์ตามแกนเวลาจริง เปรียบเทียบระหว่างสิ่งที่เกิดขึ้นในระบบ กับสิ่งที่ทีมรับรู้ ณ ขณะนั้น | แยกข้อเท็จจริงออกจากสิ่งที่รับรู้ เพื่อวิเคราะห์ช่องว่างในการตัดสินใจ |
| **4. ปัจจัยร่วม (Contributing Factors)** | เงื่อนไข ข้อจำกัด และสภาพแวดล้อมทั้งหมดที่เอื้อให้เหตุการณ์เกิดขึ้นได้ | ใช้คำว่าปัจจัยร่วมแทนสาเหตุเดียว เพราะระบบซับซ้อนแทบไม่เคยล่มจากปัจจัยโดดเดี่ยว |
| **5. การตรวจพบและการตอบสนอง (Detection & Response)** | ระยะเวลาที่ใช้ในแต่ละขั้นตอน (เวลาตรวจพบ, เวลาเริ่มตอบสนอง, เวลาบรรเทาผลกระทบ) | ระบุให้ชัดเจนว่าจุดอ่อนของระบบอยู่ที่กระบวนการตรวจจับ หรืออยู่ที่ขั้นตอนการแก้ไข |
| **6. ทำได้ดี · ทำได้ไม่ดี · โชคช่วย (Lessons Learned & Where We Got Lucky)** | สามมิติของการประเมินการทำงานอย่างซื่อสัตย์ รวมถึงปัจจัยบังเอิญที่ช่วยลดผลกระทบ | จุดที่โชคช่วยคือจุดเปราะบางที่ระบบต้องรีบแก้ไข เพราะโชคดีไม่ได้เกิดขึ้นทุกครั้ง |
| **7. สิ่งที่ต้องทำ (Action Items)** | รายการมาตรการแก้ไขเชิงวิศวกรรม ระบุผู้รับผิดชอบ วันกำหนดเสร็จ และวิธีตรวจรับงาน | เป็นส่วนเดียวของเอกสารที่สร้างความเปลี่ยนแปลงเชิงโครงสร้างอย่างแท้จริง |

> **กฎเหล็กการวิเคราะห์**: *"ถ้าเอกสารระบุว่าสาเหตุคือคนคนหนึ่ง แปลว่าเอกสารยังเขียนไม่เสร็จ — ให้ตั้งคำถามต่อไปจนกว่าจะได้เงื่อนไขเชิงระบบที่ยอมให้เหตุการณ์นี้เกิดขึ้นได้"*

### 3.2 การจัดทำบันทึกลำดับเหตุการณ์ (Timeline Analysis)
หัวใจของการวิเคราะห์ลำดับเหตุการณ์คือการ **"แยกสิ่งที่เป็นจริง ออกจากสิ่งที่รับรู้ ณ ขณะนั้น"** เพื่อให้เห็นช่องว่าง (Detection Gap) ทางวิศวกรรม:

```
[แผนภาพเปรียบเทียบลำดับเวลา: ข้อเท็จจริง vs การรับรู้]
02:10               02:14                          02:40                      03:10
  |-------------------|------------------------------|--------------------------|
  ^                   ^                              ^                          ^
ดิสก์เต็มจริง        บริการเริ่มปฏิเสธคำขอ           ทีมเพิ่งรู้ว่ามีปัญหา      บริการกลับคืนสภาพ
(Ground Truth)      (User Affected)                (และคิดว่าเป็นเครือข่าย)   (Mitigated)
                                                     |<-- เข้าใจผิด 15 นาที -->|
```

| มิติการวิเคราะห์ลำดับเวลา | รายละเอียดข้อเท็จจริงทางเทคนิค | นัยสำคัญทางวิศวกรรม SRE |
| :--- | :--- | :--- |
| **สิ่งที่เกิดขึ้นจริง (Ground Truth)** | ดิสก์เต็มตั้งแต่เวลา 02:10 และบริการเริ่มปฏิเสธคำขอของผู้ใช้ตั้งแต่เวลา 02:14 | สภาพความเป็นจริงของระบบที่ไม่ขึ้นกับว่ามนุษย์จะรับรู้หรือไม่ |
| **สิ่งที่ทีมรู้ ณ ขณะนั้น (Situational Awareness)** | เวลา 02:40 ทีมเพิ่งรับรู้ว่ามีปัญหา และเข้าใจผิดคิดว่าเกิดจากระบบเครือข่ายขัดข้อง | ภาพที่ทีมเห็นจากข้อมูลที่มีจำกัดในขณะเกิดเหตุ |
| **ช่องว่างระหว่างสองมิติ (Detection Gap)** | ระบบมีปัญหาต่อเนื่องนานถึง 30 นาทีโดยไม่มีวิศวกรหรือระบบตรวจวัดใดรับรู้ | **ปัญหาที่แท้จริงคือความล้มเหลวของการตรวจจับ (Detection)** ไม่ใช่ความเร็วในการแก้ |
| **ตัวชี้วัดที่ใช้วัดผลได้ (Engineering Metrics)** | แยกแยะและวัดผลเวลาตรวจพบ (TTD), เวลาบรรเทา (TTM) และเวลากู้คืน (TTR) | แยกตัวชี้วัดออกจากกันอย่างเด็ดขาดเพื่อปรับปรุงเครื่องมือให้ถูกจุด |

> **คำเตือนทางจิตวิทยา**: *"การเขียน Timeline ด้วยความรู้ของวันนี้ จะทำให้ทุกการตัดสินใจในอดีตดูโง่เขลา — วิศวกรต้องบันทึกว่า ณ เวลานั้นผู้ปฏิบัติงานมีข้อมูลอะไรอยู่ในมือ ไม่ใช่เขียนด้วยข้อมูลที่เพิ่งมารู้หลังจากระบบล่มแล้ว"*

---

## 4. ทำไมการโทษคนจึงไม่ได้ผล (Why Blaming Fails & Human Factors)

> **หลักคิดเชิงวิศวกรรม**: *"การไม่โทษคนไม่ใช่เรื่องของความใจดีหรือมารยาท แต่เป็นเรื่องของการสร้างสภาวะแวดล้อมที่ทำให้ได้ข้อมูลเชิงลึกที่นำไปใช้งานได้จริง"*

### 4.1 สามอคติที่ทำให้วิเคราะห์ผิดทาง (Cognitive Biases in Incident Analysis)
ในการสอบสวนสาเหตุของอุบัติเหตุ มนุษย์มักตกหลุมพรางทางความคิด 3 ประการโดยไม่รู้ตัว:

```
+-----------------------------------------------------------------------------------+
|                        สามอคติทางจิตวิทยาที่บิดเบือนการวิเคราะห์                   |
+-----------------------------------------------------------------------------------+
| 1. Hindsight Bias           | มองย้อนหลังแล้วคิดว่าสัญญาณเตือนชัดเจนแต่แรก        |
| 2. Counterfactual Reasoning | สร้างประโยค "ถ้าเขาทำอย่างนั้น..." ซึ่งไร้ประโยชน์   |
| 3. First Story vs 2nd Story | หยุดอยู่ที่ "คนทำผิด" แทนที่จะถามว่า "ทำไมเขาจึงทำ" |
+-----------------------------------------------------------------------------------+
```

1. **อคติมองย้อนหลัง (Hindsight Bias)**:
   - เมื่อทราบผลลัพธ์ของเหตุการณ์แล้ว สัญญาณเตือนหรือร่องรอยที่เคยคลุมเครือจะดูเหมือนชัดเจนขึ้นมาทันที ทำให้ผู้สอบสวนคิดตัดสินไปเองว่าผู้ปฏิบัติงานในเหตุการณ์ควรจะมองเห็นสัญญาณนั้นตั้งแต่แรก
2. **การให้เหตุผลแย้งข้อเท็จจริง (Counterfactual Reasoning)**:
   - การเขียนหรือวิเคราะห์ว่า *"ถ้าวิศวกรทำขั้นตอนนั้นแทน ปัญหาก็คงไม่เกิด"* ประโยคลักษณะนี้อธิบายถึงโลกสมมุติที่ไม่ได้เกิดขึ้นจริง และไม่ได้ให้แนวทางว่าระบบต้องปรับปรุงกลไกป้องกันอย่างไร
3. **เรื่องเล่าชั้นที่สอง (Second Story)**:
   - แนวคิดจากงานวิจัยของ **Sidney Dekker** (*The Field Guide to Understanding 'Human Error'*):
     - **เรื่องเล่าชั้นที่หนึ่ง (First Story)**: หยุดอยู่ที่ข้อสรุปว่ามนุษย์ทำงานผิดพลาด ประมาท หรือไม่ปฏิบัติตามขั้นตอน
     - **เรื่องเล่าชั้นที่สอง (Second Story)**: ศึกษาสภาพแวดล้อม แรงกดดัน เครื่องมือ และข้อมูลที่มีอยู่ในขณะนั้น เพื่อทำความเข้าใจว่าทำไมการตัดสินใจดังกล่าวจึงดูสมเหตุสมผลสำหรับเขา ณ เวลานั้น

> **หลักการตั้งต้นของ Second Story**: *"สมมติฐานว่าทุกคนตัดสินใจอย่างสมเหตุสมผลที่สุดจากข้อมูล เครื่องมือ และแรงกดดันที่มีอยู่ในเวลานั้น แล้วจึงตั้งคำถามว่า เหตุใดการกระทำนั้นจึงดูสมเหตุสมผลในสายตาของเขา"*

### 4.2 การวิเคราะห์เหตุการณ์เดียวกันด้วยคำถามสองแบบ (Person vs. System Approach)
การเปรียบเทียบระหว่างการหยุดคำถามไว้ที่ตัวบุคคล กับการถามเจาะลึกต่อไปจนถึงโครงสร้างระบบ:

```
[เปรียบเทียบการสืบค้น 5 Whys: หยุดที่ตัวคน vs ถามลึกถึงระบบ]

แนวทางที่ 1: หยุดที่ตัวบุคคล (Person Approach)
เครื่องหลุดออกจากแผน VLAN
  └── ทำไม? วิศวกรแก้ไขค่าคอนฟิกบนสวิตช์ด้วยมือ
        └── ทำไม? เพราะรีบทำงานให้เสร็จ
              ├── สรุปสาเหตุ: ความผิดพลาดและความประมาทของบุคคล
              └── มาตรการแก้ไข: ตักเตือนทีมงานให้ใช้ความระมัดระวังมากขึ้น

----------------------------------------------------------------------

แนวทางที่ 2: ถามต่อไปจนถึงโครงสร้างระบบ (System Approach)
เครื่องหลุดออกจากแผน VLAN
  └── ทำไม? ค่าบนสวิตช์ถูกแก้ไขด้วยมือ
        └── ทำไม? ไม่มีเส้นทางหรือเครื่องมือที่ผ่านการทบทวนโค้ด (Code Review) ให้แก้ไขค่านั้น
              └── ทำไม? ค่าพอร์ตสวิตช์ไม่เคยถูกนำเข้าสู่ระบบจัดการแบบโค้ด (Infrastructure as Code)
                    └── ทำไม? ไม่มีเจ้าของระบบรับผิดชอบการจัดการโครงสร้างพื้นฐานในรูปแบบโค้ด
                          ├── ปัจจัยร่วม: ไม่มีเส้นทางทบทวน, ขาดเจ้าของระบบ, ไม่มีการตรวจจับการเบี่ยงเบน
                          └── มาตรการแก้ไข: นำคอนฟิกพอร์ตเข้าสู่ Git กำหนดสิทธิ์ทบทวน และสร้างระบบแจ้งเตือน Drift
```

> **ข้อสังเกตเชิงลบของคำตักเตือน**: *"คำสั่งว่า 'ให้ระมัดระวังมากขึ้น' ไม่ใช่ Action Item เพราะมอบหมายงานให้ใครไม่ได้ กำหนดวันเสร็จไม่ได้ ตรวจวัดผลไม่ได้ และเมื่อวิศวกรคนถัดไปเหนื่อยล้าหรืออยู่ภายใต้แรงกดดัน ความผิดพลาดเดิมก็จะเกิดขึ้นซ้ำอีก"*

---

## 5. การค้นหาปัจจัยร่วมแทนการยึดติดกับสาเหตุเดียว (Contributing Factors vs. Root Cause)

> **สัจธรรมในระบบวิศวกรรม**: *"ในระบบที่มีความซับซ้อน (Complex Systems) แทบไม่มีเหตุการณ์ใดเกิดขึ้นจากสาเหตุเพียงข้อเดียว"*

### 5.1 ทำไมจึงไม่ควรใช้คำว่าสาเหตุราก (The Myth of Root Cause)
คำว่า **"สาเหตุรากเหง้า" (Root Cause)** สร้างภาพลวงตาทางวิศวกรรมและกระตุ้นให้ทีมงานรีบด่วนสรุปเพื่อยุติการสอบสวนเร็วเกินไป:

- **อุบัติการณ์จริงต้องการเงื่อนไขประกอบพร้อมกันหลายชั้น**:
  - ตัวอย่างเช่น: ดิสก์เต็ม + ไม่มีการเฝ้าระวังพื้นที่ + ระบบแจ้งเตือน (Alert) ถูกปิดเสียง (Muted) ไว้ หากขาดเงื่อนไขใดเงื่อนไขหนึ่ง เหตุการณ์ขัดข้องย่อมไม่ลุกลามจนบริการล่ม
- **การหยุดที่สาเหตุเดียวทำให้แก้ไขระบบไม่ครอบคลุม**:
  - หากสรุปว่าเหตุเกิดจากดิสก์เต็มแล้วแก้ไขเพียงแค่เพิ่มความจุดิสก์ ในครั้งถัดไประบบก็จะยังคงตรวจจับปัญหาล่าช้าเช่นเดิม
- **ถามว่าอะไรทำให้เรื่องนี้เป็นไปได้ (Systemic Enabling Conditions)**:
  - แทนที่จะถามว่า *"ใครทำให้เกิด"* (ซึ่งจะได้เพียงชื่อคน) ให้เปลี่ยนเป็นถามว่า *"สภาพแวดล้อมใดในระบบที่ยอมให้เรื่องนี้เกิดขึ้นได้"* (จะได้รายการจุดบกพร่องที่แก้ไขได้จริง)
- **แยกแยะปัจจัยที่ทำให้ตรวจพบช้า (Detection Factors)**:
  - สาเหตุที่ทำให้ระบบพัง กับปัจจัยที่ทำให้ตรวจพบปัญหาช้า เป็นคนละประเด็นกันและต้องได้รับการวิเคราะห์แยกจากกันอย่างชัดเจน

### 5.2 การแจกแจงปัจจัยร่วมและการป้องกันการเกิดซ้ำ
แนวทางปฏิบัติที่ถูกต้องคือการจัดทำ **"รายการปัจจัยร่วม" (List of Contributing Factors)** แล้วประเมินจัดลำดับความสำคัญว่า หากตัดปัจจัยข้อใดออกไป จะช่วยลดความน่าจะเป็นในการเกิดเหตุการณ์ซ้ำซ้อนได้สูงที่สุด

## 6. การกำหนด Action Item ที่สร้างความเปลี่ยนแปลงจริง (Effective Action Items)

Action Item คือส่วนประกอบที่สำคัญที่สุดของ Postmortem เพราะเป็นส่วนเดียวที่เปลี่ยนการถอดบทเรียนให้กลายเป็นการป้องกันเชิงรูปธรรม การทดสอบ Action Item ให้พิจารณาว่า: **"มอบหมายให้บุคคลได้ไหม, กำหนดวันเสร็จได้ไหม, และตรวจวัดผลการติดตั้งได้ไหม"**

### 6.1 การเปรียบเทียบ Action Item ที่ใช้ได้ กับที่ใช้ไม่ได้

| ข้อความ Action Item ที่ใช้ไม่ได้ (Flawed) | ปัญหาเชิงโครงสร้างและเหตุผลที่ใช้ไม่ได้ | การปรับปรุงเขียนใหม่ให้ใช้งานได้จริง (Effective Action Item) |
| :--- | :--- | :--- |
| **ให้ระมัดระวังมากขึ้น** | มอบหมายให้ใครไม่ได้ ตรวจวัดผลไม่ได้ และไม่ได้ปรับเปลี่ยนเงื่อนไขเชิงระบบใด ๆ เลย | **เพิ่มขั้นตอนการยืนยัน (Confirmation Prompt)** ก่อนคำสั่งลบข้อมูล โดยบังคับให้ระบบแสดงชื่อเครื่องและรอการพิมพ์ยืนยัน |
| **ปรับปรุงการเฝ้าระวัง** | เนื้อหากว้างเกินไป ไม่มีใครทราบขอบเขตที่แน่ชัด และไม่รู้ว่าจะวัดผลความสำเร็จเมื่อใด | **เพิ่ม Alert แจ้งเตือนเมื่อพื้นที่ดิสก์เหลือน้อยกว่า 20%** และส่งออกเป็น Ticket งานให้ทีมดูแล โดยกำหนดเสร็จภายในวันที่ ... |
| **อบรมทีมงานเพิ่มเติม** | โยนภาระความผิดพลาดกลับไปที่มนุษย์ ทั้งที่ต้นตอของปัญหาเกิดจากข้อบกพร่องของระบบ | **จัดทำคู่มือปฏิบัติการ (Runbook)** สำหรับกระบวนการนี้ให้ชัดเจน พร้อมแนบลิงก์เชื่อมโยงไว้ในข้อความแจ้งเตือน (Alert) ทันที |
| **ทบทวนกระบวนการ** | ไม่มีเจ้าของงานที่รับผิดชอบโดยตรง และไม่มีผลลัพธ์เชิงรูปธรรมที่สามารถตรวจรับได้ | **แก้ไขเกณฑ์การประกาศ Incident** ให้ครอบคลุมความผิดปกติของระบบจัดเก็บข้อมูล โดยมอบหมายให้วิศวกร ก. เป็นผู้รับผิดชอบส่งงานภายในวันที่ ... |

### 6.2 เกณฑ์การจัดลำดับความสำคัญของงานแก้ไข
การจัดลำดับความสำคัญของ Action Item ให้ใช้การประเมิน 2 แกนหลัก:

```
                  [แกนการตัดสินใจเลือก Action Item]
                  
                 ประสิทธิผลในการลดโอกาสเกิดซ้ำ (Impact)
                                สูง
                                 |
              [ทำทันที: Quick Wins] | [วางแผนทำ: Major Projects]
              - ได้ผลสูง / ใช้แรงน้อย  | - ได้ผลสูง / ใช้แรงมาก
       --------------------------+--------------------------
              - ได้ผลต่ำ / ใช้แรงน้อย  | - ได้ผลต่ำ / ใช้แรงมาก
              [ทำเมื่อว่าง: Fill-in] | [ตัดทิ้ง: Drop / Avoid]
                                 |
                                ต่ำ
         น้อย <----------------------------------------> มาก
                         ภาระงานและเวลาที่ใช้ (Effort)
```

> **กฎการลงมือทำ**: *"ข้อความที่ได้ผลตอบแทนสูงและใช้แรงน้อย (High Impact, Low Effort) ต้องได้รับการดำเนินการก่อนเสมอ"*

## 7. วัฒนธรรมและจริยธรรมของ SRE (SRE Culture & Professional Ethics)

> **หลักการบริหารจัดการ**: *"กระบวนการทางวิศวกรรมที่ดี จะดำรงอยู่ได้จริงก็ต่อเมื่อมีวัฒนธรรมที่ทำให้คนกล้าพูดความจริงรองรับอยู่"*

### 7.1 สิ่งที่ทำให้กระบวนการดำรงอยู่ได้จริง vs การกลายเป็นพิธีกรรม
ปัจจัยชี้ขาดว่า Postmortem จะกลายเป็นเครื่องมือพัฒนาองค์กร หรือกลายเป็นเพียงพิธีกรรมที่ไร้ความหมายภายใน 3 เดือน:

- **ความปลอดภัยทางจิตใจ (Psychological Safety)**:
  - บุคลากรต้องมีความเชื่อมั่นว่า การบอกเล่าข้อเท็จจริงและความผิดพลาดตามตรงจะไม่ส่งผลกระทบต่อความมั่นคงในหน้าที่การงาน หากขาดความปลอดภัย ข้อมูลที่ได้ในเอกสารจะถูกบิดเบือนและไม่สะท้อนความเป็นจริง
- **ผู้นำต้องเป็นแบบอย่างในการยอมรับความผิดพลาด (Leadership Vulnerability)**:
  - หากวิศวกรอาวุโสหรือผู้บริหารไม่เคยยอมรับความผิดพลาดของตนเองอย่างเปิดเผย สมาชิกคนอื่นในองค์กรจะไม่มีวันกล้ายอมรับข้อผิดพลาดเช่นเดียวกัน
- **งบประมาณความผิดพลาดเป็นเครื่องมือทางวัฒนธรรม (Error Budget as Cultural Tool)**:
  - เปลี่ยนการถกเถียงที่ใช้อารมณ์ความรู้สึกและความขัดแย้งส่วนบุคคล ให้กลายเป็นการตัดสินใจบนฐานตัวเลขและข้อตกลงที่กำหนดไว้ล่วงหน้า
- **ความยั่งยืนของทีมงาน (Team Sustainability & On-call Health)**:
  - การเข้าเวรที่ระบบปลุกเรียกบ่อยเกินไปจนรบกวนเวลาพักผ่อนจะนำไปสู่ภาวะหมดไฟ (Burnout) และการลาออก สถิติจำนวนครั้งที่ทีมงานถูกปลุกนอกเวลาทำงานต่อกะเวร คือตัวชี้วัดที่ต้องเฝ้าระวังอย่างใกล้ชิดเทียบเท่ากับ SLO

> **สัญญาณเตือนภัยของพิธีกรรม**: *"ถ้าเอกสาร Postmortem ฉบับหลัง ๆ มีเนื้อหาสั้นลงเรื่อย ๆ และไม่มีข้อถกเถียงเชิงวิศวกรรมในที่ประชุม แปลว่ากระบวนการนั้นได้กลายเป็นพิธีกรรมที่ตายซากไปแล้ว"*

### 7.2 ประเด็นจริยธรรมที่ต้องตัดสินใจในสถานการณ์จริง
ในโลกความเป็นจริงไม่มีคำตอบสำเร็จรูป แต่วิศวกรต้องตัดสินใจอย่างมีสติและสามารถอธิบายเหตุผลทางจริยธรรมได้:

1. **ความโปร่งใสต่อผู้ใช้งาน (Transparency to Users)**:
   - การเปิดเผยข้อมูลเมื่อระบบล่มต้องรักษาสมดุล: การบอกข้อมูลน้อยเกินไปจะทำลายความไว้วางใจ แต่การบอกรายละเอียดเชิงลึกมากเกินไปอาจเปิดเผยช่องโหว่ให้ผู้ไม่หวังดีใช้โจมตีซ้ำ
2. **การเปิดเผยเมื่อเกิดเหตุข้อมูลรั่วไหล (Data Breach Disclosure)**:
   - นอกเหนือจากข้อกำหนดตามกฎหมาย (เช่น PDPA) แล้ว ในเชิงจริยธรรม ความเร็วในการแจ้งเตือนผู้ที่ได้รับผลกระทบมีความสำคัญยิ่งกว่าการรอรวบรวมข้อมูลให้ครบถ้วน 100%
3. **การไม่ระบุตัวบุคคลต่อสาธารณะ (Anonymity in Public Reports)**:
   - รายงานเหตุการณ์ที่เผยแพร่สู่สาธารณะต้องไม่ระบุชื่อบุคคลที่พิมพ์คำสั่งผิดพลาด องค์กรต้องเป็นผู้แบกรับความรับผิดชอบร่วมกัน ไม่ใช่ผลักภาระไปที่พนักงานเพียงคนเดียว
4. **ความรับผิดชอบต่อผู้ใช้จำนวนมาก (Responsibility to Massive User Base)**:
   - เมื่อระบบมีผู้ใช้งานหลักพันหรือหลักหมื่นคน การตัดสินใจเชิงเทคนิคทุกอย่างย่อมส่งผลกระทบโดยตรงต่อชีวิตและการทำงานของผู้คนในสังคม

> **บริบทของรายวิชา**: *"ระบบแม่ข่ายของคณะฯ มีนักศึกษา อาจารย์ และบุคลากรใช้งานจริง การตัดสินใจทางวิศวกรรมในการปฏิบัติการจึงไม่ใช่สถานการณ์สมมุติ"*

## 8. แนวทางปฏิบัติการทดลองและการตรวจประเมินร่วมกัน (Lab Exercise & Peer Review)

### 8.1 หกขั้นตอนการปฏิบัติการ: เขียนแล้วแลกกันตรวจ
การทดลองกำหนดให้นำข้อมูลเหตุการณ์ขัดข้องจริงที่เกิดขึ้นระหว่างการติดตั้งระบบในสัปดาห์ก่อนหน้ามาจัดทำรายงาน:

```
[วงจร 6 ขั้นตอนของปฏิบัติการ Postmortem]
1. รวบรวมข้อมูล ---------> 2. คำนวณผลกระทบ ---------> 3. แจกแจงปัจจัยร่วม
   (ดึง Timeline จริง)       (ระบุเป็นตัวเลขสถิติ)        (ถามจนพ้นความผิดคน)
                                                            |
6. แลกเปลี่ยนตรวจ <------- 5. กำหนด Action Item <------- 4. ประเมินสามด้าน
   (ตรวจตามเช็กลิสต์)         (มีเจ้าของและกำหนดวัน)       (ดี / เสีย / โชคช่วย)
```

1. **รวบรวมข้อเท็จจริง (Gathering Facts)**: ดึงข้อมูลบันทึกลำดับเวลา (Timeline) จากบันทึกหน้างานจริง
2. **เขียนผลกระทบ (Quantify Impact)**: คำนวณความเสียหายเป็นตัวเลขเชิงปริมาณ ไม่ใช้เพียงคำบรรยายเชิงคุณภาพ
3. **หาปัจจัยร่วม (Identify Contributing Factors)**: ตั้งคำถามเจาะลึกจนพ้นการระบุชื่อบุคคล
4. **เขียนสามหัวข้อประเมิน (Three Perspectives)**: สรุปสิ่งที่ทำได้ดี สิ่งที่ทำได้ไม่ดี และสิ่งที่รอดพ้นเพราะโชคช่วย
5. **ตั้ง Action Item (Define Action Items)**: กำหนดงานแก้ไขที่มีผู้รับผิดชอบและวันแล้วเสร็จชัดเจน
6. **แลกกันตรวจ (Peer Review)**: แลกเปลี่ยนเอกสารกับกลุ่มอื่นเพื่อตรวจสอบตามเช็กลิสต์มาตรฐาน

> **คำเตือนในการจัดทำเอกสาร**: *"เขียนจากเหตุการณ์จริงของกลุ่มตนเอง — หากกลุ่มใดอ้างว่าไม่มีเหตุการณ์เกิดขึ้น แปลว่าบันทึกข้อมูลไม่ครบถ้วน ไม่ใช่แปลว่าระบบไม่มีปัญหา"*

### 8.2 เช็กลิสต์การตรวจประเมินเอกสารของกลุ่มอื่น (Review Checklist)
แบบฟอร์มตรวจสอบสำหรับการตรวจประเมินและส่งคืนพร้อมข้อเสนอแนะเชิงสร้างสรรค์:

| รายการตรวจสอบคุณภาพของเอกสาร Postmortem | เกณฑ์การพิจารณา |
| :--- | :--- |
| [ ] **สรุปสามประโยคอ่านแล้วเข้าใจ โดยไม่ต้องรู้บริบทมาก่อน** | มี / ไม่มี |
| [ ] **ผลกระทบระบุเป็นตัวเลขเชิงสถิติ ไม่ใช่คำบรรยายความรู้สึก** | มี / ไม่มี |
| [ ] **Timeline แยกสิ่งที่เป็นจริง ออกจากสิ่งที่ทีมรับรู้ในเวลานั้น** | มี / ไม่มี |
| [ ] **ไม่มีประโยคหรือข้อความใดที่ระบุว่าบุคคลเป็นสาเหตุของปัญหา** | ตรวจสอบละเอียดทุกบรรทัด |
| [ ] **มีการแจกแจงปัจจัยร่วมเชิงระบบมากกว่าหนึ่งข้อขึ้นไป** | นับจำนวนปัจจัยร่วม |
| [ ] **ทุก Action Item มีผู้รับผิดชอบ กำหนดวันเสร็จ และวิธีตรวจรับงาน** | นับจำนวนข้อที่ข้อมูลไม่ครบถ้วน |

> **มารยาทของการตรวจประเมินแบบ Blameless**: *"หากตรวจพบข้อความที่กล่าวโทษบุคคล ให้เขียนข้อเสนอแนะว่าควรปรับปรุงประโยคนั้นใหม่อย่างไรในเชิงระบบ ไม่ใช่เพียงแค่ชี้ว่าประโยคนั้นผิด — นั่นคือการปฏิบัติการแบบ Blameless เช่นเดียวกัน"*

## 9. บทสรุปสามประโยคประจำคาบ (Three-Sentence Summary)

```
[บทสรุปสามประโยคแห่งสัปดาห์]
1. ถ้าเป้าหมายคือหาคนผิด ครั้งหน้าจะไม่มีใครบอกความจริง — เอกสารที่สร้างความหวาดกลัวจะได้ข้อมูลที่บิดเบี้ยวและองค์กรจะไม่เกิดการเรียนรู้
2. ในระบบที่ซับซ้อนแทบไม่เคยมีสาเหตุเดียว — การถามว่าอะไรทำให้เรื่องนี้เป็นไปได้จะได้รายการสิ่งที่แก้ไขได้ ส่วนการถามว่าใครทำจะได้แค่ชื่อคน
3. Action Item คือส่วนเดียวที่ทำให้อะไรรอบตัวเปลี่ยนจริง — ข้อความที่มอบหมายไม่ได้ กำหนดวันไม่ได้ และตรวจวัดไม่ได้ มีค่าเท่ากับไม่ได้เขียนอะไรไว้เลย
```

## 11. คำอธิบายเสริมและบริบทเชิงปฏิบัติการจริงจากผู้สอน (Instructor Insights & Lab Realities)

### 11.1 ปรัชญา SRE vs DevOps และการทลายกำแพงระหว่างทีม (SRE vs. DevOps & Breaking Team Silos)
- **ปัญหาเรื้อรังของการแบ่งแยกส่วนงาน (Silo Mentality)**:
  - ผู้สอนชี้ให้เห็นว่าในองค์กรไอทีทั่วไป ทีมโครงสร้างพื้นฐาน (Infrastructure Team), ทีมเซิร์ฟเวอร์ (Server Team), ทีมเครือข่าย (Network Team) และทีมนักพัฒนา (Development Team) มักทำงานแบบแยกส่วนและโยนภาระให้แก่กันเมื่อเกิดปัญหา
  - คำพูดที่พบบ่อยในการทำงาน: *"ฝั่งฉันตรวจสอบแล้วว่าระบบปกติ ปัญหาน่าจะเกิดจากฝั่งของเธอ"* ผลลัพธ์คือการโต้เถียงที่ไม่มีวันยุติ เพราะต่างฝ่ายต่างพยายามปกป้องขอบเขตความรับผิดชอบของตนเอง โดยไม่มีใครมองไปที่ผลกระทบของผู้ใช้งาน (User Experience)
- **DevOps ไม่ควรเป็นชื่อตำแหน่งงาน (DevOps is a Culture, Not a Job Title)**:
  - ในตลาดแรงงานปัจจุบันมักมีการเปิดรับสมัครตำแหน่ง "DevOps Engineer" ซึ่งผู้สอนระบุว่าเป็นการนำคำศัพท์ไปใช้ผิดบริบท แท้จริงแล้ว DevOps คือ **"กรอบความคิด (Mindset) และวัฒนธรรมการประสานงาน"** ระหว่างฝ่ายพัฒนาซอฟต์แวร์กับฝ่ายปฏิบัติการ ไม่ใช่วิชาชีพเดี่ยว
- **ขอบเขตและความรับผิดชอบของ SRE ที่เหนือกว่า DevOps**:
  - วิศวกร DevOps ทั่วไปมักจำกัดบทบาทอยู่เพียงการสร้าง Virtual Machine (VM), การสร้าง Container, การเขียนสคริปต์อัตโนมัติ และการสร้าง Continuous Integration / Continuous Deployment (CI/CD) Pipeline
  - ในทางกลับกัน **วิศวกร SRE (Site Reliability Engineer)** ครอบคลุมทักษะด้าน Automation ทั้งหมดของ DevOps แต่ขยายมุมมองไปสู่ความน่าเชื่อถือทั้งระบบ โดยประเมินว่าผู้ใช้งานปลายทางสามารถเข้าถึงบริการได้จริงหรือไม่ และมีระบบตรวจวัดความสามารถในการสังเกต (Observability) คอยเฝ้าระวังอยู่ตลอดเวลา อาชีพ SRE จึงมีขอบเขตงานที่กว้างขวาง ลึกซึ้ง และมีมูลค่าผลตอบแทนในตลาดสูงกว่า
- **วัฒนธรรมการสื่อสารแบบมืออาชีพ**:
  - ผู้สอนเน้นย้ำถึงการสื่อสารตรงไปตรงมา โดยแยกแยะระหว่าง "เรื่องงานเชิงเทคนิค" ออกจาก "ความรู้สึกส่วนบุคคล" ไม่นำความผิดพลาดในงานมาเป็นเรื่องบาดหมางหรือคิดเล็กคิดน้อย เพื่อให้ทีมสามารถมุ่งเน้นไปที่การแก้ไขปัญหาเชิงระบบได้อย่างแท้จริง

### 11.2 กรณีศึกษาจริง: โน้ตบุ๊กตกพื้น และเหตุการณ์สายไฟสวิตช์หลุดในตู้แร็ค (Physical Incidents & Systemic Thinking)
- **กรณีศึกษาที่ 1: โน้ตบุ๊กประจำห้องปฏิบัติการ 10/2 ตกกระแทกพื้นพัง**:
  - *ข้อเท็จจริง (Fact)*: โน้ตบุ๊กในห้องปฏิบัติการตกลงมากระแทกพื้นจนเสียหาย โดยไม่มีนักศึกษาคนใดเจตนาทุ่มเครื่องลงพื้น
  - *การตอบสนองแบบดั้งเดิม vs แบบ Blameless*:
    - แนวทางเดิม: มุ่งเปิดกล้องวงจรปิดเพื่อตามหาตัวนักศึกษาที่ทำตกแล้วบังคับให้ชดใช้ค่าเสียหาย
    - แนวทาง Blameless: ทีมงานยอมรับข้อเท็จจริงว่าเครื่องชำรุดและแจ้งทีมโครงสร้างพื้นฐานเพื่อจัดหาเครื่องทดแทน จากนั้นวิเคราะห์เชิงระบบพบว่า **"โต๊ะเรียนมีปัญหาเรื่องล้อเลื่อนที่ไม่ล็อก และการทิ้งน้ำหนักลงบนขอบโต๊ะทำให้โต๊ะเอียงคว่ำได้ง่าย"**
    - *การแก้ไขเชิงระบบ (Knowledge Management)*: กำหนดให้เลิกจัดซื้อโต๊ะรุ่นดังกล่าว และในห้องเรียนอื่นได้มีการติดตั้งจอภาพยึดติดกับผนังอย่างถาวร เพื่อขจัดความเสี่ยงที่อุปกรณ์จะร่วงหล่นซ้ำ
- **กรณีศึกษาที่ 2: การเลื่อนเซิร์ฟเวอร์เข้าตู้แร็คแล้วชนสายไฟสวิตช์หลุด (Power Cable Dislodged)**:
  - *สถานการณ์สมมุติในการทำแล็บ Data Center*: นักศึกษานำเครื่องเซิร์ฟเวอร์เข้าไปติดตั้งในตู้แร็ค แล้วดันเซิร์ฟเวอร์เข้าไปจนไปเบียดสายไฟของ ToR Switch หลุด ทำให้สวิตช์ดับและเครือข่ายของศูนย์ข้อมูลหยุดทำงานทั้งหมด
  - *การวิเคราะห์แบบหยุดที่ตัวบุคคล*: สรุปว่านักศึกษาทำงานประมาท และออกคำสั่งเตือนให้เพิ่มความระมัดระวัง
  - *การวิเคราะห์แบบเจาะลึกเชิงระบบ*:
    1. **ขาดขั้นตอนปฏิบัติการที่เป็นมาตรฐาน (Missing SOP / Checklist)**: ไม่มีระเบียบกำหนดว่าการติดตั้งอุปกรณ์ขนาดใหญ่ต้องใช้คนอย่างน้อย 2 คน โดยคนหนึ่งประคองด้านหน้าและอีกคนคอยระวังสายด้านหลังตู้
    2. **ขาดการจัดการสายสัญญาณและสายไฟ (Poor Cable Management)**: สายไฟของสวิตช์ถูกวางพาดขวางช่องเลื่อนรางเซิร์ฟเวอร์ โดยไม่มีแขนรัดสายหรือรางเก็บสายไฟ
    3. **ขาดขั้นตอนการตรวจสอบก่อนออกจากห้อง (Missing Post-Installation Verification)**: ผู้ปฏิบัติงานติดตั้งเสร็จแล้วปิดตู้เดินออกจากห้องทันที โดยไม่ได้เดินตรวจสอบไฟสถานะ (Status LEDs) ทั้งด้านหน้าและด้านหลังตู้ว่าอุปกรณ์ทุกตัวยังทำงานเป็นปกติหรือไม่

### 11.3 การวิเคราะห์ Timeline, ช่องว่างการตรวจพบ และการถอดบทเรียนสตอเรจเต็ม (Timeline Analysis & Storage Realities)
- **การแยกแยะมิติเวลาใน Timeline เพื่อชี้เป้าจุดบกพร่อง**:
  - ในเหตุการณ์ระบบจองห้องใช้งานไม่ได้:
    - เวลา 02:10 (หรือ 14:10 น.): พื้นที่จัดเก็บข้อมูล (Disk) เต็ม
    - เวลา 02:14 (หรือ 14:14 น.): บริการเริ่มปฏิเสธคำขอของผู้ใช้งาน
    - เวลา 02:40 (หรือ 14:40 น.): ทีมงานเพิ่งรับรู้ว่ามีปัญหา และเข้าใจผิดว่าเป็นปัญหาเครือข่าย
  - **ช่องว่าง 30 นาที (Detection Gap)** ชี้ชัดว่าจุดอ่อนของระบบอยู่ที่ **"การขาดระบบตรวจวัดและแจ้งเตือน (Lack of Monitoring & Alerting)"** ไม่ใช่ความช้าในการแก้ปัญหา เพราะเมื่อทีมตรวจพบต้นตอว่าดิสก์เต็ม ทีมสามารถขยายพื้นที่หรือลบไฟล์เพื่อบรรเทาปัญหาได้ในเวลาอันรวดเร็ว
- **ตัวชี้วัดที่ต้องบันทึกแยกจากกัน**:
  - **เวลาตรวจพบ (Time to Detect: TTD)**: ใช้เวลาตั้งแต่เกิดเหตุจนกระทั่งทีมรับรู้
  - **เวลาบรรเทาผลกระทบ (Time to Mitigate: TTM)**: ใช้เวลาตั้งแต่เริ่มแก้ไขจนกระทั่งบริการกลับมาเปิดทำงานได้ (เช่น การตัดสลับไประบบสำรอง หรือการเพิ่มทรัพยากรชั่วคราว)
  - **เวลากู้คืนระบบหลัก (Time to Restore / Recover: TTR)**: ใช้เวลาในการสืบสวนและแก้ไขระบบหลักให้กลับสู่สภาวะสมบูรณ์
- **บทเรียนการบริหารพื้นที่จัดเก็บข้อมูลจากประสบการณ์จริงของผู้สอน**:
  - ผู้สอนยกตัวอย่างงานของทีมสื่อสารดิจิทัล (Digital Communication: DC) ซึ่งมีการบันทึกไฟล์วิดีโอ Footage และภาพถ่ายความละเอียดสูงจำนวนมหาศาลลงบนสตอเรจส่วนกลาง
  - พื้นที่สตอเรจเต็มบ่อยครั้งจนต้องขยายขนาดจาก 10 TB เป็น 15 TB และ 20 TB แต่ก็ยังคงเต็มอย่างต่อเนื่อง เนื่องจากราคาของดิสก์ความเร็วสูง (High-Speed Storage) มีมูลค่าแพง ไม่สามารถขยายได้ไม่จำกัด
  - *การแก้ไขเฉพาะหน้า (Ad-hoc)*: ผู้สอนต้องคอยย้ายไฟล์เก่าลงฮาร์ดดิสก์ภายนอก (External HDD) เมื่อได้รับการแจ้งเตือน
  - *การแก้ไขเชิงระบบที่ยั่งยืน*: ต้องวางข้อกำหนดวงจรชีวิตข้อมูล (Data Lifecycle Policy) เช่น การกรองไฟล์ก่อนอัปโหลด การลบไฟล์ Footage ที่ไม่ได้ใช้งานทิ้งทันทีหลังตัดต่อเสร็จ และการย้ายไฟล์ที่เสร็จสิ้นเข้าสู่ระบบจัดเก็บถาวร (Archive Storage) อัตโนมัติ

### 11.4 เทคนิค 5 Whys จากงานออกแบบสู่งาน SRE และการก้าวข้าม Root Cause (5 Whys & Complex Systems)
- **การนำหลักการ 5 Whys มาประยุกต์ใช้**:
  - เทคนิคการถาม "ทำไม" ซ้ำ ๆ 5 ครั้ง เป็นเครื่องมือที่ยืมมาจากกระบวนการออกแบบ (Design Thinking) และการทดสอบการใช้งาน (Usability Testing) เพื่อค้นหาความต้องการและปัญหาที่แท้จริงของผู้ใช้
  - ในงาน SRE การถาม 5 Whys ต้องกระทำเพื่อ **"สาวลึกไปสู่เงื่อนไขเชิงระบบ"** ไม่ใช่การถามเพื่อต้อนให้คนจนมุมหรือหาตัวคนผิด
- **ภาพลวงตาของคำว่า Root Cause (The Fallacy of Root Cause)**:
  - ผู้สอนเตือนว่าการใช้คำว่า "Root Cause" มักทำให้ทีมงานด่วนสรุปปัญหาเร็วเกินไป (Premature Closure) ทั้งที่ในความเป็นจริง ระบบวิศวกรรมที่ซับซ้อน (Complex Systems) แทบไม่เคยล่มสลายจากปัจจัยโดดเดี่ยว
  - อุบัติการณ์ใหญ่เกิดจากการประกอบกันของข้อบกพร่องย่อยหลายประการ (Compounding Failures) หากขาดเงื่อนไขใดเงื่อนไขหนึ่ง ระบบก็จะไม่ล่ม ดังนั้นการบันทึกเอกสารจึงต้องระบุเป็น **"ปัจจัยร่วม" (Contributing Factors)** ให้ครบทุกมิติ

### 11.5 การสร้างความปลอดภัยทางจิตใจและการใช้ Log เป็นข้อมูล ไม่ใช่หลักฐานเอาผิด (Psychological Safety & Log as Fact)
- **นิยามใหม่ของการจัดเก็บ Log ในระบบเครือข่ายและเซิร์ฟเวอร์**:
  - ระบบบันทึกประวัติการทำงาน (Audit Logs) บันทึกข้อมูลละเอียดว่า ใครล็อกอินเข้าอุปกรณ์เวลาใด พิมพ์คำสั่งใด หรือแก้ไขค่าคอนฟิกตัวใด
  - **มุมมองเชิงบวกทางวิศวกรรม**: บันทึกเหล่านี้มีไว้เพื่อเป็น **"ข้อมูลข้อเท็จจริง (Fact / Data)"** ในการแกะรอยลำดับเหตุการณ์ (Tracking) เพื่อทำความเข้าใจว่าระบบได้รับคำสั่งใดและมีพฤติกรรมอย่างไร ซึ่งจะนำไปสู่การหามาตรการป้องกันเชิงเทคนิค
  - **ข้อห้ามทางวัฒนธรรม**: ห้ามนำ Log ไปใช้เป็น **"พยานหลักฐานในการเอาผิดบุคคล (Evidence for Punishment)"** เพราะจะทำให้วิศวกรพยายามหลีกเลี่ยงการบันทึก หรือแก้ไขประวัติคำสั่งเพื่อปกปิดความผิด
- **วัฒนธรรมการรับผิดชอบร่วมกันในทีม (Shared Team Responsibility)**:
  - ผู้สอนถ่ายทอดประสบการณ์การบริหารทีมว่า สมาชิกทุกคนในทีมมีความเท่าเทียมกัน (Flat Structure) ทำงานร่วมกันในฐานะทีม
  - เมื่อเกิดความผิดพลาดขึ้นในการปฏิบัติงาน **ผู้นำทีมมีหน้าที่ออกหน้ารับผิดชอบในนามของทีมทั้งหมด** โดยไม่มีการโยนความผิดไปที่ลูกน้องคนใดคนหนึ่ง วัฒนธรรมนี้ช่วยเสริมสร้างความปลอดภัยทางจิตใจ (Psychological Safety) และกระตุ้นให้สมาชิกทุกคนกล้าเปิดเผยข้อผิดพลาดอย่างรวดเร็ว

### 11.6 ข้อสั่งการปฏิบัติการ Lab: การติดตั้ง Proxmox VE, การเข้าสายแลน และการเตรียมรับมือ Chaos Injection (Lab Directives & Data Center Rules)
- **การเตรียมจำลองเหตุการณ์ขัดข้องโดยผู้สอน (Chaos Engineering Simulation)**:
  - ผู้สอนประกาศเตือนล่วงหน้าว่า เมื่อนักศึกษาติดตั้งระบบแม่ข่ายและวางเครือข่ายเสร็จสิ้น **ผู้สอนจะทำการสุ่มแทรกแซงความผิดปกติ (Simulated Fault Injection) เข้าสู่ระบบของแต่ละกลุ่มอย่างต่อเนื่อง**
  - แต่ละกลุ่มต้องจัดเตรียมระบบตรวจวัด (Monitoring), การแจ้งเตือน (Alerting) และการจัดเวรยาม On-call เพื่อรับมือกับเหตุการณ์จำลอง หากกลุ่มใดไม่มีระบบตรวจวัด ระบบจะล่มโดยไม่มีใครทราบ
- **เกณฑ์ขั้นต่ำของการติดตั้งระบบแม่ข่าย (Proxmox VE & VM Baseline)**:
  - ทุกกลุ่มต้องติดตั้งระบบปฏิบัติการ Proxmox VE (PVE) ลงบนเครื่องเซิร์ฟเวอร์จริง (Bare-metal Server) ให้สำเร็จ
  - เงื่อนไขขั้นต่ำถัดไป: **แต่ละเซิร์ฟเวอร์ต้องมีการติดตั้งและเปิดใช้งาน Virtual Machine (VM) อย่างน้อย 1 เครื่อง** เพื่อพร้อมสำหรับการจัดสรรภาระงาน
  - ให้แต่ละกลุ่มจัดทำเอกสารตรวจสอบสถานะ (Checklist Sheet) ระบุเวอร์ชันของระบบปฏิบัติการ และสถานะความคืบหน้าอย่างต่อเนื่อง
- **กฎระเบียบและข้อกำหนดการปฏิบัติงานทางกายภาพใน Data Center**:
  - **การเตรียมสายแลน (LAN Cable Policy)**: ไม่อนุญาตให้หยิบสายแลนสำเร็จรูปในห้องปฏิบัติการออกไปใช้อีกต่อไป นักศึกษาแต่ละกลุ่มต้องวัดระยะทางจริงจากตำแหน่งเซิร์ฟเวอร์ในตู้แร็คไปยังสวิตช์ด้านบน และทำการ **"เข้าหัวสายแลนด้วยตนเอง"** ให้มีความยาวเหมาะสมและเพียงพอต่อการทำ Redundancy (Link Aggregation)
  - **หลักการเข้าปฏิบัติงานรอบเดียวให้จบ (One-shot Execution)**: วางแผนการเข้าทำงานอย่างรอบคอบ เตรียมอุปกรณ์ สายไฟ สายแลน และหัวแปลงให้ครบถ้วน ติดตั้งและทดสอบการเปิดเครื่องและการเข้าถึงระยะไกล (Remote Access) ให้สำเร็จภายในครั้งเดียว ไม่เข้าออกห้องหลายรอบโดยไม่จำเป็น
  - **กฎการเข้าห้อง Data Center ชั้น 10 ในวันหยุด**: ในวันหยุดราชการเจ้าหน้าที่อาคารไม่เข้าปฏิบัติงาน การเบิกกุญแจห้องจำเป็นต้องผ่านกระบวนการเขียนคำร้องที่มีขั้นตอนซับซ้อน ดังนั้นจึง **ไม่อนุญาตให้นักศึกษาเข้าปฏิบัติงานในวันหยุด** ให้เข้าทำงานเฉพาะวันและเวลาทำการปกติ เว้นแต่เป็นเหตุฉุกเฉินร้ายแรงเท่านั้น
